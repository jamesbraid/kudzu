# Device unit numbers and the ioconfig file

How the IRIX 6.5.30 IP35 kernel (`6.5.30/unix.IP35`) keeps the "controller number" of a hardware-graph vertex, and where the messages "unit number %d from ioconfig is invalid" and the Gigabit Ethernet unit limit come from. Addresses are in `6.5.30/unix.IP35` unless a file is named. The user-space program (`6.5.30/sbin/ioconfig`) is held and is read in the last two sections; no `/etc/ioconfig.conf` file from a running system is held, so the file format comes from the program's reader and writer.

## Where the number lives

A vertex's controller number is a word in one of its inventory records, not a field of the vertex. The inventory records of a vertex hang from a label of that vertex (`graph_info_get_LBL` with the label string "_invent" at `0xc0000000004d61c8`, read by `hwgraph_inventory_get_next`).

- `device_controller_num_get` (`6.5.30/unix.IP35` `0xc0000000002772c8`, 28 bytes) calls `hwgraph_controller_num_get` with its own arguments and returns the result. Established.
- `device_controller_num_set` (`6.5.30/unix.IP35` `0xc0000000002772e4`, 28 bytes) calls `hwgraph_controller_num_set` with its own arguments and returns the result. Established.
- `hwgraph_inventory_get_next` (`6.5.30/unix.IP35` `0xc000000000341f40`, 180 bytes) takes a vertex (a0), a cursor (a1) and an output pointer (a2). It returns 3 when the vertex is -1 or the cursor was started on a different vertex, 2 when the "_invent" label cannot be found, and 0 when it stored a record pointer through a2. A cursor whose first word is -1 is started on the vertex and its doubleword at +16 is cleared; the first call then reads the label's record list head, each later call follows the first doubleword of the current record. Established.
- `device_inventory_get_next` (`6.5.30/unix.IP35` `0xc000000000277280`, 44 bytes) calls `hwgraph_inventory_get_next` and returns the record pointer it stored, or 0 for any nonzero status. Established.
- `hwgraph_controller_num_get` (`6.5.30/unix.IP35` `0xc000000000341ff4`, 96 bytes) copies the 24-byte template at the pool word gp-4408 (`0xc0000000015ea520`: a first word of -1 and zeros after it) to the stack as the cursor, and fetches the vertex's first inventory record with `device_inventory_get_next`. With no record it returns -1. Otherwise it returns the word at +20 of the record when the record's class (the word at +8) is 8, and the word at +16 for every other class. Established.
- `hwgraph_controller_num_set` (`6.5.30/unix.IP35` `0xc000000000342054`, 156 bytes) fetches the first record the same way and does nothing when there is none. When the class is 8 it stores the new number as the word at +20. When the class is 25 or 27 it fetches the next record and stores the number at +16 of that one (the second record's class is not tested, and nothing is stored if there is no second record). For any other class it stores at +16 of the first record. Established.

The two routines are not symmetric: for a vertex whose first record has class 25 or 27, the setter writes the second record while the getter reads the first record's +16. Whether any vertex has such a first record is not read. The vertex itself is never written, and the setter never creates a record, so a vertex with no inventory record keeps the answer -1.

## Who sets it in the kernel

`device_controller_num_set` is called from 23 sites (found by scanning the whole disassembly), in these routines: `scsi_ctlr_nums_add` (2), `ioc4_eiattach` (2), `eiattach` (2), `usb_pckm_init`, `usb_pckm_rmalias`, `ioc4_pckm_rmalias`, `ioc3_pckm_rmalias`, `dkscioctl`, `smfd_alias_make`, `htp_guiop`, `ioc3_serial_attach` (2), `ioc4_serial_attach` (4), `fdfs_newroot` and `dsioctl` (3). The arguments were read only at three of them:

- `ioc3_serial_attach` on the console port: `device_controller_num_set(vertex, 1)` ([ip35-ioc3.md](ip35-ioc3.md)).
- `dkscioctl` (the site at `0xc0000000001099a8`) and `dsioctl` (the site at `0xc00000000043f99c`): each reads the controller number of one vertex with `device_controller_num_get` and sets that same number on a second vertex, then builds a hardware-graph alias (`dk_alias_make` in `dkscioctl`; a `sprintf` name and further graph calls in `dsioctl`). The vertex chosen is reached through three pointer loads from a record; what those records are was not worked out. Inferred: the disk alias takes the controller number of its host controller.

The other sites were not read, so where their numbers come from is not established. None of them is the user-space entry: that is the attribute path described in "How user space sets the number".

## Who reads it, and the two messages

- `if_egopen` (`6.5.30/usr/cpu/sysgen/IP35boot/if_eg.o` `0xc50`) is the Gigabit Ethernet open routine. Its first argument is the vertex. It fetches the driver record with `hwgraph_fastinfo_get` (a missing record returns 5); a halfword at record +26 other than -1 means the unit is already set and the routine returns 0 at once. Otherwise it calls `device_controller_num_get`. A negative result logs at level 1 "%v: eg_open: vertex missing ctlr number" and returns 5 (this is not the "from ioconfig" message). A result of 32 or more (`slti 32` fails) logs at level 1 the "eg%d: The Gigabit Ethernet unit eg%d exceeds the system limit of %d cards ..." message with the number, the number, 32 and 32 as its arguments, calls `if_egdetach` and returns 5. Otherwise it stores the number as the halfword at +26 and, when the word at +1204 is not -1, builds a name with `sprintf` ("%s%d" from "eg" and the number) and registers it with `if_hwgraph_alias_add`; then it reads the MAC address and calls `ether_attach` with the unit. Established for the control flow and the limit of 32; the strings were read from the object's `.rodata` at offsets 0x2a0 ("%s%d"), 0x150 ("eg"), 0x2a8 (the missing-number message) and 0x2d0 (the limit message), through the first word of `.srdata`, which the relocation table points at the start of `.rodata` with a zero addend.
- `mad_ioctl` (`6.5.30/usr/cpu/sysgen/IP35boot/mad_dd.o` `0x28`, 268 bytes) is the audio card's control entry, not attach. It acts only on the request `0x6d687767` (the four characters "mhwg"); every other request returns 0 after the soft state lookup. With a missing soft state it logs at level 4 and returns 5. It then calls `device_controller_num_get` on the vertex; a negative number logs at level 4 "%v: unit number %d from ioconfig is invalid" (the vertex and the number) and returns 5. Otherwise it formats two names into the soft state at +300 and +332 from the number, sets the default subsystem priority with `kdsp_set_default_subsys_pri` to the number plus 10 (or plus 20 when the word at soft +5528 is nonzero), adds the path "audio" under the root with `hwgraph_path_add` and then calls `hwgraph_edge_add` with the new vertex, the word at soft +560 and the first name, the string at soft +300 ("MAD%d"), and returns 0. Established for the request value, the negative test, the two names ("MAD%d" and "MAD %d"), the priority and the edge call's arguments; what the word at soft +560 is was not worked out.
- The same message is also in `rad_dd.o`, `emu_dd.o` and `usbaudio_dd.o` of the 6.5.30 IP35 objects (found with a byte search of `usr/cpu/sysgen/IP35boot`); only the audio objects were not read beyond the message; whether each calls `device_controller_num_get` was not checked. Inferred that they follow the `mad_ioctl` pattern.

So the kernel never invents a unit number for these drivers: the number must already be on the vertex's inventory record, and an unset one (-1) is rejected. The request `0x6d687767` is one of a family of four-character or small-integer "make hardware-graph" requests that the user-space program sends after setting the number; the SCSI host adapter's request 29446 ([driver-ioctls.md](driver-ioctls.md)) reads the number the same way.

## What the shipped configuration fragments say

The 6.5.22 sysgen directories carry `var/sysgen.IP27/ioconfig`, `var/sysgen.IP30/ioconfig` and `var/sysgen.IP35/ioconfig`, each with a `README` and fragments `dmedia`, `ifcl`, `usb` and `vme`. They are the input format of the user-space program; the README defines the columns:

`<class> <type> <state> <suffix> <pattern> <start_num> <ioctl_num>`

where class, type and state are the numbers of an inventory record (the same three fields the kernel stores with `device_inventory_add`), -1 in type or state means "any", `suffix` of -1 is ignored, `pattern` of -1 means the base name of the device's canonical name is used, `start_num` is the first number to hand out, and `ioctl_num` is the driver request to send after the number is assigned (-1 means none). A more specific entry must come after a more general one. Examples shipped: class 10 type 7 start 1 request `0x6d687767` (the audio card, matching the `mad_ioctl` request above); class 26 type 769 (a USB keyboard, request `0x7501`); class 13 type 0 start 1 request `0x20007363` (VME); the README's own examples: class 4 type 16 suffix "d" pattern "tty" start 2 request `0x7a05` for serial ports, and class 14 type 1 start 2 for the PC mouse. Established as the contents of those shipped files (read in full for the README, `dmedia`, `ifcl` and `vme`; `usb` read for its first entries).

Inferred, from the column meanings and the kernel side above: the user-space program walks the hardware graph, matches each vertex's inventory record against these lines, assigns the next number from `start_num` (remembered in `/etc/ioconfig.conf`, named in the Ethernet limit message), stores it with the controller-number setter and then sends `ioctl_num` to the driver. The next two sections replace this inference with the program and kernel code that were read.

## How user space sets the number

No control request sets the controller number. The user-space program writes it as a named attribute of the vertex's path, and the hardware-graph file system's attribute-set operation turns that into the one kernel setter already described.

- Kernel attribute-set operation of the hardware-graph file system (`6.5.30/unix.IP35`, the unnamed routine at `0xc00000000042961c`; no symbol covers it, it sits between `fdfs_newroot` and `hwginit`). Its arguments are the vnode, the attribute name, the value pointer, the value length, flags and credentials. It asks `cap_able_cred` (`0xc000000000429664`) for the capability bit 1 << 37 (the shift is in the delay slot at `0xc000000000429668`) and returns 1 when the caller lacks it. A name equal to `_controller_name` (compare at `0xc000000000429678`) returns 22 when the value length is under 4 (`sltiu` at `0xc000000000429684`); otherwise it calls `device_controller_num_set` (`0xc00000000042971c`) with the vertex (the word at +0x48 of the first doubleword of the vnode) and the first word of the value, and returns 0. Any other name that starts with an underscore returns 17 (`0xc000000000429714`). Names without a leading underscore are user attributes: the value is copied into kernel memory and stored by routines I did not follow. Established for the `_controller_name` and underscore branches; the user-attribute branch is unread.
- The matching read operation (the routine around `0xc0000000004291c0` to `0xc0000000004295b8`) recognises four reserved names by string compare: `_devname`, `_drivername`, `_masternode` and `_inventory` (strings at `0xc0000000004dfe10` to `0xc0000000004dfe40`). `_inventory` walks the vertex's records with `device_inventory_get_next` and copies 24 bytes starting at +4 of each record to the caller, so the user-space record is six words: one word taken from +4 of the kernel record that the program never reads, then class, type, controller, unit and state. That is why the user program reads the class at +4 and the type at +8 where the kernel reads +8 and +12 of its own record, and why the getter's "word at +20 for class 8, else +16" is the user's unit word (+16) and controller word (+12). Established for `_inventory`; the other three names were not read to the end.

## The user-space program

`6.5.30/sbin/ioconfig` (N32, 41768 bytes, stripped, built for 6.5.30m; the `.debug_frame` section only). Routine addresses below are in that file; the names come from the program's own strings and its dynamic imports, and a name that is only an inference says so. Established unless marked.

Invocation (`parse_args`, `0x10003f38`; option string `df:2`): `-d` turns on debug printing; `-f DIR` names the starting directory (the path is converted with `filename_to_devname`; if that fails the text is used as given) and is required, since without it the routine prints `usage: ioconfig [-d]  -f starting_directory` and exits 0 (the test of a flag set by `-f` is at `0x10004034`); `-2` changes the run mode from 1 to 2. Mode 1 (the initial value of the mode word at `0x10008e28`) walks the tree under the starting directory; mode 2 walks `/hw/scsi_ctlr` only. A bad option prints the same usage text. The machine type is read with `uname` and the program records whether the machine field contains the text `IP35`.

Startup and tables:

- It builds two tables (`init_tables`, `0x10002414`): 256 argument rows of 0xd0 bytes (two 100-byte strings, suffix and pattern, then a start number and a request word) and 256 process rows of 0x14 bytes (class, type, state, a flag word, and a pointer to an argument row or to a handler). Ten rows are built in. On a machine whose type contains `IP35`, the start number of two built-in rows (class 14, type 1, state 0 and state 1, which are `INV_MISC` / `INV_MISC_PCKM`, keyboard and mouse) is set to 0 and their request to `0x7001`.
- The ten built-in rows (class by `sys/invent.h`; request in hex): class 2 type 1 (disk / SCSI controller, a handler routine at `0x10002e30`, start from the kernel, request `0x7306`); class 4 type 16 (serial, `INV_IOC3_DMA`; suffix `d`, pattern `tty`, start 3, request `0x7a05`); class 8 any type (network; start 0); class 8 type 19 (`INV_ETHER_EF`; start 1); class 8 type 37 (`INV_NET_GENERIC`; start 1). For class 8 the table's "type" column is matched against the record's controller word, not its type word (the substitution is at `0x100037fc`), which is why these two values are the Ethernet-controller and generic-network values of `sys/invent.h`; class 10 type 5 (audio, `INV_AUDIO_RAD`; pattern `rad_subsys`, start 1, request `0x6d687767`); class 14 type 1 state 1 and state 0 (keyboard and mouse; start 2 off IP35); class 14 type 2 (`INV_MISC_IOC3_EINT`; start 2, request `0x6517`); class 5 type 6 (`INV_EPP_ECP_PLP`, parallel; start 1, request `0x700c`). Read from the initialised data at `0x10008e48` and `0x10009668`.
- `device_tables_update` (`0x100025d0`) then reads every file in `/var/sysgen/ioconfig` (skipping `.` and `..`), ignores lines that start with `#` or hold only whitespace, parses each remaining line with `%d %d %d %s %s %d %x` (class, type, state, suffix, pattern, start number, request in hex) and appends a row; a line that does not parse prints a format complaint and is skipped. Rows are appended up to 256; past that it prints "Reached the pre-defined max# of devices". The format message in the program still lists an extra `<case>` column that the parser does not read; the shipped README has the seven-column form. A file-defined row has its flag word set to 1.
- Lookup (`dpt_search`, `0x10002534`, called with class, type and state) scans the process rows from the last to the first for the first row whose class matches, whose type is -1 or equal, and whose state is -1 or equal. A later file row therefore overrides an earlier or built-in one, which is why the README demands generic lines first.

The walk (mode 1): `nftw` (depth 100, physical) visits the tree under the starting directory with `walk_fn` (`0x10003674`). A directory whose path matches one of `/hw/.invent`, `/hw/hw`, `/hw/xvm`, `/hw/input*` (table at `0x10008e30`, tested with `fnmatch`) is skipped for its own visit. For every other path `walk_fn` fetches the `_inventory` attribute (`attr_get`), splits it into 24-byte records and looks each up. A row with a non-zero flag word and an argument row goes to `process_ioc_device_vertex` (`0x100029ac`); the one built-in row with a zero flag calls its handler instead. `process_ioc_device_vertex` prints a "FOUND ..." line per kind (SCSI controller, serial, network, audio, keyboard or mouse, parallel) when debugging, calls `ioc_control_num_update`, then forms the node name from the suffix (path plus `/` plus suffix, with the special pattern text `-1` meaning no suffix) and, when the row's request is not -1, opens it, sends the request with no argument, and closes it. An open failure is reported at level 1.

Numbering (`ioc_control_num_update`, `0x10002c98`; it takes the vertex path, the pattern, the start number and the inventory record):

1. `ioconfig_find` (`0x10002080`) rewinds `/etc/ioconfig.conf` and reads it line by line, skipping lines that start with `#` and blank lines. Each line is `<number> <path>` (scanned with `%d %s`). The key is the pattern, or the base name of the path when the pattern is `-1`. A line whose path equals the vertex path exactly returns its number. Every other line whose path contains the key as a whole `/`-delimited component raises a running counter, initially the start number, to one above that line's number. The result is the persisted number (-1 when absent) and the next free number for that device family. Established for the exact-match return and the counter rule; the component-boundary test is read from the compare against 0x2f on both sides of the match and is inferred to be that.
2. The kernel's current number comes from the `_inventory` record: the unit word when the class is 8, the controller word otherwise (`ioc_ctlr_num_get`, `0x10001f90`).
3. If the kernel number is -1, or the class is 26 (`INV_USB`), or the machine is an IP35 and the record is class 14 type 1 (the keyboard and mouse), the persisted number wins: when the file has none, the program appends `<next free number> <path>` to the file (`ioconfig_add`, `0x100023c0`; it flushes after each line) and uses that number; either way it stores the number on the vertex with `ioc_ctlr_num_put` (`0x10001ff8`), which is `attr_set(path, "_controller_name", &number, 4, 0)` and, on failure, reports the attribute error and returns 0. Elsewhere, a kernel number that equals the persisted one or has no persisted counterpart is left alone and nothing is written to the file. If the two differ and the kernel number is at least the start number, the program reports through its error routine (message 6: the persisted number differs from the hardware-graph number, the system may have been reconfigured) and keeps the kernel's number. Every report of that routine also goes to `syslog` at priority 6 with the prefix `IOCONFIG:`; below the start number the difference is ignored (printed only when debugging).

So the file records only numbers the program itself handed out for vertices the kernel left unnumbered (or for the USB and keyboard/mouse classes), keyed by the vertex path, and the next number for a family is one above the highest recorded number whose path contains the family key, or the start number when none.

SCSI controllers (handler `0x10002e30`): it asks the kernel for the first user-assignable controller number with `syssgi` selector 408 (`0x198`, the selector documented in [syssgi.md](syssgi.md)), runs the numbering above with the pattern `scsi_ctlr`, and for a path that does not contain `.master` opens the path's `bus` node and sends request `0x7306` (29446, the host adapter request in [driver-ioctls.md](driver-ioctls.md)), then forks a child (`spawn_scsi_ctlr_process`, `0x100035b8`) that walks the controller's subtree with `scsi_ctlr_walk_fn` (`0x10003174`) and exits. The walk function inspects disks and removable media (`check_removable_media`, `check_raid_controller`) and issues requests `0x642e` and `0xc0044470` on opened nodes; what those requests do was not read, and the per-disk rules are unknown. In mode 2 the program instead lists `/hw/scsi_ctlr`, resolves symbolic links with `readlink`, and spawns one such child per controller.

After the walk the parent waits for all children (loop on `wait` until `ECHILD`), then applies `/etc/ioperms` (`ioc_owner_perm_set`, `0x10003874`): each non-comment line is `<device name> <octal mode> <owner> <group>`; a name containing `*` is handled by two `system` calls that pipe the name to `xargs chown` and `xargs chmod`; any other name is resolved with `getpwnam` and `getgrnam`, then `chown` and `chmod`. An unknown owner or group is reported (level 13) and the line skipped. The program then calls `syssgi` with selector 197 (`0xc5`; documented in [syssgi.md](syssgi.md) as the early swap registration call) and finally opens `/etc/ioconfig.conf` read-write only to `fsync` and close it (`ioc_control_num_file_sync`, `0x10003cd4`). Inferred reason for the order: swap devices are named by disk paths whose numbers are only stable after the numbering pass. The arguments of the selector-197 call were not read.

Grades. Established: the attribute name and the 4-byte value; the capability check and the two kernel return values; the six-word user record layout and its match to the kernel record; the table sizes and built-in rows; the file line forms; the startup, walk and ownership sequence. Inferred: the interpretation of the whole-component test in `ioconfig_find`; the reason for the swap call. Unknown: what requests `0x642e` and `0xc0044470` do; what the per-disk walk renames; the contents of any `/etc/ioconfig.conf` on a real system (none is held), which would settle the path form (`/hw/...` canonical names versus device-name aliases); the stored forms for removable media. What would settle the last: an installed system's `/etc/ioconfig.conf` and `/etc/ioperms`, or a run of the program against a booted guest.
