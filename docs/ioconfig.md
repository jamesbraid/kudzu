# Device unit numbers and the ioconfig file

How the IRIX 6.5.30 IP35 kernel (`6.5.30/unix.IP35`) keeps the "controller number" of a hardware-graph vertex, and where the messages "unit number %d from ioconfig is invalid" and the Gigabit Ethernet unit limit come from. Addresses are in `6.5.30/unix.IP35` unless a file is named. The user-space `ioconfig` program and `/etc/ioconfig.conf` are not held, so the writer of the number from user space is not read here (see [open-questions.md](open-questions.md)).

## Where the number lives

A vertex's controller number is a word in one of its inventory records, not a field of the vertex. The inventory records of a vertex hang from a label of that vertex (`graph_info_get_LBL` with the label string "_invent" at `0xc0000000004d61c8`, read by `hwgraph_inventory_get_next`).

- `device_controller_num_get` (`6.5.30/unix.IP35` `0xc0000000002772c8`, 28 bytes) calls `hwgraph_controller_num_get` with its own arguments and returns the result. Established.
- `device_controller_num_set` (`6.5.30/unix.IP35` `0xc0000000002772e4`, 28 bytes) calls `hwgraph_controller_num_set` with its own arguments and returns the result. Established.
- `hwgraph_inventory_get_next` (`6.5.30/unix.IP35` `0xc000000000341f40`, 180 bytes) takes a vertex (a0), a cursor (a1) and an output pointer (a2). It returns 3 when the vertex is -1 or the cursor was started on a different vertex, 2 when the "_invent" label cannot be found, and 0 when it stored a record pointer through a2. A cursor whose first word is -1 is started on the vertex and its doubleword at +16 is cleared; the first call then reads the label's record list head, each later call follows the first doubleword of the current record. Established.
- `device_inventory_get_next` (`6.5.30/unix.IP35` `0xc000000000277280`, 44 bytes) calls `hwgraph_inventory_get_next` and returns the record pointer it stored, or 0 for any nonzero status. Established.
- `hwgraph_controller_num_get` (`6.5.30/unix.IP35` `0xc000000000341ff4`, 96 bytes) copies the 24-byte template at the pool word gp-4408 (`0xc0000000015ea520`: a first word of -1 and zeros after it) to the stack as the cursor, and fetches the vertex's first inventory record with `device_inventory_get_next`. With no record it returns -1. Otherwise it returns the word at +20 of the record when the record's class (the word at +8) is 8, and the word at +16 for every other class. Established.
- `hwgraph_controller_num_set` (`6.5.30/unix.IP35` `0xc000000000342054`, 156 bytes) fetches the first record the same way and does nothing when there is none. When the class is 8 it stores the new number as the word at +20. When the class is 25 or 27 it fetches the next record and stores the number at +16 of that one (the second record's class is not tested, and nothing is stored if there is no second record). For any other class it stores at +16 of the first record. Established.

The two routines are not symmetric: for a vertex whose first record has class 25 or 27, the setter writes the second record while the getter reads the first record's +16. Whether any vertex has such a first record is not read. The vertex itself is never written, and the setter never creates a record, so a vertex with no inventory record keeps the answer -1.

## Who sets it in the kernel

`device_controller_num_set` is called from 23 sites (found by scanning the whole disassembly), in these routines: `scsi_ctlr_nums_add` (2), `ioc4_eiattach` (2), `eiattach` (2), `usb_pckm_init`, `usb_pckm_rmalias`, `ioc4_pckm_rmalias`, `ioc3_pckm_rmalias`, `dkscioctl`, `smfd_alias_make`, `htp_guiop`, `ioc3_serial_attach` (2), `ioc4_serial_attach` (4), `fdfs_newroot` and `dsioctl` (3). The arguments were read only at three of them:

- `ioc3_serial_attach` on the console port: `device_controller_num_set(vertex, 1)` ([ip35-ioc3.md](ip35-ioc3.md)).
- `dkscioctl` (the site at `0xc0000000001099a8`) and `dsioctl` (the site at `0xc00000000043f99c`): each reads the controller number of one vertex with `device_controller_num_get` and sets that same number on a second vertex, then builds a hardware-graph alias (`dk_alias_make` in `dkscioctl`; a `sprintf` name and further graph calls in `dsioctl`). The vertex chosen is reached through three pointer loads from a record; what those records are was not worked out. Inferred: the disk alias takes the controller number of its host controller.

The other sites were not read, so where their numbers come from is not established.

## Who reads it, and the two messages

- `if_egopen` (`6.5.30/usr/cpu/sysgen/IP35boot/if_eg.o` `0xc50`) is the Gigabit Ethernet open routine. Its first argument is the vertex. It fetches the driver record with `hwgraph_fastinfo_get` (a missing record returns 5); a halfword at record +26 other than -1 means the unit is already set and the routine returns 0 at once. Otherwise it calls `device_controller_num_get`. A negative result logs at level 1 "%v: eg_open: vertex missing ctlr number" and returns 5 (this is not the "from ioconfig" message). A result of 32 or more (`slti 32` fails) logs at level 1 the "eg%d: The Gigabit Ethernet unit eg%d exceeds the system limit of %d cards ..." message with the number, the number, 32 and 32 as its arguments, calls `if_egdetach` and returns 5. Otherwise it stores the number as the halfword at +26 and, when the word at +1204 is not -1, builds a name with `sprintf` ("%s%d" from "eg" and the number) and registers it with `if_hwgraph_alias_add`; then it reads the MAC address and calls `ether_attach` with the unit. Established for the control flow and the limit of 32; the strings were read from the object's `.rodata` at offsets 0x2a0 ("%s%d"), 0x150 ("eg"), 0x2a8 (the missing-number message) and 0x2d0 (the limit message), through the first word of `.srdata`, which the relocation table points at the start of `.rodata` with a zero addend.
- `mad_ioctl` (`6.5.30/usr/cpu/sysgen/IP35boot/mad_dd.o` `0x28`, 268 bytes) is the audio card's control entry, not attach. It acts only on the request `0x6d687767` (the four characters "mhwg"); every other request returns 0 after the soft state lookup. With a missing soft state it logs at level 4 and returns 5. It then calls `device_controller_num_get` on the vertex; a negative number logs at level 4 "%v: unit number %d from ioconfig is invalid" (the vertex and the number) and returns 5. Otherwise it formats two names into the soft state at +300 and +332 from the number, sets the default subsystem priority with `kdsp_set_default_subsys_pri` to the number plus 10 (or plus 20 when the word at soft +5528 is nonzero), adds the path "audio" under the root with `hwgraph_path_add` and then calls `hwgraph_edge_add` with the new vertex, the word at soft +560 and the first name, the string at soft +300 ("MAD%d"), and returns 0. Established for the request value, the negative test, the two names ("MAD%d" and "MAD %d"), the priority and the edge call's arguments; what the word at soft +560 is was not worked out.
- The same message is also in `rad_dd.o`, `emu_dd.o` and `usbaudio_dd.o` of the 6.5.30 IP35 objects (found with a byte search of `usr/cpu/sysgen/IP35boot`); only the audio objects were not read beyond the message; whether each calls `device_controller_num_get` was not checked. Inferred that they follow the `mad_ioctl` pattern.

So the kernel never invents a unit number for these drivers: the number must already be on the vertex's inventory record, and an unset one (-1) is rejected. The request `0x6d687767` is one of a family of four-character or small-integer "make hardware-graph" requests that the user-space program sends after setting the number; the SCSI host adapter's request 29446 ([driver-ioctls.md](driver-ioctls.md)) reads the number the same way.

## What the shipped configuration fragments say

The 6.5.22 sysgen directories carry `var/sysgen.IP27/ioconfig`, `var/sysgen.IP30/ioconfig` and `var/sysgen.IP35/ioconfig`, each with a `README` and fragments `dmedia`, `ifcl`, `usb` and `vme`. They are the input format of the user-space program; the README defines the columns:

`<class> <type> <state> <suffix> <pattern> <start_num> <ioctl_num>`

where class, type and state are the numbers of an inventory record (the same three fields the kernel stores with `device_inventory_add`), -1 in type or state means "any", `suffix` of -1 is ignored, `pattern` of -1 means the base name of the device's canonical name is used, `start_num` is the first number to hand out, and `ioctl_num` is the driver request to send after the number is assigned (-1 means none). A more specific entry must come after a more general one. Examples shipped: class 10 type 7 start 1 request `0x6d687767` (the audio card, matching the `mad_ioctl` request above); class 26 type 769 (a USB keyboard, request `0x7501`); class 13 type 0 start 1 request `0x20007363` (VME); the README's own examples: class 4 type 16 suffix "d" pattern "tty" start 2 request `0x7a05` for serial ports, and class 14 type 1 start 2 for the PC mouse. Established as the contents of those shipped files (read in full for the README, `dmedia`, `ifcl` and `vme`; `usb` read for its first entries).

Inferred, from the column meanings and the kernel side above: the user-space program walks the hardware graph, matches each vertex's inventory record against these lines, assigns the next number from `start_num` (remembered in `/etc/ioconfig.conf`, named in the Ethernet limit message), stores it with the controller-number setter and then sends `ioctl_num` to the driver. The setter reached from user space was not identified; it is not among the call sites above. Unknown until the program is read: the assignment order and how the file persists the mapping.
