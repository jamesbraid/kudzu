# Kernel text replication, user text replication and node numbering after start-up

Answers four questions about the IRIX 6.5.30 kernels for SN0 (`unix.IP27`: Origin 200/2000, Onyx2) and SN1 (`unix.IP35`: Origin 3000, Onyx 3000). Evidence: the linked kernels `6.5.30/unix.IP27` and `6.5.30/unix.IP35` (disassembled for this page), the `mtune/numa` file of the 6.5.22 configuration tree, and the shipped manual pages `replication(5)`, `numa(5)`, `mmci(5)`, `systune(1M)`, `sn(1)`, `icrash(1M)` and `numa_view(1)` from the 6.5.30 media. The published-document library service was down while this was written (every backend refused connections), so the SGI administration and tuning guides were not consulted; the manual pages above are the published text used. No kernel was run. Grades follow [AGENTS.md](../AGENTS.md). The sections down to [Seeing where each CPU's text lives](#seeing-where-each-cpus-text-lives) are 6.5.30; [IRIX 6.5.22](#irix-6522), [IRIX 6.5.23](#irix-6523) (not held) and [Differences from 6.5.30](#differences-from-6530) follow them. Sibling pages: [page-migration.md](page-migration.md) (migration, and the removal of page replication in 6.5.23), [klconfig.md](klconfig.md) (node numbering and `setup_replication_mask`), [kernel-tracing-and-modules.md](kernel-tracing-and-modules.md) (patching replicated text).

## Short answers

| Question | Answer | Grade |
|---|---|---|
| Does the kernel replicate its own text per node? | Yes, on both platforms, at boot, controlled by one tunable, `numa_kernel_replication_ratio`, default 1 (a copy on every node). 0 means master node only. | Established |
| Does IRIX replicate user text (libc, shared libraries)? | Not in 6.5.30. A page-replication engine existed through 6.5.22, tied to executable mapping, but it was disabled by a kernel variable no tuning file sets, and 6.5.23 removed it. | Established (6.5.30 absence, 6.5.22 presence and off state); unknown (whether any 6.5.22 or earlier system ever ran it enabled) |
| Does a node's NASID, or the cached-alias size, change after the kernel starts? | No routine in the 6.5.30 kernels was found that does. The node tables are written only by `cpu_node_probe` and `do_cpumask`, called once from `mlreset`; the alias size register is written only in `mlreset`; no hot-plug, partition-join or migration routine touches them. The manual says compact node numbers can change across reboots. | Established for the writers found; inferred for "no other writer" |
| Quick guest-side view of which node holds each CPU's kernel text? | No tool prints it. `systune numa_kernel_replication_ratio` shows the policy only. The placement is derivable by hand (below). | Established (no shipped tool); inferred (the manual route) |

## Kernel text replication

`replicate_kernel_text` (`6.5.30/unix.IP35` 0xc000000000074d14, 376 bytes; `unix.IP27` 0xc000000000050874, 328 bytes) is called once, from `allowboot` (IP35 call at 0xc000000000066090; IP27 0xc000000000044478), on the boot processor. Its helpers are `copy_kernel` (IP35 0xc000000000074e8c, 152 bytes) and `set_ktext_source` (IP35 0xc000000000074f24, 152 bytes). Established.

Behaviour, read in full on IP35:

1. It checks that the end of the replicated range is above its start (the range runs from the first byte of `.text` to the end of the first `.rodata`, 0xc000000000040000 to 0xc000000000519ebf) and calls `cmn_err` otherwise.
2. It calls `set_ktext_source` for the master node with the master as source, so the master runs from its own copy (the original load).
3. For each compact node from 1 to `maxnodes` - 1 it tests the node's bit in `ktext_repmask` (IP35 0xc000000001652698, 512 bits; IP27 0xc0000000014dea48, 128 bits). If the bit is set it calls `copy_kernel` for that node's NASID (a `bcopy` of the range into that node's memory through the cached window, at the same offset the image has on the master) and makes that node the current source. Then, set or not, it calls `set_ktext_source` for the node with the current source. So a node without a copy is pointed at the most recent replicating node with a lower compact number, or the master if there is none. Established for IP35; the IP27 routine is the same shape and its size and addresses are read in [kernel-tracing-and-modules.md](kernel-tracing-and-modules.md); instruction-level equality was not rechecked here (inferred).
4. `set_ktext_source` writes the target node's kernel-variable record. Read: it stores a pointer to the record in the node's boot directory (node-local offset 0x21d0, written through the uncached memory window 0x96...), then writes into the record a word 0x5f4b565f at +0, the text-source NASID as a halfword at +4, the master NASID at +6, the text-source base address at +8 and the master base address at +16. Established for the stores. The public Linux names (`KLI_KERN_VARS`, `kern_vars_t`, magic "_KV_") match this layout; that is a hint, so the field names are inferred.
5. Each processor consumes the record in `bootstrap` (IP35 0xc000000000065468): it reads its own NASID from the local hub, loads the pointer at node-local offset 0x21d0, loads the halfwords at +4 and +6 and calls `mapped_kernel_setup_tlb` (IP35 0xc000000000065538; IP27 0xc000000000043808) with them. That routine writes wired TLB entry 1 with a 16 MB page pair: the first page (text and read-only data) at physical address (text-source NASID << 33) plus the kernel's own offset, the second (writable data and bss) at (master NASID << 33) plus that offset. On IP27 the shift is 32 (inferred from the NASID shift recorded in [klconfig.md](klconfig.md)). Established for IP35; the physical-address formula is established from the instruction sequence, the IP27 shift is inferred.

Consequences: a CPU's text node is the NASID in its own node's record at +4, not a per-CPU setting; all CPUs of a node share it. Data is never replicated; only the master holds the writable image. A patch must be written to every copy (see [kernel-tracing-and-modules.md](kernel-tracing-and-modules.md)).

### Control

`numa_kernel_replication_ratio`: default 1 in `mtune/numa` (6.5.22 and 6.5.30 identical) and in the linked kernels (IP35 symbol 0xc00000000163bf8c, IP27 0xc0000000014ca844, both a 4-byte word holding 1). `setup_replication_mask` (IP35 0xc000000000074c38; IP27 0xc0000000000507b8), called from `mlreset`, sets bit 0 and then bit i for each node i from 1 to `maxnodes` - 1 for which the ratio is nonzero and divides i exactly, then stores the mask's address at +64 of the node's global data area. So ratio 1 is every node, 2 is every second node, 0 is the master only. Established. The only reader of the tunable is `setup_replication_mask`, so the value matters at boot; `systune -r` can write the word on a running kernel but nothing re-reads it (inferred from the single reader; the systune binary was not read). The manual `replication(5)` describes the same rule and the default, and says the ratio is read at boot. A stale heading in `mtune/numa` says the whole replication group has "no effect on any systems, reserved for future"; it was written for the removed page-replication entries and is wrong for this one (the code above is live in 6.5.30). Established.

Other state: `ktext_repmask`, `get_freemem_start` (reserves the copy's space when sizing each node's free memory, see [klconfig.md](klconfig.md)). No other kernel symbol or tunable mentions kernel text replication.

## User text and page replication

6.5.30: no replication code. The routines removed in 6.5.23 are listed in [page-migration.md](page-migration.md#what-6523-removed-for-replication). What remains are strings `ReplicationDefault` and `ReplicationOne`, `pm_repl_srvc`, and the user-visible policy slots; `mmci(5)` states both replication policies "have not been implemented" and applying them "has no effect", and the replication row of its policy table is "(not implemented, retained for compatibility)". Established.

6.5.22 (and earlier): `repl_interpose` was called from the executable-mapping path and attached a replication behaviour to the executable's vnode; `rp_default_getpage` asked `repl_control` for a target node, `repl_resource_check` compared free memory with `numa_repl_mem_lowmark` and router traffic with `numa_repl_traffic_highmark_percentage`, and `page_replica_insert` entered the copy (addresses in page-migration.md). The enabling variable `numa_page_replication_enable` is 0 and is not a tuning-file entry; `numa_repl_control_enabled` likewise. Policy modules: `ReplicationDefault` and `ReplicationOne` (the latter by its name, one replica; its behaviour was not read, unknown). Established for the off state and the call chain; unknown for what a debugger-set non-zero value would have done.

The manual `numa(5)` still says the numa tunables tune "the aggressiveness of both migration and replication" and that automatic locality management exists on Origin 2000/200 only. Both are marketing for a disabled feature; for the replication half the kernel contradicts it.

Library text (libc and libraries) is therefore a single shared copy per page cache entry, placed by first touch, and moved at most by explicit migration calls (`migration(3C)`, `6.5.30/usr/sbin/dplace`) or, on Origin 2000/200 only, the automatic migration engine (page-migration.md). Inferred from the absence of replication code.

## Node renumbering and alias size after start

NASID tables. `nasid_to_compact_node`, `compact_to_nasid_node` and `cpuid_to_compact_node` (IP35 0xc000000001646f00, 0xc000000001647000, 0xc000000001647100; IP27 0xc0000000014d4c80, 0xc0000000014d4e80, 0xc0000000014d4f00) are filled by `cpu_node_probe` and `do_cpumask` ([klconfig.md](klconfig.md)). `cpu_node_probe` has one call site in each kernel, in `mlreset` (IP35 0xc00000000004db08; IP27 0xc0000000000262d4); `do_cpumask` is called only from `cpu_node_probe`. Of the 154 (IP35) and 177 (IP27) routines that load a pointer to these tables, the ones that also store halfwords through a computed pointer are boot, hardware-graph and statistics routines (for example `init_platform_nodepda`, `module_add_node`, `klhwg_add_node`, `init_pebrick`); none is named for hot-plug, node removal or renumbering, and the kernels have no symbol with `hotplug`, `offline` or `node_(add|remove)` in the name beyond `cpu_enabled`, `cpu_restrict` and an unrelated file-system quiesce. Established for the writers named; inferred that nothing else writes the tables (an indirect store through a copied table pointer was not ruled out in every routine). `numa(5)` says compact node and processor numbers "may change across reboots", which matches this, and describes NASIDs as the section of physical space a node covers. Established.

Cached-alias size. The alias size is the hub processor-interface register at offset 0x28 of the hub (the register Linux names `PI_CALIAS_SIZE`). `mlreset` writes it for every compact node through the remote hub window, with the value 2 (IP27 store at 0xc000000000026394; IP35 loop with stores at 0xc00000000004dc80 and 0xc00000000004dc88 covering both processor-interface blocks, offsets 0x18/0x28 and 0x200018/0x200028, plus a zero at +0x400190). The value 2 decodes in the kernel's own consumers as 4096 << (2 - 1) = 8 KB. The consumers `memory_iscalias` (IP35 0xc000000000050244; IP27 0xc00000000002b0a8), `page_iscalias` and `page_local_calias` do not cache the size: each loads a pointer from the global pointer area that holds 0x9200000001000028 (the local hub's alias-size register; read from the IP35 slot at gp+2440 and the IP27 slot at gp-24344) and reads the register on every call. If the value is 0 there is no alias; otherwise an address is an alias when its low 33 bits (IP35) or 32 bits (IP27) of the node-local offset are below 4096 << (value - 1). So a hardware-side change would be seen at once, but nothing in the kernel makes one: no other store to offset 0x28 was found in any routine that uses the hub window base (scan of all such routines on both kernels). Established for the consumers and the `mlreset` writes; inferred for "never changed afterwards". `protect_hub_calias` (IP35 0xc00000000004e29c, 64 bytes, called from `per_hub_init`) only calls `nasid_to_region` 64 times and stores nothing; the IP27 routine (0xc00000000002695c, 184 bytes) zeroes 64 pairs of directory-protection words in the alias window. Established.

Not covered: whether the PROM or the hub reprograms the NASID or alias size at partition reset (a reboot, so not "after the kernel starts"), and what happens to a router-visible node when a partition is reconfigured while the kernel runs; the cross-partition code is in [page-migration.md](page-migration.md). Unknown.

## Seeing where each CPU's text lives

No shipped command prints it. What exists:

- `systune numa_kernel_replication_ratio` (or `systune numa`) prints the policy value only (`systune(1M)`; the tunable is in the `tunename` table, see page-migration.md). Established.
- `/hw/nodenum` and `/hw/cpunum` give cnode and cpuid to node-path maps (`numa(5)`); `hinv`, `topology(1)` and `gfxtopology(1)` show structure and distances. None shows NASIDs or text sources. `numa_view(1)` shows placement of a process's mapped memory, not kernel text. `sn(1)` and `nstats(1)` are Origin 2000/200 migration controls and report nothing about replication. Established from the pages.
- `icrash(1M)` on a live system (`/unix`, `/dev/mem`): `nodepda`, `pda`, `dump addr count`, `dirmem`, `vtop` and `hubreg` exist. The first-principles route, inferred and untested: read `ktext_repmask` with `dump` using the symbol name; the set bits are the nodes with a copy. For a node N, compute its record from the node-local boot directory (physical address (NASID_N << 33) + 0x21d0 on IP35, << 32 on IP27, read as `0xa800000000000000` plus that) and `dump` the pointer, then the halfword at +4 of the record: that is the NASID whose copy N's processors execute. A CPU's node comes from `/hw/cpunum`; its NASID from `nasid_to_compact_node` and `compact_to_nasid_node` (`dump` on the symbols). Whether `icrash` accepts XKPHYS addresses in `dump`, and whether `vtop` handles the mapped kernel region, is not known.
- A behavioural check: compare `dump` of the first words of `.text` through the cached window at (NASID << 33) + 0x40180 for two nodes. Inferred.

### Kernel text replication (6.5.22)

| Item | IP35 | IP27 |
|---|---|---|
| `replicate_kernel_text` | 0xc000000000074bf4, 376 bytes | 0xc00000000004fef4, 328 bytes |
| called from `allowboot` at | 0xc0000000000663a0 | 0xc000000000043c18 |
| `copy_kernel` | 0xc000000000074d6c, 152 bytes | 0xc00000000005003c, 116 bytes |
| `set_ktext_source` | 0xc000000000074e04, 152 bytes | 0xc0000000000500b0, 128 bytes |
| `setup_replication_mask`, called from `mlreset` at | 0xc000000000074b18, 220 bytes; 0xc00000000004e528 | 0xc00000000004fe38, 188 bytes; 0xc0000000000260e8 |
| `ktext_repmask` | 0xc0000000015a8398 (8 words zeroed: 512 bits) | 0xc0000000014dd3c8 (2 words zeroed: 128 bits) |
| `numa_kernel_replication_ratio` (4-byte word, value 1) | 0xc000000001592784 | 0xc0000000014c95fc |
| `mapped_kernel_setup_tlb` | 0xc000000000065848, 168 bytes | 0xc000000000042fa8, 168 bytes |

Established for every row (symbol table and instruction reading).

Mask. `setup_replication_mask` zeroes `ktext_repmask`, sets bit 0, then sets bit i for each i from 1 to the node count minus one for which the ratio is nonzero and divides i exactly (a `div` and a remainder test; ratio 0 skips the loop), and stores the mask's address at +64 of the node's global data area. The ratio is read once, at IP35 0xc000000000074b5c and IP27 0xc00000000004fe64. A scan of every global-pointer load and every address formation (`lui` plus 16-bit add) finds no other reader on either kernel. Established.

Copy. `replicate_kernel_text(numnodes)` checks that the end of the range is not below its start (a `cmn_err` call otherwise), calls `set_ktext_source` with the master node as both arguments (IP35 call 0xc000000000074c94; IP27 0xc00000000004ff78), then for each compact node from 1 up tests its mask bit, calls `copy_kernel` if set (IP35 0xc000000000074ce4; IP27 0xc00000000004ffc8) and calls `set_ktext_source` for every node with the most recent copied-to node (or the master) as the source (IP35 0xc000000000074cf0; IP27 0xc00000000004ffd4). Same shape as the 6.5.30 reading above. Established.

Range. IP35: from 0xc000000000040000 to the doubleword at 0xc000000001594968, which holds 0xc000000000496af3: 0x456af3 bytes, exactly the file size of the read-only, executable program segment (text and the first `.rodata`). The writable segment starts at 0xc000000001496af8 and is not copied. IP27: from 0xc000000000019000 (the word at 0xc0000000014cc0d8) to 0xc00000000040382b (the word at 0xc0000000014cc0c0): 0x3ea82b bytes, again the first segment. `copy_kernel` ends in a `bcopy` (IP35 call at 0xc000000000074df0; IP27 0xc00000000005009c). The destination is the cached window (0xa800000000000000) address of the master's copy with the node field replaced by the target node: the field is cleared with a constant mask and the target NASID shifted left 33 (IP35, `dsll32 ...,1`) or 32 (IP27, `dsll32 ...,0` at 0xc000000000050064) is ORed in. Established. The 6.5.30 text above grades the IP27 shift as inferred; in 6.5.22 it is read directly at IP27 `copy_kernel`, `set_ktext_source` (0xc0000000000500c4) and `setup_replication_mask` (0xc00000000004febc).

Record. `set_ktext_source` stores a pointer to a record at node-local offset 0x21d0 (through the uncached window 0x96...) and fills it: the word 0x5f4b565f at +0, the text-source NASID as a halfword at +4, the master NASID at +6, the text-source base at +8 and the master base at +16. IP35 puts the record at offset 0x8578 of the node's private data; IP27 at 0x4938. Established for the stores; field meanings inferred as in the 6.5.30 text.

Mapping. `bootstrap` (IP35 0xc000000000065778; IP27 0xc000000000042ed8) reads the processor's own NASID from the word at 0x9200000001600000 (IP35 bits 39..32; IP27 bits 16..8), loads the record pointer from node-local 0x21d0 through the cached window, loads the halfwords at +4 and +6 and calls `mapped_kernel_setup_tlb`. The master processor calls it from `start` (IP35 0xc000000000041928; IP27 0xc00000000001a568) with its own NASID twice, so the master runs from its original load. The routine writes PageMask 0x1ffe000 (16 MB), EntryHi 0xc000000000000000, Index 1, EntryLo0 from the text-source node (flags 0x2b: global, valid, cache attribute 5, not writable), EntryLo1 from the master node (same flags plus dirty), then `tlbwi`. After the jump to the mapped address `bootstrap` sets PageMask 0x6000 and Wired 7 (IP35 0xc000000000065824; IP27 0xc000000000042f84), so Index 1 is inside the wired range. The text page pair and the writable page pair are physically separate: data is not replicated. Established. These are the only two callers of `mapped_kernel_setup_tlb` in either kernel.

Default. `numa_kernel_replication_ratio` is 1 in the linked kernel (the two addresses in the table), in the `master.c` initializer (`var/sysgen.IP35/master.c` line 3589; `var/sysgen.IP27/master.c` line 3324: `0x1`) and in `mtune/numa` line 198 (identical in both trees). No tuning file sets it. The `mtune` comment says there is always a copy on the master node and on every nth other node, and that 0 means do not replicate. The heading over the replication group in that file says "No effect on any systems, reserved for future"; as in 6.5.30 it is stale for this tunable. Established.

The first instruction of `repl_interpose` loads `numa_page_replication_enable`; when it is 0 the routine returns before it attaches anything to the executable's file. Nothing else in either kernel reads the word (global-pointer and address-formation scans) and nothing writes it; neither it nor `numa_repl_control_enabled` appears in `master.c` or `mtune`. When it is nonzero and the node count is not 1, `repl_interpose` calls `panic` with the string "repl behavior doesn't work" (the body of `panic` hands over to `icmn_err_tag`; what that does next was not followed). `nodepda_numa_init` (IP35 call 0xc0000000002ee348; IP27 0xc000000000277220) calls `repl_control_init`, which copies `numa_repl_control_enabled` and the traffic threshold into a per-node record; `repl_control` returns its node argument at once while the enabled byte is 0. So the call chain from exec mapping to `page_replica_insert` is linked and wired, and it is off. Established for the code, the callers and the values; unknown for what a debugger-set nonzero value would do.

Migration. IP35 has no automatic engine in 6.5.22, the same absent set as in 6.5.30 ([page-migration.md](page-migration.md#6522-for-comparison)); it keeps migration on request (for example `migr_xface_migrate`, 0xc0000000002f67e4). IP27 has the engine: `hub_migrintr_init` (0xc0000000000398c8, called from `per_hub_init` at 0xc000000000026b8c) connects level 3 to `migr_intr_handler` (0xc00000000026b4a8), which calls `migr_manager` (0xc00000000027fdb8, call at 0xc00000000026b630); `mem_tick` (0xc00000000027a048) is the clock-driven part. Established. The default mode word `numa_migr_default_mode` is 2 on both (IP35 0xc0000000015927f4; IP27 0xc0000000014c966c; `mtune/numa` line "numa_migr_default_mode 2"). In IP27 `migr_control_init` (0xc000000000281db4, 3176 bytes; mode dispatch from 0xc000000000281e38) mode 2 sets the control nibble to 0x30, mode 3 to 0x20, mode 1 to 0x10, mode 0 clears it, and mode 4 chooses 0x30 or 0x20 by `physmem_maxradius` (the IP35 routine makes the same choices). The `mtune` comment names mode 2 "use default migr policy (OFF), users can override" and mode 3 "(ON)". Inferred: the default policy is off and a user must ask for it; the code that reads the nibble per page was not decoded. Whether migration can pick executable file pages is not settled: `migr_check_migratable` (IP27 0xc00000000027cff0, 280 bytes) tests a hold count, two reverse-map scans and a page-flag mask 0x1000002 and does not look at what the page maps. Unknown.

### Node numbering and alias size (6.5.22)

Node tables. `nasid_to_compact_node`, `compact_to_nasid_node` and `cpuid_to_compact_node` are one block of 16-bit arrays (IP35 0xc00000000159ce00, +0x100, +0x200; IP27 0xc0000000014d3600, 0xc0000000014d3800, 0xc0000000014d3880). A forward scan that follows every register loaded from a pointer slot or formed by address arithmetic into the block, over every routine including those with no symbol-table entry, finds halfword stores through them in only two routines on each kernel: `cpu_node_probe` (IP35 0xc000000000046240, 768 bytes; IP27 0xc00000000001f0c8, 556 bytes) and `do_cpumask` (IP35 0xc000000000046540; IP27 0xc00000000001f2f4). `do_cpumask` is called only from `cpu_node_probe` (IP35 0xc00000000004634c); `cpu_node_probe` is called only from `mlreset` (IP35 0xc00000000004e42c; IP27 0xc000000000026080). Direct address uses elsewhere (`set_ktext_source`, `ecc_display`, `ecc_handler`) only load. The scan follows straight-line code and drops its state at calls, so an indirect store is not excluded. Established for the two writers; inferred that there are no others.

Hot-plug. No routine in either symbol table or debug-information list is named for hot-plug, node removal, online or offline. `part_add_regions` is an 8-byte stub (IP35 0xc0000000004433ec; IP27 0xc0000000003c2b7c). `ip27log_xbox_nasid_set` (IP27 0xc00000000003cca8, 76 bytes) formats a number and stores it in a PROM environment variable named `XboxNasid` through `ip27log_setenv`; it does not touch the tables. `cpu_restrict` and `cpu_unrestrict` are scheduler routines by name (bodies not read). Established for the names and the two bodies; inferred for the rest.

Node-number register. The processor reads its NASID in `get_nasid` (IP35 0xc000000000041204; IP27 0xc00000000001d434), `start` and `bootstrap`, all loads from 0x9200000001600000. No store through the pointer slot for that address (IP35 slot 0xc00000000159a0c0, 3 loading routines; IP27 slot 0xc0000000014caec8, 7 loading routines) exists. Established for the reads; inferred for "never written".

Alias size. `mlreset` (IP35 0xc00000000004e270, 1204 bytes; IP27 0xc000000000025eb0, 1020 bytes) stores the value 2 at offset 0x28 of each node's hub window: IP35 store at 0xc00000000004e5c0 (the `movn` pair at 0xc00000000004e590 picks 0x28 or 0x200028, so both processor-interface blocks), IP27 store at 0xc000000000026140. It also stores a kernel variable at offset 0x18 (and 0x200018 on IP35) and zero at +0x190 of a second window. The loop sits after a check that the running node is the master (IP35 0xc00000000004e53c). `mlreset` is called from `cboot` (IP35 0xc000000000066864; IP27 0xc000000000044090) and `mlsetup` (IP35 0xc000000000264bc8; IP27 0xc0000000001eddfc), `mlsetup` from `start` (IP35 0xc000000000041ad0; IP27 0xc00000000001a710). A forward scan of every routine for stores through the local hub window slot (IP35 gp+264; IP27 gp-24672) found 16 (IP35) and 21 (IP27) routines storing to other registers (interrupt, error, timer, block-transfer); the only routine with a 0x28 or 0x200028 offset is `mlreset`. The alias-size consumer slot (IP35 gp+416, IP27 gp-24432, both 0x9200000001000028) has no stores. Established for the `mlreset` stores; inferred for "no other writer".

### Run-time rewriting of kernel text (6.5.22)

1. The copy in `replicate_kernel_text` above, once per boot, from `allowboot`, which `main` calls (IP35 call 0xc0000000002a41c8). Established.
2. `_hook_exceptions` (IP35 0xc00000000006df0c, 836 bytes; IP27 0xc00000000004c35c, 852 bytes), called from `cboot` (IP35 0xc00000000006686c; IP27 0xc000000000044098) and `initmasterpda` (IP35 0xc000000000256368; IP27 0xc0000000001e066c), copies code templates word by word into the per-node vector area through the uncached window (`lui 0xa000`). It writes vector memory, not the image. Established.
3. IP27 only: `sw_cachesynch_patch` (0xc00000000004c6b0, 108 bytes; called from `initmasterpda` at 0xc0000000001e0540) reads the PRId register (`get_cpu_irr`, `mfc0 $15`), and only if bits 15..8 equal 4 overwrites three instruction words in `cache_sync`: 0xc00000000002bb28, 0xc00000000002bb2c and 0xc00000000002bb70 receive the words at 0xc00000000002baa4 +0, +4 and +8 (0x677bfff0, 0x309a000f, 0x675a0010), by plain stores through the mapped kernel addresses. Established for the code and the table. The usual MIPS numbering (4 for the R4000; 9, 14 and 15 for the R10000, R12000 and R14000; recalled, not checked against a manual here) says the patch does not run on an Origin processor. Inferred. IP35 has no such routine. This is a second patching site that the runtime-patching section of [kernel-tracing-and-modules.md](kernel-tracing-and-modules.md#runtime-code-patching) does not list for 6.5.30; the same routine is in `6.5.30/unix.IP27` at 0xc00000000004d050 with the same body.
4. User code only: `install_bp` (IP35 0xc00000000021d99c, 328 bytes; IP27 0xc0000000001a7704) fetches the next instruction of a traced process with `fuword` and places a breakpoint there for single stepping; it does not address kernel text. Inferred from the body.
5. Migration. Page-moving routines are driven by a process address space or a page list (`migr_user_range_migrate`, `migr_vas_pages`, `migr_coald_move_pages`), and the mapped kernel region at 0xc000... is not a process mapping. Inferred that kernel text is not moved. The wired entry gives the text a fixed physical home per node. `utlbmiss_patched` and `need_utlbmiss_patch` (IP35 0xc00000000159beac, 0xc00000000159bea8; IP27 0xc0000000014d26bc, 0xc0000000014d26b8) are 0 in the image.

No other routine that stores into the executable segment was found, but the search was by name and by the patch table, not an exhaustive tracking of every store. Inferred.

## IRIX 6.5.23

Not held. `root/` has `6.5.22` and `6.5.30` (with `unix.IP27`, `unix.IP30` and `unix.IP35` each) and three add-on trees (`divodvc-2.4-6.5.11m`, `dmediapro-dm2-1.1.3ml`, `vl-6.5.30m`); [binaries.tsv](inventory/binaries.tsv) and [functions.tsv](inventory/functions.tsv) list the same releases and nothing named 6.5.23. No 6.5.23 kernel was read, so none of the four answers is established for it. One related fact is recorded elsewhere from kernel object archives read off the installation discs when those were available: 6.5.23 removed the page-replication objects and compile switches from both platforms ([page-migration.md](page-migration.md#what-6523-removed-for-replication)). That makes the 6.5.30 answer to question 2 the likely 6.5.23 answer (inferred); the kernel-text copy, node tables, alias size and run-time patching in 6.5.23 are unknown. Route: a 6.5.23 installation set or its linked kernels.
