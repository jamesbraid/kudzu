# Network addressing and filtering; XVM and XFS copy-on-write primitives

Two questions about the 6.5.30 kernel, asked for a plan that wants containers and a copy-on-write image store: what the IPv4 stack offers for several addresses per interface, per-process source binding and packet filtering, and what XVM and XFS offer for snapshots, clones and project accounting. The IP35 kernel is read first. IP27 is noted where it differs.

## Evidence and method

Linked kernels: `6.5.30/unix.IP35` and `6.5.30/unix.IP27`. Kernel objects: `6.5.30/usr/cpu/sysgen/IP35boot/` (`xvm.a`, `xfs.a`, `xfsquotas.a`, `ipfilter.o`, `snif.a`). Object-relative addresses are offsets into the member's `.text`; the linked kernel's addresses are virtual.

Routines were read from the symbol table and disassembly; the `syssgi` selector rows are from [selectors.tsv](inventory/selectors.tsv) and the case code at the cited address. Public names for selectors and ioctl codes are hints from published headers and manuals, not read from the binary.

IP27 compared with IP35: for `in_control`, `in_pcbbind`, `in_pcbsetaddrx`, `arprequest`, `sfmatch`, `snoop_match`, `snoop_input2`, `ifa_ifwithaddr`, `ip_ctloutput`, `xfs_swapext`, `xfs_swap_extents`, `xfs_fsoperations`, `xfs_mk_sharedro` and `xfs_clear_sharedro` the instruction text is equal once call targets, branch targets and gp displacements are masked (`in_control` differs in eight instructions, all the gp displacement of the address-count words, and `arprequest` in the gp displacement of one `daddiu`). Nothing below differs on IP27 unless stated. Established.

The user-space tools that drive these interfaces (`ifconfig`, the XVM and XFS administration commands, `xfs_fsr`, `ipfilterd`, `quota` tools) are not in `root/` (`ipfilterd` is on the Overlays 1 disc in `eoe.sw.ipgate`; the XVM tools are in `eoe.sw.xvm`); the only XFS programs held are `6.5.30/usr/sbin/xfs_db` and `6.5.30/usr/sbin/xfs_repair`. Every statement about those commands is therefore unknown or a hint.

## Network

### Several addresses on one interface

`in_control` (`6.5.30/unix.IP35`, 0xc0000000001b4fcc, 3452 bytes) is the IPv4 interface-ioctl handler (`ifioctl`, 0xc0000000001b2ac0, reaches it indirectly through the socket protocol's control entry; `udp_usrreq` and `tcp_usrreq` call it directly). Its request codes are the BSD interface codes in group `'i'`: it compares against at least 0x8020690e, 0x80206918, 0xc020690f, 0xc0206917 (32-byte argument) and 0x80446922, 0xc0446921, 0xc0446923 (68-byte argument), among others (the compare tree also tests codes such as 0x...690c, 0x...690d, 0x...6919 and 0x...691a, for example at 0xc0000000001b5138, 0xc0000000001b5318, 0xc0000000001b5534 and 0xc0000000001b5268; see the open questions). The 68-byte codes are the alias requests (the argument carries an interface-name block plus address-sized blocks, described below). Established that the codes are tested; the names are inferred from the BSD codes.

Multiple IPv4 addresses per interface are supported. The per-address records come from `in_inifaddr_alloc` (0xc0000000001b479c, 128 bytes, called from four sites in `in_control`), are inserted into a global address hash with `hash_insert`, and are counted by `in_ifaddr_count` (0xc000000001646d34). One of the 68-byte requests enumerates: it keeps an index at +64 of the argument, advances it with `hash_enum_getnext` over the address hash filtered by the interface, and copies three 16-byte blocks out for the n-th entry, to argument offsets +16, +32 and +48 (code at 0xc0000000001b5b30 to 0xc0000000001b5bd0); the index is at +64, which gives the 68 bytes. The first block comes through the pointer at +0x28 of the address record and the second through the pointer at +0x30; the third is read from record +0xa4 to +0xb0. No fourth block is copied in this path, so no broadcast address is returned here. Established for the copies; that the blocks are the address, the destination and the mask, in that order, is inferred from the request being an alias enumeration; no field name was read.

The mutating interface requests need `cap_able` with bit 1 << 36 (`addiu a0,zero,1; dsll32 a0,a0,4`): `in_control` has six such calls, at 0xc0000000001b502c, 0xc0000000001b5118, 0xc0000000001b5274, 0xc0000000001b5330, 0xc0000000001b53cc and 0xc0000000001b54ac. Established for the six sites; which request code reaches which site (that one of them is the add) is inferred, as the sites were not each mapped to a code.

`arprequest` (`6.5.30/unix.IP35`, 0xc0000000001b82fc, 336 bytes) reads the tunable `arpreq_alias` (0xc00000000163c078, default 0, range 0 to 1). The 6.5.22 tunable file `root/6.5.22/var/sysgen.IP35/mtune/bsd` (the nearest shipped configuration; no 6.5.30 `var/sysgen` is held) describes it: when set, an ARP request uses an alias address on the target network as its source instead of the primary address. The code walks the address hash with `hash_enum` and passes the chosen record's address to `send_arp`. Established for the code shape; the description is the file's own comment.

Unknown: how `ifconfig` spells alias commands, and whether more than one alias per network is allowed. Settling route: the `ifconfig` binary, not held.

### Binding a process to a source address

`in_pcbbind` (`6.5.30/unix.IP35`, 0xc0000000001cac94, 644 bytes) is the `bind` path for TCP and UDP sockets. For a nonzero local address that is not multicast it copies the 16-byte socket address and calls `ifa_ifwithaddr` (0xc0000000001b1cac, 256 bytes, two `hash_lookup` calls over the address hash); a miss returns 126 (the can't-assign-requested-address error of the published error list, a hint). A multicast or zero address skips that check. A port below 1024 needs `cap_able` with bit 1 << 31 (`ori a0,zero,0x8000; dsll a0,a0,16` at 0xc0000000001cadfc), else it returns 13. The address is stored with `set_inp_laddr`. Port allocation is `in_pcbportassign` (0xc0000000001cb344, 908 bytes). Established.

`in_pcbsetaddrx` (0xc0000000001cbc6c, 1040 bytes), reached from `in_pcbconnect` (0xc0000000001cb6d0, 104 bytes), picks the local address for an unbound socket at connect time: it routes the destination with `rtalloc` and then chooses an interface address with `ifa_ifwithdstaddr`, `ifa_ifwithnet` and `ifatoia`. So an unbound outgoing socket takes the address of the interface the route leaves from, unless the process bound a source address first. Established for the call sequence; inferred for the stated effect.

This is per socket, set by the process that calls `bind` before `connect`. Nothing in the symbol table gives a per-process or per-credential source-address setting, and no socket option that pins the outgoing interface for unicast was found: `ip_ctloutput` (0xc0000000001a3b78, 1244 bytes) passes options to `ip_pcbopts` (IP options), `ip_setmoptions` and `ip_getmoptions` (multicast interface, TTL, loopback and membership) and to `m_get`/`ovbcopy` paths. Inferred from the callees; the option numbers were not decoded. Unknown: whether any option selects the outgoing interface for unicast. Settling route: decode the compare tree of `ip_ctloutput` and `sosetopt` (0xc0000000001b0584) against the published socket-option list.

Different processes bound to different aliases coexist; the connection tables are keyed by local address and port (`in_pcblookupx`, 0xc0000000001cd0fc). Inferred.

### Packet filtering

There are two separate mechanisms.

**IP filter** (`ipfilter.o`, configured by the `ipfilter` module). The linked 6.5.30 IP35 kernel was built with the stub: `ipfilter_kernel` (`6.5.30/unix.IP35`, 0xc000000000083e88, 8 bytes) is `jr ra` with 0 in the delay slot, there is no `ipfilterioctl` in its symbol table, and `ipf_process` (0xc000000001646c10) is an empty word. The real module is `6.5.30/usr/cpu/sysgen/IP35boot/ipfilter.o`, part of the optional subsystem `eoe.sw.ipgate` (the IP network gateway support) together with the `ipfilterd` daemon on the same installation disc; the 6.5.30 IP35 `irix.sm` names it on `USE: ipfilter` (line 435), and the stub is the one-line block in `master.d/ipfilter`, there being no separate stubs archive. The kernel is not linked with the module because the subsystem was not installed on the system it was linked on (inferred). The 6.5.22 module configuration (`root/6.5.22/var/sysgen.IP35/master.d/ipfilter`; no 6.5.30 equivalent is held) says it depends on `bsd` and is loaded when named in `system/irix.sm`; the stub is `ipfilter_kernel(){false}`. Established for the kernel and for the 6.5.22 files; that 6.5.30 configures it the same way is inferred.

The only call of `ipfilter_kernel` is in the IPv4 input path, at 0xc0000000001bc998, inside `ip_input` (0xc0000000001bc79c, 2740 bytes, a name known from debug information; the symbol table alone places the call at `ip_check_broadcast+0x270`). After the header checksum it tests that the version nibble is 4 and that the word at gp+0x35e0 (`ipfilterflag`, 0xc000000001646d50, a four-byte global defined in the `ip_input.o` of `bsd.a` and `socket.a` and only imported by `ipfilter.o`; no 6.5.22 configuration file names it) is nonzero, then calls `ipfilter_kernel` with the interface and the mbuf, and with `ipf_process` loaded from gp+0x34a0 into the eighth argument register just before the call; a result of 2 jumps to 0xc0000000001bc808, which is the drop path. Established. `ip_output` (0xc0000000001a2a54, 3664 bytes) and `ip_init` also use the pointer `ipf_process` (0xc000000001646c10, set to 0 in `ip_init`, tested at 0xc0000000001a2dd4 and 0xc0000000001a31e4) as an optional hook; no shipped object other than `ip_input.o` and `ip_output.o` (in `bsd.a` and `socket.a`) names it, so on the shipped objects it is never set. Established for an undefined-and-defined symbol scan of the symbol tables of every archive and object in `6.5.30/usr/cpu/sysgen/IP35boot/`.

What the module matches (`ipfilter_kernel`, `ipfilter.o` offset 0x28, 1424 bytes). First, a packet whose source address equals an address configured on the host is accepted: the routine calls `hash_lookup` on the IPv4 interface-address hash with the match routine `ipfilter_kernel_match` (offset 0, 40 bytes), which compares the source with the address word of the interface-address record. Then a nonzero IP fragment offset is accepted, and if filtering is not active the answer comes from the tunable `ipfilterd_inactive_behavior` (default 1, range 0 to 1; the 6.5.22 `mtune/bsd` comment on that tunable says 1 rejects packets from foreign sources and 0 accepts everything). Otherwise it builds a key and searches the kernel verdict cache (`ipfiltercache`, 32 entries in the 6.5.22 module configuration): input interface, source address, destination address, protocol byte, and two 16-bit values, which are the source and destination ports for TCP (6) and UDP (17) and the type and code bytes for ICMP (1) and IGMP (2). A hit returns by the entry's verdict byte: kind 1 returns 1 (accept); kind 6 logs and returns 1; kind 4 returns 4; kind 7 logs and returns 4; kind 5 logs and drops (returns 2 after `m_freem`); any other kind drops. A miss goes on to a queue read by the daemon. Established for the key fields and the return values; inferred for what 4 means (the caller special-cases only 2).

Rule loading and queue service are the module's ioctl: `ipfilterioctl` (`ipfilter.o` offset 0x5b8, 1244 bytes) accepts one request code, 0xc0517a7f (`'z'` 127, 0x51-byte argument), under a `cap_able` check, copies the argument in and out and can sleep for queued packets with `psema`. The daemon that talks to it is named by the shipped files as `ipfilterd(1M)`; it is not held. Established for the ioctl shape; unknown for the rule-file syntax and the meaning of the argument fields. Settling route: the `ipfilterd` binary.

Not matched by this module as far as the key fields show: user, group, process, socket owner, or interface address other than by the source/destination fields. Inferred from the key list; not proven by exhaustive reading of the rule-table walk.

**Snoop filter** (the raw/snoop socket path, `snif.a` and the `bsd` module). `snoop_match` (`6.5.30/unix.IP35`, 0xc0000000001a5f04, 220 bytes) tests each active filter record against a packet with `sfmatch` (0xc0000000001a54b0, 80 bytes). `sfmatch` compares up to nine 32-bit words: for each word it ANDs the packet word with a mask word and compares the result with a value word (records are 76 bytes: nine mask words, nine value words, flags). The offset of the window is adjusted by the link-header length. So this filter matches any bits in a window of at most 36 bytes (the start is moved back by a byte at +0x32 of the filter object). `snoop_match` returns the first matching record; with the interface flag word's bit 0x4000 clear it also stores the record at +0x188 of the packet descriptor. Established. It selects packets for capture on a raw/snoop socket, not for dropping, and it knows nothing about IP fields.

IPsec hooks exist in the output path (`ip_output` calls `swipe_getopol`, `sw_output` and `sesmgr_ip_output`) and security-label options (`ip_sec_*`); their policy is not part of this page. Established that the calls exist; unknown what they do on a kernel without those packages.

### Virtual interfaces and per-process network context

Virtual interface types present: loopback (`loattach` 0xc0000000001c2368, `looutput`), the tunnel interface `gifattach` (0xc000000000495e9c, 8 bytes in this kernel: the stub, because the IPv6 and tunnel code is in the optional subsystem `eoe.sw.ipv6`, `USE: ipv6` at line 463 of the 6.5.30 IP35 `irix.sm`) with the tunable `ngif` (default 4, range 0 to 64) and `config_tunnel_enable`, plus the PPP and SLIP pseudo-drivers (`if_ppp`, `if_sl`). Aliases (above) are additional addresses on an existing interface, not extra interface objects. Established for the symbols; the stub status of `gifattach` is established (8 bytes); the tunnel code is in the `in_gif_*` routines of the kernel.

No per-process, per-credential or per-namespace network state was found. The kernel's symbol table has no jail, virtual-network, network-namespace or container symbols; `chroot` exists but changes the file-system root only (the tunable `allow_chroot_with_open_dirs` is the only related name). The interface list, address hash (`ifnet`, the hash used by `ifa_ifwithaddr`), routing tables (`rt_tables`) and protocol control-block lists are single global structures reached through gp slots. Inferred from absence and from the globals read; not proven by exhaustive reading of the socket layer. Unknown: whether the array-session or process-accounting records influence socket lookups. Settling route: read `in_pcbfusermatch` (0xc0000000001ce5e8, 1064 bytes) and its callers; its name suggests a user match, which was not followed.

## XVM

### The snapshot (copy-on-write) feature exists

`6.5.30/usr/cpu/sysgen/IP35boot/xvm.a` has two snapshot members, `xvm_snapshot.o` and `xvm_irix_snapshot.o`, plus snapshot code in `xvm_user.o` and `xvm_build.o` and the `xvm_snapshot_max` and `xvm_snapshot_blocks` globals in `xvm.o` (a tunable for the number of snapshot devices, `nbufavoiddev`, is documented in the 6.5.22 `mtune/kernel`: default 16, range 2 to 256). The XVM module is configured as `xvm` (depends on `xfs`) and is named in the 6.5.22 `system/irix.sm`; the older XLV module is configured next to it. Established.

The linked 6.5.30 IP35 kernel carries XVM only as stubs: its symbol table has `xvm_dev`, `xvm_boot_disk`, `xvm_get_subvolumes`, `xvm_icrash`, `xvm_label_boot`, `xvm_root_to_swap`, `xvm_sgi` and `xvm_prt_*` entries from the stub module and none of the real routines below. The routines below are in the object archive, so they are what a kernel configured with `xvm` has. Established.

The model, from the routines and their messages: a snapshot is a copy-on-write volume layered over a subvolume. The original data stays on the base volume. Before a write to a region of the base is allowed, the region's old data is copied into a repository, which is a file in an XFS filesystem on another XVM volume; the repository is found, opened and mounted by uuid (`/xvm/repositories/<uuid>/...` appears in the messages). A per-region bitmap records which regions have been copied; reads of the snapshot take the saved copy for copied regions and the base for the rest. Chains of snapshots over one base exist (`xvm_copy_rep2rep`). Established for the routines' existence, calls and strings; inferred for the stated reading as a whole, since the routines were read for callees and messages, not line by line.

### Routines (all `6.5.30/usr/cpu/sysgen/IP35boot/xvm.a`, object-relative)

`xvm_make_cow` (`xvm_snapshot.o`, 0xff8, 648 bytes): attaches copy-on-write state to a base subvolume; errors if the subvolume has no child element. Calls `xvm_init_cow` and `xvm_insert_ve`. Established.

`xvm_make_snapshot_vol` (`xvm_snapshot.o`, 0x1280, 1044 bytes): creates a snapshot volume element through `create_snapvol_ve`, names it with `xvm_gen_svname`, attaches it (`xvm_attach_ve`) and propagates it (`xvm_propagate`). `xvm_cow_iterate` (0x1acc, 700 bytes) walks the existing snapshots of a base and re-creates or propagates each. Established.

`xvm_copyonwrt` (`xvm_snapshot.o`, 0x29f0, 1828 bytes): the write interception. Under read/update locks it locates the region (`xvm_locate_region`), reserves space in the repository (`xvm_prealloc_repository` 0x41ac, 944 bytes, with `xvm_rep_resvsp`), copies old data (`xvm_copy_base2rep` 0x1ff8, 724 bytes, which reads the base with `xvm_rdwr` and writes the repository with `xvm_rdwr_repository`) and sets the region bit (`xvm_set_region_bit`, 0x1fac, 76 bytes). Established.

`xvm_open_repository` (0x4f60, 1608 bytes) and `xvm_mount_repository` (0x4d04, 364 bytes) open and mount the repository by uuid, building its path from `/xvm/repositories/%s/%s`; `xvm_build_regmap` (0x3890, 544 bytes) builds the region map from the repository file's block map (`xvm_get_bmap`). `xvm_delete_snapshot` (0x564, 1360 bytes) removes the snapshot element and the repository file and directory with `vn_remove`; `xvm_collapse_cow_commit` (0x440, 292 bytes) removes the repository mount point on collapse. Established.

Snapshot creation freezes the base filesystem: `xvm_fs_freeze` (`xvm_irix_snapshot.o`, 0xdb4, 208 bytes) calls the XFS freeze routine `xfs_fs_freeze` and `xvm_fs_thaw` (0xe84, 128 bytes) thaws it; the failure messages are "Can't freeze base volume" and "Can't unfreeze base volume". Established.

### How user space drives it

Device ioctl. `xvmioctl` (`xvm.o`, 0xc54, 624 bytes) hands requests on the API node to `xvm_api_ioctl` (`xvm.o`, 0x1934, 584 bytes), which takes a small request number and returns 6 until XVM initialisation has completed. Request 1 copies in a 16-byte block and calls `xvm_ioctl_config`; request 2 copies in 0x68 bytes and handles four failover sub-commands (1 to 4); requests 3 and 5 wait for or check cell initialisation; request 4 returns the status word; request 6 copies in 0x20 bytes (not read further); anything else returns 22. Established for the dispatch; the node path and the user-space structure names are unknown.

`xvm_ioctl_config` (`xvm_user.o`, 0x39cc, 740 bytes) is the configuration command dispatcher. The 16-byte block is: version halfword (+0, must be 24, except for the get-version command), command halfword (+2), status word (+4, written back), user pointer to the payload (+8). A wrong version leaves status 0xbe05001f; an out-of-range command (23 or more) leaves 0xbe070007 and returns 22. The command is the index of a table of 23 handlers; a kernel buffer of the handler's size is allocated, the payload copied in, the handler called, its result stored as the status word and the buffer copied out. Established. The command table, with the buffer size in bytes and whether a privilege check (`xvm_privleged_user`) runs first:

`xvm_cow` (`xvm_user.o`, 0x16e0, 588 bytes) is the snapshot command. It requires a zero halfword at payload +0 (else status 0xbe000003) and a byte at +0x7a equal to 2 or 3 (else 0xbe070031); with `xvm_snapshot_max` zero it also needs a nonzero word at payload +4 (else 0xbe0d0017). It finds the volume element by the id at payload +8 (`xvm_id2ve`), takes the update lock, and for each piece of the subvolume (the piece count is the halfword at +0x20 of the element) calls `xvm_cow_piece` (0x3ce8, 1552 bytes). It refuses with 0xbe0d0018 or 0xbe0d001c in other branches (the block total against `xvm_snapshot_blocks`, and an empty request) and stores a halfword result at payload +0xfc. `xvm_cow_piece` freezes the filesystem with `xvm_fs_freeze`, creates or removes the copy-on-write element with `xvm_make_cow`, `xvm_make_snapshot_vol`, `xvm_collapse_ve` or `xvm_delete_snapshot`, and thaws. Established for the call structure; the meaning of byte +0x7a (2 and 3 look like "make" and "collapse") is inferred.

`xvm_collapse` (`xvm_user.o`, 0xe2c, 156 bytes) and `xvm_delete` (0xec8, 268 bytes) test the element with `xvm_snapshot_check` before acting. Established.

Unknown: the names of the administration commands that issue these requests, their option syntax, and the on-disk label format of a snapshot element. The user-space XVM programs are not held; the published XVM administrator's guide was not consulted in this pass. Settling route: install media for the XVM user package, or the guide by document number.

### What the primitive offers for an image store

Block-level, volume-granular snapshots with a per-region copy-on-write bitmap and a file-backed repository, created under a filesystem freeze. Writes to the base trigger copies; the snapshot costs no space until the base changes. Established as a mechanism; inferred as a usable image store, because writability of snapshots is not shown: the string "Shouldn't be writing" in `xvm_snapshot.o` and the lack of a write path in the routines read suggest a snapshot is read-only. Unknown whether a snapshot can be written or cloned further. Settling route: read `xvm_snapshot_io` and `xvm_io` for the write case.

The limits that are visible: snapshots per base are bounded (message "too many snapshots for volume", global `xvm_snapshot_max`), the total snapshot block count is bounded by `xvm_snapshot_blocks`, and the repository must be an XFS file system on another XVM volume. Established.

## XFS

### Project identifiers and project quotas

A per-inode project identifier exists. The `xfs_db` program lists `projid` among the inode fields (`6.5.30/usr/sbin/xfs_db`, strings) and `pquotino` and `qflags` among the superblock fields; the kernel has `va_projid`, `di_projid` and `qi_pquotaip`. Established.

Setting it: `syssgi` selector 222 reaches `chproj` (`6.5.30/unix.IP35`, 0xc0000000002a9044, 172 bytes): it needs `cap_able` with bit 1 << 11 (0x800), copies in an 8-byte value from a user pointer, returns 79 if the value does not fit in 16 bits, and calls `namesetattr_audit_extended` on the path with the attribute mask 0x4000000 and the value. The call follows symlinks. Project ids are therefore 16-bit. Established. The selector's public name was not looked up.

The same field is exposed through the file control call: `xfs_fcntl` (`6.5.30/usr/cpu/sysgen/IP35boot/xfs.a(xfs_vnodeops.o)`, 0x81ec, 1500 bytes) dispatches the command minus 10 through a 47-entry table at `.rodata` 0xc8. Commands 31 and 45 call `xfs_getattr` and copy out a 28-byte extended-attribute record; command 32 copies in 28 bytes and calls `xfs_setattr` with the mask 0x4c00000, which contains the bit 0x4000000 that `chproj` also sets for the project field. The record's word at +12 is stored at +0xa0 of the attribute record (and read back from the same place), which is the field `chproj` writes, so it is the project id. The other two mask bits and the words at +0 and +4 are inferred to be the flags and the extent-size hint. Established for the project word; inferred for the rest. The names F_FSGETXATTR and F_FSSETXATTR for 31 and 32 are the public ones (hint).

The other fcntl commands in that table, by number: 10, 11, 36, 37, 40, 41, 42, 43 reach `xfs_change_file_space` (space allocate, free, reserve and unreserve, with 64-bit variants); 30 returns a 20-byte direct-I/O description; 38 and 44 call `xfs_getbmap` with a 32-byte request; 39 sets the data-management attributes (`xfs_set_dmattrs`); 46 and 47 set and get the buffered-I/O size (`xfs_set_uiosize`, `xfs_get_uiosize`); 51 goes to `xfs_dm_fcntl` or, when `cell_enabled` is set, `cxfs_dm_fcntl`; 56 calls `xfs_fcntl_getbmapx`. Established for the call targets; the public command names are hints.

The linked 6.5.30 IP35 kernel carries quotas as a stub: `xfs_quotactl` there (0xc000000000497634) is 28 bytes, and the XFS file-system operations table holds a pointer to it (at 0xc0000000015eaaf0). The real code is in the archive named next. Established.

Project quota control: `xfs_quotactl` (`6.5.30/usr/cpu/sysgen/IP35boot/xfsquotas.a(xfs_qm_syscalls.o)`, 0x0, 720 bytes) is the quota call. Its command is range-checked against 26 entries; the targets are quota on, quota off, get/set limits, get status, remove quota files and set warnings. The type passed to `xfs_qm_scall_getquota` and `xfs_qm_scall_setqlim` is 1, 2 or 4; the same object has the strings `UQUOTA`, `GQUOTA` and `PQUOTA`, so 1, 2 and 4 are user, project and group (read from the id widths in `xfs_qm_dqattach`, below). Quota on is refused for a filesystem with a real-time subvolume ("Cannot turn on quotas for realtime filesystem"). Established.

The superblock lists a user quota inode and a project quota inode (`uquotino`, `pquotino` in `xfs_db`); `xfs_repair` carries checks named for user, project and group inodes (`have_uquotino`, `have_pquotino`, `lost_gquotino`). The mount structure has only two quota inode numbers, at +0xe0 and +0xe8 (`xfs_qm_init_quotainos`, `6.5.30/usr/cpu/sysgen/IP35boot/xfsquotas.a(xfs_qm.o)`, 0x245c, 608 bytes: it calls `xfs_iget` on each and `xfs_qm_qino_alloc` for a missing one), and the quota information record names only `qi_uquotaip` and `qi_pquotaip`. Established.

Group and project quotas do not run together. `xfs_mountfs_int` (`6.5.30/usr/cpu/sysgen/IP35boot/xfs.a(xfs_mount.o)`, 0x884, 4112 bytes) compares two flag words of the mount structure: the halfword at +0xf0, the quota flags in force for this mount, and the word at +0x300, which holds the flags the superblock records (the test pairs in the next paragraph show the first as the requested side and the second as the on-disk side; inferred from the "requested" and "disk contains" wording and from their use in the quota-on routine). A mount that asks for group accounting (bit 0x8 of the first word) while the disk records project accounting (bit 0x40 of the second), or the reverse (checks at 0x978 to 0x990 and 0xd90 to 0xdb8; which of the two names the message prints first fixes group as 0x8 and project as 0x40 in these words), prints "XFS: Filesystem mount requested with %s quotas, but disk contains %s quotas." (the two names are `group` and `project`) and "XFS: If this is what was intended, turn off the %s accounting first and then re-mount", and fails with error 89 (error exit at 0x1830 to 0x1874). `xfs_qm_dqattach` (`xfs_qm.o`, 0xfcc, 400 bytes) attaches to an inode a user dquot and then at most one other: when the mount's active-flags word (+0x300) has bit 0x200 it is a type 2 dquot keyed by the halfword at +0x28c of the inode (the project id, the same field `xfs_create_new` uses below); otherwise, when bit 0x400 is set, a type 4 dquot keyed by the word at +0x284 (16-bit versus 32-bit ids make these project and group). If both active bits were set the project dquot wins and no group dquot is attached. Established. This also fixes the type numbers of the quota call: 1 user, 2 project, 4 group (the earlier reading of 2 as group was inferred from the strings and is withdrawn; the other readers of the type were not rechecked).

The quota-on routine `xfs_qm_scall_quotaon` (`xfs_qm_syscalls.o`, 0x7b8, 656 bytes) is read in full. In it the halfword at +0xf0 of the mount is the flags in force and the word at +0x300 the flags the superblock records plus the active bits 0x100 (user), 0x200 (project) and 0x400 (group), which sit above the accounting bits. It needs `cap_able` with bit 1 << 30 (error 1 otherwise). It masks the request with 0x5b: user accounting 0x1, user enforcement 0x2, group accounting 0x8, enforcement for the shared group/project slot 0x10, project accounting 0x40 (meanings from the mount messages and the checks). On a device other than the root device it clears the accounting bits (0x49), so only enforcement can be switched on after mount; on the root device it clears them only when every requested accounting bit is already active. It returns 22 for an empty request, or for an enforcement bit whose accounting is neither recorded in the superblock nor requested; 17 when every requested bit is already active; otherwise it sets the quota bit 0x40 in the superblock version word (+0xa4; when the low nibble of that word is not 4 it first rewrites the word as version 4 and resets both quota inode numbers to -1 and the superblock quota flags to 0), ORs the new flags into the superblock flags and the mount's active flags under the quota lock, and writes the superblock with `xfs_qm_write_sb_changes`. It has no test that rejects a request holding both 0x8 and 0x40, so the exclusion comes from the mount check and the single shared slot. What a running system keeps when a request names both was not followed. Unknown.

Project id of a new file: `xfs_create_new` (`6.5.30/usr/cpu/sysgen/IP35boot/xfs.a(xfs_vnodeops.o)`, 0x2c78, 4328 bytes) takes the id from the create request when the request's attribute mask carries the project bit 0x4000000 (the bit `chproj` also sets; test at 0x2db4 to 0x2dbc), otherwise from the global default `dfltprid` (halfword, load at 0x30d8). It then tests bit 0x200 of a halfword of the parent directory's inode flags (0x2dc8 to 0x2dd0) and, when it is set, replaces the id with the parent's project id (halfword at +0x28c of the inode record, 0x2dd8). Established. So a directory can force its project id onto new entries; calling that flag "project inherit" is inferred from the effect. Which call sets the flag on a directory (probably the extended-attribute set of the fcntl call above) was not read. Unknown.

### Extent sharing and clones

Nothing in the 6.5.30 XFS shares extents between files. The kernel and `xfs.a` have no reflink, extent-reference-count, reverse-mapping or dedup symbol or string; the only `refcount` hits are buffer-item and generic reference fields. The superblock feature words printed by `xfs_db` (strings: attributes, nlink, quota, alignment, data alignment, shared, directory v2, log v2, extent flags, attr2, parent, lazy superblock counters, more-bits) have no reference-count or sharing-of-blocks bit. The one feature named "shared" is the shared-read-only mount state below, which is a cluster mount mode and not block sharing. Established as absence from the shipped strings and symbol tables; inferred for "no such feature", since a feature could exist without a string.

`xfs_swapext` (`6.5.30/usr/cpu/sysgen/IP35boot/xfs.a(xfs_dfrag.o)`, 0x0, 532 bytes), reached by `syssgi` selector 229 (case at 0xc0000000002e2114): copies in a 0xa8-byte request, resolves two open file descriptors with `getf`, checks they are on the same filesystem and compatible, and calls `xfs_swap_extents` (0x214, 1836 bytes). That routine locks both inodes (`xfs_lock_inodes`), checks the caller owns or has capability (`xfs_iaccess`, `cap_able_cred`, `mac_xfs_iaccess`), counts blocks with `xfs_bmap_count_blocks`, and swaps the two inodes' extent maps inside one transaction. Established for the structure. It exchanges the data of two files atomically (this is what a file defragmenter needs); it creates no sharing. Using it to publish a prepared file in place of another is possible; whether it checks modification times of the target is inferred from the 0xa8-byte request size and not read.

`xfs_mk_sharedro` and `xfs_clear_sharedro` (`xfs_utils.o`, 0xad8 and 0xb4c, 116 bytes each), reached by `syssgi` selectors 363 and 364, find the mount from a descriptor, require a mount whose device major field equals 0xc0, set or clear a byte at +0x38c of the mount record and log "Filesystem \"%s\" will [not] be marked shared read-only on unmount". This marks a filesystem so that it is written as shared read-only at unmount, which is the superblock's "shared" feature bit. Established; its use (a cluster read-only sharing mode) is inferred.

Filesystem freeze: `xfs_fsoperations` (`xfs.a(xfs_fsops.o)`, 0x12f0, 800 bytes), reached by `syssgi` selector 153, dispatches 13 operations through a table at `.rodata` 0x88: geometry queries (cases 0, 7, 8, 12), grow data (1), grow log (2), grow real-time (3), free-block counts (4), get and set the reserved block pool (6, 5), shut down (9), freeze (10, `xfs_fs_freeze` 0xfc0, 348 bytes) and thaw (11, `xfs_fs_thaw` 0x111c, 48 bytes). A mount with bit 0x10 in the word at +0x2e4 of the mount record returns 5 for every operation. Established. This is the same freeze `xvm_fs_freeze` calls.

Bulk inode listing for backup tools is `xfs_bulkstat` (`6.5.30/unix.IP35`, 0xc0000000003a9a04, 2976 bytes) behind `xfs_itable` (0xc0000000003aac18, 444 bytes), selectors 142 and 143. Established.

### A copy-on-write image store on this kernel

Block layer: XVM snapshot gives point-in-time block copies of a volume, created under a freeze, with a repository on another volume. Whole-volume granularity; no cloning of individual files.

File layer: XFS offers no reflink or per-file clone. The tools are a plain copy, `xfs_swapext` for atomic replacement of one file's extents by another's, space preallocation (`F_RESVSP` family) and extent-size hints (the same attribute record), and project quotas to account usage per directory tree.

Inferred shape for an image store: one XFS volume per image set, snapshots of the volume for point-in-time copies, project ids to account space per image tree, and swapext to replace a finished copy. Whether a snapshot volume can be mounted writable and used as a clone is unknown (above).
