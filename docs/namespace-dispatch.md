# Namespace dispatch: pointer tables and where the code lives

For the three kernel states that [process-model.md](process-model.md#namespace-scope) found to be global (the mount list, the host name, the System V IPC keys), this page answers two questions per behaviour. A: is the code reached through a table of function pointers that other code could extend, or through a hard call? B: does the routine that would be replaced live in the always-linked core object, or in a member of an archive (or a stand-alone optional object) that an explicitly linked object could supply in its place?

It does not say how to change kernel memory while the kernel runs. It only says what the shipped link inputs and the linked kernel show about dispatch and symbol placement.

All addresses are `6.5.30/unix.IP35` unless said. Grades: **established** (read in the binary or in a shipped file, with the address), **inferred** (reasoned, reasoning given), **unknown** (with the route that would settle it). 6.5.22 is covered at the end.

## How core and archive were told apart

- The link inputs are the 353 files of `6.5.30/usr/cpu/sysgen/IP35boot/`: 181 objects, 170 archives and two headers. `nm` over every object and every archive member gave a map from each global symbol to its defining member (22,140 definitions). `readelf -r` and `nm -u` over the same files gave which members reference which symbols. Read directly.
- A member counts as linked into the kernel when its functions are in `unix.IP35` at the same size. Every member named below matches in full (for example 12 of 12 functions of the archive member that holds `uname`, 4 of 4 of the one that holds `lookuppn`, 5 of 5 of `ipc.o`, 42 of 42 of `sem.o`). Read directly.
- The one mandatory core object is `kernel.o`: its configuration file (`6.5.22/var/sysgen.IP35/master.d/kernel`) carries the flag `k` ("only one such object can be configured into a kernel", `master.d/README`) and `system/irix.sm` names it on its `KERNEL:` line. It defines 1,177 global text symbols, 1,076 of them with a recorded size. None of the routines asked about is in it; it only calls into them (it references `vhost_local` and `sysent`). Read directly. The 6.5.22 configuration files are used because no 6.5.30 copy is held (the same limit as in [module-interfaces.md](module-interfaces.md)).
- `os.a` is a required module (`master.d/os` flags `oxr`; `INCLUDE: ... os ...` in `irix.sm`). All of the targets except the System V semaphore and message code are members of it. Of its 146 members that define globals, 145 have at least one of them in the kernel; the one that does not (`ktrace.o`, one function) is referenced by no boot object. Every `os.a` member that is in the kernel is referenced by some other boot object. That is what archive-member selection by unresolved reference looks like, and it is not what a link of the whole archive looks like. Reasoned: the order, flags and duplicate-symbol policy that `lboot` gives the linker are not held (`lboot` is not in `root/`), so whether a same-named symbol in a boot object wins, clashes or is ignored was unknown from the files alone. **Resolved by observation** (not read from a binary in this repository): a booted-kernel `lboot` link-order spike showed that a duplicate definition is a warning, the link exits 0 and the first definition wins, so an added boot object's symbol overrides the archive member's, confirmed by an overriding of a real archive symbol on a booted kernel. A boot object can therefore supply single symbols and need not replace a whole member. The remaining caveat is reasoned, not tested: a call from one routine to another inside the same member may bind within the member and not see the override, so check for intra-member callers of any symbol replaced.
- The vendor's own build already swaps same-named code by configuration. A stubs archive (flag `u`: "stub functions ... always loaded after all other modules", `master.d/README`; 72 `*stubs.a` in the directory) defines the same entry points as its real module, and `lboot` links one or the other; `noncell.a` is described in its master file as "local versions of routines having cellular counterparts", and `os.a` itself carries `_lp` ("local") members next to the layer above them. A module that is absent gets only the stubs its master file lists. Read directly for the files; that the swap is the supported way to replace a module is reasoned.

## 1. Host name and domain name

### A. Dispatch: a pointer table behind one record, but only for part of the name state

Established.

- `sethostname` (0xc000000000264ab8, 208 bytes) calls `vhost_local` (0xc0000000003154a8, 8 bytes), which returns the word `local_vhp` (0xc00000000163d610). It then loads the record's first behavior descriptor (word +0), that descriptor's operations pointer (+0x10), and calls through slot +0x28 (indirect call at 0xc000000000264b5c) with the descriptor itself, the kernel copy of the name and the address of a stack word holding the length. `gethostname` (0xc000000000264a34, 132 bytes) does the same through slot +0x30 (indirect call at 0xc000000000264a68).
- The table is `phost_ops` (0xc000000001599520, 136 bytes, initialised data in the writable `.data` section, defined in the `os.a` member for the host layer). Slots, from the linked kernel:

  | Slot | Routine | Slot | Routine |
  | --- | --- | --- | --- |
  | +0x00 | header word 0x0000010100000000 | +0x50 | `phost_reboot` |
  | +0x08 | `phost_register` (0xc000000000314eb4) | +0x58 | `phost_sync` |
  | +0x10 | `phost_deregister` (0xc000000000314ed0) | +0x60 | `phost_sysget` |
  | +0x18 | `phost_sethostid` | +0x68 | `phost_systune` |
  | +0x20 | `phost_gethostid` | +0x70 | `phost_sysacct` |
  | +0x28 | `phost_sethostname` (0xc000000000264d20) | +0x78 | `phost_set_time` |
  | +0x30 | `phost_gethostname` (0xc000000000264cec) | +0x80 | `phost_adj_time` |
  | +0x38 | `phost_setdomainname` | +0x40 | `phost_getdomainname` |
  | +0x48 | `phost_killall` | | |

- The record is built once. `vhost_init` (0xc0000000002de0a0) calls `vhost_cell_init` (0xc000000000315488), which stores the result of `vhost_create` (0xc0000000002de0bc) in `local_vhp`. `vhost_create` allocates a 32-byte head, initialises it as a behavior head and calls `phost_create` (0xc000000000314e68, 76 bytes). `phost_create` allocates a 32-byte behavior descriptor, stores the address of `phost_ops` at +0x10 (the address comes from a literal at 0xc0000000016420a8) and inserts it as the first behavior. Nothing selects another record by caller.
- `phost_register` and `phost_deregister` (the two slots that sound like a registration interface) only call `panic`. There is no call that takes a table or a pointer and installs it. So an object cannot add itself: it can only be the object that defines `phost_ops` (see B), or write into the table (a runtime store, outside this page).
- Callers of `vhost_local` are 16 call sites in `adjtime`, `bdflush_wake_proc`, `getdomainname`, `gethostid`, `gethostname`, `sethostid`, `sethostname`, `setdomainname`, `settime`, `sync`, `syssgi` (2) and `uadmin` (4). The table is the host-wide operations of the machine (time, sync, reboot, kill-all, system tuning), with the host name as two of its slots.
- **Not through the table:** `uname` (0xc000000000263ff0, 288 bytes) reads the five 257-byte members of the global `utsname` (0xc00000000158e638) directly and is reached by a direct call from `utssys` (at `utssys`+0xfc) and by a pointer in both syscall tables (`sysent`+0xec0, `irix5_64_sysent`+0xec0). `systeminfo` (0xc000000000264354) reads `hostname` and `utsname` through global-pointer slots and calls `vhost_local` nowhere; its set case calls `sethostname`. `inituname` (0xc000000000263f58) fills `utsname` and is referenced from the boot-time main routine. Other kernel code reads the globals directly: `utsname` is referenced by `nfs.a(nfs_subr.o)`, `os.a(acct.o)`, `os.a(main.o)` and `os.a(vmdump.o)`, and `hostname` by `lockd.o` and `oncrpc.a(kauth_unix.o)`.
- So the name has two readers' families: callers of `gethostname`, `sethostname`, `getdomainname`, `setdomainname` go through `phost_ops`; callers of `uname`, `systeminfo` and the kernel-internal users read the globals. A per-container name made only by replacing slots +0x28 to +0x40 would show in `gethostname` and not in `uname`, `systeminfo` or the NFS client.

### B. Where it lives

Established for placement, inferred for what replacing it takes.

| Symbol | Archive member | Linked | Referenced from other members |
| --- | --- | --- | --- |
| `phost_ops`, `phost_create`, `phost_register`, `phost_deregister`, `phost_killall`, `phost_reboot`, `phost_sync`, `phost_set_time`, `phost_adj_time` | `os.a` host-layer member | yes | only `phost_create` (from the member holding `vhost_create`); `phost_ops` by no other member |
| `vhost_init`, `vhost_create` | `os.a` member | yes | `vhost_init` from the main routine and the local-provider member |
| `local_vhp`, `vhost_local`, `vhost_cell_init`, `vhost_lp_init` | `os.a` local-provider member (`vhost_lp.o`) | yes | `vhost_local` from 8 members plus `kernel.o`; `vhost_lp_init` from the main routine |
| `uname`, `utsname`, `hostname`, `hostnamelen`, `inituname`, `systeminfo`, `sethostname`, `gethostname`, `setdomainname`, `getdomainname`, `phost_sethostname`, `phost_gethostname`, `phost_setdomainname`, `phost_getdomainname` (23 global entries, 5 of them absolute symbols) | `os.a(name.o)` | yes | `uname` from the syscall-table member and `utssys`; `utsname` from 4 members; `hostname` from 2 (`lockd.o`, `kauth_unix.o`); `inituname` from the main routine; the `phost_*name` routines from the host-layer member |
| `phost_gethostid`, `phost_sethostid` | `bsd.a(bsdinit.o)` (a second copy is in `socket.a`) | yes | slots +0x18, +0x20 |

- None is in `kernel.o`. All are in `os.a` (required module) or `bsd.a`.
- Placement of a replacement, reasoned under the standard archive rule: a boot object that defines `phost_create` and `phost_ops` (and the other six exports of the host-layer member) leaves that member unpulled, and its table can point slots +0x28 and +0x30 at the object's own routines. Only `phost_create` has an outside reference, so the surface to supply is small. Replacing `uname` and the globals means supplying the whole of `name.o` (18 real definitions, 13 referenced from other members), because `utsname` and `hostname` are data that other members use.
- The vendor's own bsd master file lists `gethostname`, `sethostname`, `getdomainname` and `setdomainname` as stubs ("not installed") for a kernel without `bsd`; these four are also defined in `name.o`. Why both exist was not followed: unknown.

## 2. Mount view

### A. Dispatch: a hard structure walk with per-file-system vectors at the ends

Established.

- Crossing a mount point: `lookuppn` (0xc0000000002c1698, 2,260 bytes) looks up each path component with one indirect call (at 0xc0000000002c184c) through the directory vnode's behavior chain (vnode word +0x60, its operations at +0x10). When the vnode's word at +0x28 is non-zero it calls `traverse` (0xc0000000002c1f6c, 376 bytes; direct call at 0xc0000000002c1894). `traverse` reads that word (a covering file-system record), takes `vfslock`, and calls the root operation through the record's own behavior chain (word +0x68, operations at +0x10, slot +0x30; indirect call at 0xc0000000002c2038). The choice of whether and what to cross is a field read; no per-process, per-root or per-file-system vector is consulted for it. The file-system vector is consulted only to obtain that file system's root vnode.
- Placing a mount: `mount` calls `cmount` (0xc000000000289eac), which resolves the path with `lookupname` (direct call at 0xc000000000289ee4) and calls the cover operation of the covered vnode through its behavior chain (slot +0x168 of the vnode operations; indirect call at 0xc000000000289f48). The default implementation of that slot is `fs_cover` (0xc000000000288ab4), which is the value in the vnode-operations tables of ten file-system types (the autofs, cachefs, efs, hwgfs, lofs, namefs, nfs, nfs3, udf and xfs members). `fs_cover` itself calls the file-system type's mount routine through the type's own vector (`vfssw` slot +8, per the earlier section) and `vfs_add` (direct), and stores the covering record in the vnode's word +0x28.
- So there is a per-file-system-type vector (vnode and vfs operations, 18 and 15 tables, see the general section) that a new file-system type fills, but the generic mount list (`rootvfs`, one list, `vfs_add`) and the crossing walk are not vectored. Mount point crossing is shared by all file systems and all processes.

### B. Where it lives

Established.

| Symbols | Archive member | Linked | Referenced from other members | Grade |
| --- | --- | --- | --- |---|
| `lookupname`, `lookuppn`, `traverse`, `lookup_init` | `os.a(lookup.o)` (4 functions, 4 of 4 linked) | yes | `lookupname` from about thirty members (file systems, loaders, NUMA and others); `lookuppn` from 4 (`exec.o`, `intp.o`, `vncalls.o`, `vnode.o`); `traverse` from `lofs.a(lofs_vnops.o)` and `snfs.a(nfs_server.o)` | established |
| `mount`, `cmount`, `vfs_add`, `vfs_remove`, `rootvfs` and 62 other global entries | `os.a(vfs.o)` | yes | `cmount` from `eag.a`; `vfs_add` from 5; `mount` from the syscall-table member; many of the rest from file-system members | established |
| `fs_cover` and 33 other global entries (`fs_nosys`, `fs_noerr`, `fs_dounmount`, ...) | `os.a(fs_subr.o)` | yes | `fs_cover` from the ten file-system members above; the others from nearly every file-system member | established |

- None is in `kernel.o`; all are in `os.a`, so the always-linked code is in an archive, not a stand-alone object. Read directly.
- Placement of a replacement, reasoned under the standard archive rule: the crossing walk is replaceable by supplying `lookup.o`'s four functions from another object (three are referenced from outside; `lookup_init` has no outside reference in the boot objects). That member is small. `vfs.o` (67 global entries) and `fs_subr.o` (34) are wide: they are the interface every file system links against, so replacing `fs_cover` or `cmount` as a whole member is not a small change. A per-container mount list therefore looks like a replacement of the crossing in `lookup.o` over the existing global cover words, not a replacement of mount placement.
- Another route needs no replacement and is reasoned only: a new file-system type, registered through the vector tables below, answers its own directory lookups through its own vnode operations and can return a different view by calling process. The existing `lofs` member shows the pattern (it calls `traverse` and `fs_cover`). Not tested.

## 3. System V IPC keys

### A. Dispatch: a direct scan of a global table; only the matched entry is vectored

Established.

- Shared memory: `shmsys` (0xc000000000317dd8, in the `os.a` member for the system call) function 3 runs the routine at 0xc000000000317a24, which calls `vshm_lookup_key` (0xc000000000316124, 464 bytes) directly. That routine scans `vshmtab` (0xc000000001646568, `vshmtabsz` entries), compares the word at +0x14 of each entry with the key (0xc0000000003161b4), then, for an entry that matches, calls the entry's key-check operation through its behavior chain (entry word +0x20, operations +0x10, slot +0x10; call at 0xc0000000003161e4). That slot is `pshm_keycheck` in `pshm_ops` (0xc000000001599600, 80 bytes; slots +8 `pshm_getmo`, +0x10 `pshm_keycheck`, +0x18 `pshm_attach`, +0x20 `pshm_setdtime`, +0x28 `pshm_rmid`, +0x30 `pshm_ipcset`, +0x38 `pshm_getstat`, +0x40 `pshm_mac_access`, +0x48 `pshm_destroy`). A second indirect call at 0xc000000000316298 is slot +0x40 (`pshm_mac_access`) on a newly created entry. Creation is a direct call to `vshm_create`.
- Semaphores: `vsem_lookup_key` (0xc0000000000e4074, 472 bytes) is the same shape over `vsemtab` (0xc000000001644eb8): key compare at +0x14 (0xc0000000000e4114), then slot +8 of the entry's operations (`psem_keycheck` in `psem_ops`, 0xc00000000155a5b0, 128 bytes; call at 0xc0000000000e4140). Direct call to `vsem_create`.
- Messages: `ipcget` (0xc0000000000e61dc, 660 bytes) walks `msgque` through two function pointers that its caller passes in as arguments (indirect calls at 0xc0000000000e6234, 0xc0000000000e625c, 0xc0000000000e6370, 0xc0000000000e639c); the caller `msgget` passes its own local routines, so the indirection is a parameter of one call, not a table that another object can extend. The key compare is in `ipcget`.
- So each facility has a per-object vector (`pshm_ops`, `psem_ops`) but the part that decides which object a key names, the scan of one global table, is not behind a vector in any of the three. A per-container key space needs the compare to include a container identity, so it needs the lookup routine itself replaced, not only an operations table.

### B. Where it lives

Established.

| `shmsys` and 5 other globals | `os.a(shm_syscalls.o)` | yes | `shmsys` from the syscall-table member | established |
| `pshm_ops` | `os.a(pshm.o)` | yes | from `vshm_mgr_lp.o` | established |
| `vsem_lookup_key`, `vsemtab`, `psem_ops`, `semsys` and 53 other globals | stand-alone `sem.o` (57 globals) | yes | **`semsys` only** among its code and data symbols, from the syscall-table member (`idbg.o` also names its absolute `mac_enabled` and `sat_enabled`, which about a hundred members define alike and which are not links into it) | established |
| `ipcget`, `msgque` and `msgsys` | stand-alone `msg.o` (20 globals), `ipcget` in stand-alone `ipc.o` (6 globals) | yes | `msgsys` from the syscall-table member and `uncintf.o`; `ipcget` from `msg.o` only; the other `ipc.o` symbols (`ipcaccess`, `ipc_init`, the two permission converters) from `msg.o`, `sem.o`, `pshm.o`, `shm_syscalls.o`, `xpmem.o` | established |

- None is in `kernel.o`. Shared memory is in the required archive; `sem.o`, `msg.o` and `ipc.o` are separate objects that `irix.sm` names on `USE:` lines and whose master files list stubs for the case that they are absent (`semsys`, `semexit`; `msgsys`; `ipc_init`, `ipcaccess`, the two converters; all "not installed"). Read directly.
- Consequence, reasoned under the standard rule: the semaphore and message modules are whole modules whose only outside entry points are the syscall functions `semsys` and `msgsys`, which the syscall table points at. A replacement object that defines those two and its own key space, and uses the existing `ipc.o` for permissions, replaces them completely. This is the module-level substitution the configuration language is built for. Shared memory is different: its lookup is in `vshm_mgr.o`, which has 14 symbols used from other members, so it is a replacement of one archive member of the required module (with the local-provider member that calls it).

### C. Shared memory: scoping by key and by id, without touching attach

Read for container containment, at the level of the system call entries, the key scan and the permission record only. Nothing here follows how a segment is mapped; the attach body was not read for this page. Addresses are `6.5.30/unix.IP35`.

**Entry points and replaceability.**

- `shmsys` (`6.5.30/unix.IP35`, 0xc000000000317dd8, 196 bytes) in `os.a(shm_syscalls.o)` is the system call handler. Both syscall tables (`sysent` entry at 0xc0000000015945c8, `irix5_64_sysent` entry at 0xc000000001595c00) hold it, and the table words are relocations against the undefined global `shmsys`, so an override of `shmsys` is reached, as for `semsys` and `msgsys`. It is not in `kernel.o`. Established. The first word of the argument block selects a subcommand (compares with 0 to 5 at 0xc000000000317dfc to 0xc000000000317e24; anything else returns 22), and each case calls one routine with the rest of the block: 0 calls `shmat`, 1 `shmctl`, 4 `shmstatus`, and 2, 3 and 5 call three routines that have no symbol of their own (below). Established.
- The subcommands by what they take from the caller: `shmat` (`6.5.30/unix.IP35`, 0xc0000000003175cc, 196 bytes, case 0) takes a segment id and resolves it with `vshm_lookup_id` at 0xc0000000003175e0; `shmctl` (`6.5.30/unix.IP35`, 0xc000000000317690, 720 bytes, case 1) takes an id and resolves it with `vshm_lookup_id` at 0xc0000000003176bc; `shmstatus` (`6.5.30/unix.IP35`, 0xc000000000317c9c, 316 bytes, case 4) copies in an id and calls `vshm_getstatus` (0xc0000000003174ec), which resolves it with `vshm_lookup_id` at 0xc00000000031750c. The get-segment case 3 (the routine at 0xc000000000317a24, 316 bytes, inside the extent of `shmctl`) takes a key: key 0 creates a private segment through `vshm_create` (0xc0000000003173cc, call at 0xc000000000317ad8), any other key goes to `vshm_lookup_key` (call at 0xc000000000317a80). Case 5 (the routine at 0xc000000000317b60, 316 bytes) is the same with one more argument word (+0x1c) that is passed as an id hint, `vshm_lookup_key` at 0xc000000000317bbc and `vshm_create` at 0xc000000000317c14. Case 2 (the routine at 0xc000000000317960, 196 bytes) takes an address, not a key or an id; it was not traced. Read directly for the dispatch and the call targets.
- The member `shm_syscalls.o` has six global entries: `shmat`, `shmctl`, `shmstatus`, `shmsys`, `shm_rmid_callback` (0xc000000000317fbc, 100 bytes, an exit callback that resolves an id with `vshm_lookup_id` at 0xc000000000317fd8) and the data word `time`. The routines for cases 2, 3 and 5 are local to the member, so an override object cannot call them by name. Read directly from the member's symbol table.

**The key table and the key scan.**

- `vshm_lookup_key` (`6.5.30/unix.IP35`, 0xc000000000316124, 464 bytes) in `os.a(vshm_mgr.o)`, called only from the two get-segment routines above (`.text` scan). Arguments: key in a0, flags in a1 (the low 9 bits are the mode, 0x200 asks for create, 0x400 exclusive), size in a2, creator process id in a3, credential in t0, a pointer for the result in t1, id hint in t2 (-1 for none). It returns 0 with the segment record in the result slot and a reference held (the caller releases it with `vshm_rele`, 0xc000000000316424), or an error number. Established.
- Table: `vshmtab` (0xc000000001646568, a pointer, gp+0x2df8) points at `vshmtabsz` (0xc000000001646560, gp+0x2df0) buckets of 0x78 bytes. A bucket is a circular list head (next at +0, previous at +8) with a lock at +0x10. An entry is placed in bucket (id modulo `vshmtabsz`) by `vshm_enter` (0xc000000000315f80, 188 bytes), so the table is hashed by id, not by key, and the key lookup walks every bucket in turn (loop at 0xc000000000316188 to 0xc000000000316240) and every entry of each, comparing the key word at entry +0x14 (compare at 0xc0000000003161b4). The global lock is `vshm_lookup_lock` (0xc0000000016e1528), taken with `mrlock` at 0xc000000000316170 for the scan. Read directly.
- On a match it takes a reference (`vshm_ref`, 0xc0000000003163fc), drops the lock, calls the segment's key-check operation (behavior operations slot +0x10, `pshm_keycheck`, 0xc000000000316b4c, 208 bytes) with the credential, flags and size, and, when `mac_enabled` is set, the access operation (slot +0x40). `pshm_keycheck` returns 17 when flags has both the create and exclusive bits and 13 for a permission or size failure. On no match it calls `vshm_create` and retries the whole lookup when that returns 11. `vshm_create` returns 2 when the create bit is not set; otherwise it takes an id from `vshm_allocid` (0xc000000000315d10, 236 bytes: a bitmap of `shmmni` bits at gp+0x2e18, cursor at gp+0x2e08, ids start at `shmid_base`, 0xc000000001646570), builds the record (`vshm_create_id`, 0xc000000000315e50, 208 bytes) and enters it with `vshm_enter`. Read directly.
- A key scan is therefore the single place a key becomes a segment, and the segment's key is not hidden: any entry whose key word equals the number is found, whoever created it. Read directly.

**Where a segment records who made it.**

- The segment entry (zone-allocated) holds: reference word +0x10 (starts at 1), key +0x14, id +0x18, and a behavior head at +0x20 (set up by `vshm_create_id` at 0xc000000000315ea0). The permission and creator record is the private data of its one behavior: `pshm_alloc` (`6.5.30/unix.IP35`, 0xc000000000316940, 432 bytes) allocates a 0xa8-byte record, fills it, and inserts a descriptor at record +0x70 whose private-data word is the record, whose object word (+0x78) is the segment entry and whose operations word (+0x80) is `pshm_ops` (0xc000000001599600). Reaching the record from the entry is entry +0x20, first behavior, private data. Read directly.
- `ipc_init` (`6.5.30/unix.IP35`, 0xc0000000000e6470, 44 bytes, in `ipc.o`, called from `pshm_alloc`) fills the front of the record from the key, the mode and the creating credential: owner user id at +0x00 and creator user id at +0x08 (both from credential +0x8), owner group id at +0x04 and creator group id at +0x0c (both from credential +0xc), mode at +0x10 (the low 9 bits of the flags, with 0x8000 set), key at +0x20. `pshm_alloc` then stores the size at +0x48, the creator process id at +0x5c (the argument in a3), a time word at +0x68 and the label word at +0x90. Established for the stores.
- There is no container tag, session or process-group field in the record or the entry. A tag therefore has to be kept in a side table keyed by segment id, filled when the override creates the segment. Read directly for the absence in the stores above; the side table is a design suggestion.
- `ipcaccess` (`6.5.30/unix.IP35`, 0xc0000000000e60f8, 228 bytes, in `ipc.o`) is the permission test used for segments: it compares the caller's user id with record +0x00 and +0x08, then the group tests against +0x04 and +0x0c, then the mode bits at +0x10, and falls back to a capability test. It checks the mode of the caller against the creating credential, not any namespace. Established.

**Can the attach routine stay stock?** Yes, for containment by key and by id. Every id a caller names reaches a segment through `vshm_lookup_id` (0xc0000000003174c0, 44 bytes, in `os.a(vshm_mgr_lp.o)`) before anything else is done with it: `shmat` calls it at its first step (0xc0000000003175e0), `shmctl` at 0xc0000000003176bc, `shmstatus` through `vshm_getstatus` (0xc00000000031750c), and the mandatory-label routines at 0xc000000000316768 and 0xc00000000031686c. Its only work is to call `vshm_lookup_id_local` (0xc0000000003162f4, 264 bytes, in `vshm_mgr.o`), which finds the entry by id in bucket (id modulo `vshmtabsz`) through `vshm_qlookup` (0xc000000000315f20) and returns a referenced entry, or 22 when the id is not there. A containment check placed at `vshm_lookup_id` (refuse an id whose recorded tag is not the caller's, with the same error as a missing id) is reached by every id-taking path, including the exit callback, and leaves `shmat` and `shmctl` unchanged. Established for the call sites (seven sites: two in `shmctl`, one each in `shmat`, `vshm_getstatus`, the exit callback and the two label routines); inferred that no id-taking path skips this function, since the `.text` scan found no other caller.

**Where to put the override, and the shadowing hazard.**

- The segment table and the id bitmap are single globals (`vshmtab`, the bitmap at gp+0x2e18), shared by every caller. Overriding `shmsys` or `shm_syscalls.o` as a whole does not give a container its own table: it only changes who may reach the one table. Read directly.
- Replacing the handler the way `semsys` and `msgsys` are replaced is a poor fit here. Cases 2, 3 and 5 are local routines of `shm_syscalls.o`, so a replacement `shmsys` cannot fall through to them for host callers; it would have to reproduce them, and the address-based case 2 cannot be reproduced without the attach internals. That route therefore needs the attach internals and is not recommended.
- The recommended route stays below the handler and reproduces nothing but the key scan: override the global `vshm_lookup_key` (called only from the two get-segment routines, cross-member, so a boot object's definition is reached) with a copy of the scan above that skips entries whose recorded tag differs from the caller's tag (tag recording is left to the `vshm_create` override, which the copied scan's own call to `vshm_create` reaches cross-member; see *Where creation happens* below); and override the global `vshm_lookup_id` (44 bytes, called from the seven sites above) with a wrapper that calls `vshm_lookup_id_local` (not replaced, so still callable by name) and releases and refuses the result when the tag does not match. For a caller without a tag, the replacement `vshm_lookup_key` runs the same scan with no filtering and the wrapper returns what `vshm_lookup_id_local` returned, so host behaviour is the stock behaviour. Stock `vshm_lookup_key` cannot be called from its replacement (the replacement wins the symbol), so the scan has to be copied; it is short and uses only exported symbols (`vshm_ref`, `vshm_rele`, `vshm_create`, `mrlock`, `mrunlock`). Reasoned; the `vshm_create`-owns-the-tag variant below is **verified on-guest**.
- Host tools that list segments (`ipcs` and the status subcommand) walk ids through the same `vshm_lookup_id`, so the id check also hides other tags' segments from a tagged caller's listing. Whether a host listing should show tagged segments is a policy choice: the wrapper above lets an untagged caller see every segment. Reasoned.

**Facts for reimplementing the key scan (signatures, references, locks, iteration).** Read directly from the routines named; addresses are `6.5.30/unix.IP35`. Established unless marked.

*Signature of `vshm_lookup_key` (0xc000000000316124).* `int vshm_lookup_key(int key, int flags, size_t size, pid_t pid, cred_t *cred, vshm_t **out, int idhint)`. The registers on entry are a0 key (32-bit), a1 flags, a2 size, a3 creator process id, t0 credential, t1 the out pointer, t2 the id hint (-1 for none; the first call site, the get-segment routine at 0xc000000000317a24, passes -1; the second, at 0xc000000000317b60, passes the caller's extra word). The result is 0 with the entry stored at `*out` and one reference held for the caller, or an error number with `*out` untouched. A miss on a non-private key without the create bit (0x200) returns 2 (from `vshm_create`, below). Callers release the reference with `vshm_rele`.

*Where creation happens.* Inside `vshm_lookup_key`. When the scan ends with no match, the lookup calls `vshm_create` itself (call at 0xc00000000031625c) with the same key, flags, size, pid, credential, out pointer and hint, and returns its status (restarting the whole lookup, with the lock taken again at 0xc000000000316170, if `vshm_create` returns 11). The system call code does not create a keyed segment. It calls `vshm_create` only for key 0, the private case (call at 0xc000000000317ad8, and 0xc000000000317c14 for the variant with an id hint), and never when the key lookup has been asked for a key. The create flag therefore changes nothing in `vshm_lookup_key` itself: a reimplementation records the container tag after its own call to `vshm_create` returns 0, using the id stored in the new entry (`(*out)->id`, entry +0x18), and records it also for the private-key calls if the override covers them. **Verified on-guest 2026-11-07** (nsipc shm module): the earlier premise that this keyed `vshm_lookup_key`→`vshm_create` call stays intra-member, so a global `vshm_create` override would miss it, does not hold once `vshm_lookup_key` is itself overridden. The override lives in a separate boot object, so its call to `vshm_create` is cross-member and a global `vshm_create` override fires on the keyed create as well as the private (key 0) one. The simpler working route is therefore to let the `vshm_create` override own the tag for both the keyed and the private create, and to drop the tag-set from the `vshm_lookup_key` override, which then only filters the scan. On-guest this recorded every segment at creation, refused unrecorded segments to the container, and removed the first-use claim race.

*`vshm_create` (0xc0000000003173cc, 244 bytes) and `vshm_create_id` (0xc000000000315e50, 208 bytes).* `int vshm_create(int key, int flags, size_t size, pid_t pid, cred_t *cred, vshm_t **out, int idhint)`, the same argument registers as `vshm_lookup_key` (a0 to a3, t0, t1, t2). It returns 0 or an error number, and the object, not the id, is returned through `*out`, with a reference held for the caller; the id is `(*out)->id` (entry +0x18). Without the create bit it returns 2 (after releasing the lock when the key is non-zero). It gets an id from `vshm_allocid(idhint)` (negative result: returns 28), builds the entry with `vshm_create_id` (a0 key, a1 id, a2 flags, a3 size, t0 pid, t1 credential, t2 out; it zone-allocates the entry, sets reference word +0x10 to 1, key +0x14, id +0x18, initialises the behavior head at +0x20 and calls `pshm_alloc`; on failure it frees the entry and returns the error and `vshm_create` frees the id with `vshm_freeid`), and on success enters it with `vshm_enter` (0xc000000000315f80), which takes a second reference for the table. So a successful create leaves the entry at reference count 2: one for the table, one for the caller.

*Lock state across `vshm_create`.* Critical for a copy of the scan. For a non-zero key `vshm_create` expects the caller to hold the lookup lock and always releases it before returning (`mrunlock` at 0xc000000000317404 for the no-create return, 0xc000000000317470 after creating, 0xc000000000317498 when no id is available). `vshm_lookup_key` is holding the lock (taken at 0xc000000000316170) when it calls `vshm_create`. For key 0 the caller holds nothing and `vshm_create` takes the lock itself in access mode (call at 0xc0000000003174b0) and releases it at 0xc000000000317470. A reimplementation that calls `vshm_create` with a non-zero key must therefore hold the lookup lock in the same way, and must not release it afterwards.

*References and `vshm_lookup_id_local` (0xc0000000003162f4).* `vshm_ref` (0xc0000000003163fc, 40 bytes, `void vshm_ref(vshm_t *e)`) atomically adds 1 to the word at entry +0x10 (load-linked, store-conditional loop) and returns nothing. `vshm_rele` (0xc000000000316424, 84 bytes, `void vshm_rele(vshm_t *e)`) atomically subtracts 1 from the same word and, when the result is zero, calls the first behavior's operation at slot +0x48 (`pshm_destroy`, 0xc000000000317338); it returns nothing. `vshm_lookup_id_local(int id, vshm_t **out)` sets `*out` to 0 first and, on success, stores an entry that is **already referenced**: `vshm_qlookup` (0xc000000000315f20, 96 bytes, `void vshm_qlookup(bucket_head *b, int id, vshm_t **out)`, a linear walk of one bucket that calls `vshm_ref` on the match at 0xc000000000315f70 and stores it, or stores 0) is called under the bucket's lock, and the one rejection path in `vshm_lookup_id_local` itself (the label check at 0xc0000000003163c8) calls `vshm_rele` before returning 13. So a tag-mismatch rejection in the wrapper **must call `vshm_rele(entry)`, set `*out` to 0, and return an error** (22 matches a missing id: `vshm_lookup_id` turns the local return 2 into 22 at 0xc0000000003174dc). Skipping the release leaks one reference per rejected call and the entry can then never be destroyed. Return values of `vshm_lookup_id_local`: 22 for a negative id, 2 for no such id, 13 for a label refusal, 0 for success.

*The lookup lock.* `vshm_lookup_lock` (0xc0000000016e1528, 104 bytes) is a multi-reader lock (an `mrlock`) at the symbol itself: pass `&vshm_lookup_lock` (0xc0000000016e1528) directly to `mrlock` and `mrunlock`, not an object plus an offset. Verified on-guest 2026-11-07 (nsipc shm module); the earlier +0x10/separate-mutex decode was wrong and panics with "Unlocking an unknown mrlock!". The lock is taken with `mrlock(lock, mode, 0x19)` (0xc00000000023ac90, 28 bytes: mode 1 jumps to `mraccessf`, 0xc000000000237648, any other value to `mrupdatef`, 0xc000000000237810) and released with `mrunlock` (0xc0000000002379e4). The key scan takes it in mode 2 (update; `mrlock` call at 0xc000000000316170), `vshm_iterate` also in mode 2 (0xc00000000031649c), the id lookup and `vshm_remove` in mode 1 (access; 0xc000000000316320 and 0xc00000000031608c). The key scan holds it across the whole walk and releases it at 0xc0000000003161c8 only after a match has been referenced (and passes it, still held, to `vshm_create` on a miss). The per-bucket lock (bucket +0x10) is separate: the id lookup takes it in mode 1 around `vshm_qlookup`, `vshm_enter` and `vshm_remove` take it in mode 2; the key scan does not take it. Whether mode 2 excludes concurrent mode 1 holders was not read (inferred only that the scan is protected from `vshm_enter`/`vshm_remove` by the bucket and entry updates being made under the bucket lock).

*The walk.* There are no slots to be free or used: `vshmtab` (0xc000000001646568, read as a pointer each iteration) addresses `vshmtabsz` (0xc000000001646560) buckets of 0x78 bytes, and each bucket is the head of a circular list of entries (head next at +0, previous at +8). For bucket i from 0 to `vshmtabsz` - 1: head = `vshmtab` + i * 0x78; the bucket is empty when head->next == head (compare at 0xc00000000031618c); otherwise e = head->next and, while e != head, test the key word at e +0x14 (`lw` and compare at 0xc0000000003161b0 and 0xc0000000003161b4; confirmed) and advance with e = e->next (`ld` at 0xc00000000031619c, loop end at 0xc0000000003161a0). The first match ends the walk; a second entry with the same key is never reached. Both globals are re-read each iteration (0xc000000000316230, 0xc000000000316238).

*Removed entries.* `vshm_remove` (0xc00000000031603c, 220 bytes, `void vshm_remove(vshm_t *e, int clear_id)`) unlinks the entry from its bucket under both locks, stores 0 in the entry's next and previous words (0xc0000000003160e8, 0xc0000000003160f0) and drops the table's reference. A removed entry is therefore on no list and the scan cannot meet it; it survives only while others hold references. `vshm_is_removed` (0xc000000000316118, 12 bytes) is true when the previous word (+8) is 0. `vshm_islocal` (0xc0000000003175b0, 20 bytes) compares a word at argument +0x10 with a global (a cell-identity style test) and is not a removal test; do not use it for that.

*What the override may reuse.* `vshm_iterate` (0xc000000000316478, 208 bytes, `void vshm_iterate(void (*fn)(vshm_t *e, void *arg), void *arg)`) walks every bucket and every entry under the lookup lock in mode 2, calls `vshm_ref` on the entry, calls `fn(e, arg)`, then `vshm_rele`; the return value of `fn` is ignored (so it cannot stop early) and the lock is held during `fn`, so `fn` must not take the lookup lock or call `vshm_create`, `vshm_remove` or `vshm_lookup_id`. An override can call it with a function that compares the key and the tag and, on a match, takes its own `vshm_ref` and stores the entry, then run the behavior key-check and create-on-miss itself after the walk returns, serialising the whole sequence with a lock of its own (the library lock is released between the walk and `vshm_create`, so two callers could both miss and create the same key without it). `vshm_qlookup` is for an id inside one bucket and `vshm_lookup_id_local` already uses it; `vshm_allocid`, `vshm_create_id` and `vshm_freeid` are steps inside `vshm_create` and should not be called separately. The key-check step an override must repeat after a match is: take the entry's first behavior (entry +0x20), its operations (+0x10), and call slot +0x10 with the behavior, the credential, the flags and the size (the call at 0xc0000000003161e4); a non-zero result is returned after `vshm_rele`; when the global at gp+0x2d20 (`mac_enabled`) is non-zero call slot +0x40 with the behavior and the current credential (0xc000000000316298) and treat a non-zero result the same way; on success store the entry at `*out`, keeping the reference taken for it. Established for the reading; the reuse advice is inferred.

## General characterisation

Measured on `6.5.30/unix.IP35` unless marked.

- **Indirect calls are rare in code, common in the shape of the data.** Counting instruction words in `.text` that are a direct call (`jal`) or a register call (`jalr`): 81,035 and 4,171, so 4.9% of calls are register-indirect. Almost all calls are direct; the indirect ones go through the tables listed next. The count is an opcode scan of the section and includes any data words in it.
- **Behavior operations tables (vector, extendable by data):** the pattern is a head record, a behavior descriptor whose word +0x10 holds an operations table, and an indirect call through a slot. Tables of this kind are `phost_ops`, `pshm_ops`, `psem_ops`, `psession_ops`, `ppgrp_ops`, `pfile_ops` and `pas_ops`, plus 18 vnode-operations tables and 15 file-system (vfs) operations tables (types `xfs`, `efs`, `nfs`, `nfs3`, `lofs`, `autofs`, `udf`, `umfs`, `fifo`, `pipe`, `spec`, `nm`, `fdfs`, `hwgfs` and the process file system; the vnode tables add a dead-vnode table and two more for devices). All are static initialised data in the same archive member as the code that creates the object. No registration call exists for the host, shared-memory and semaphore tables (see above); a file system is registered through the switch below.
- **Generated switch tables (extendable by configuration):** the file-system switch `vfssw` (0xc00000000154a798, 0x3f0 bytes), the character and block device switches `cdevsw` (0xc000000001542f78, 0x3d28) and `bdevsw` (0xc000000001540538, 0x29d8), and the streams module switch `fmodsw` (0xc00000000154a3b8, 0x3e0) are defined by no boot object. The shipped 6.5.22 `var/sysgen.IP35/master.c` is marked as generated by `lboot` and defines arrays of those names, built from the master files (flags `j` file system, `c` and `b` devices, `f` and `m` streams). So a new file system, device or streams module is added by a master file, an object in the boot directory and a `USE:` line. The 6.5.30 link of those arrays is reasoned from the 6.5.22 files.
- **Static dispatch table:** the system-call tables `sysent` and `irix5_64_sysent` (`sysent` at 0xc0000000015940e0, 0x1638 bytes) are initialised data in one `os.a` member, read by `kernel.o`, `proc.a(priface2.o)` and `uncintf.o`. Each entry holds the handler's address (`uname` at +0xec0). Whether anything writes the table at run time was not searched: unknown.
- **Hard calls and global tables:** the mount list and crossing, `utsname` and `hostname`, `vshmtab`, `vsemtab`, `msgque`, the credential and capability checks. These carry no vector.
- **Loadable modules** (flag `d`, loaded by the module loader) resolve their undefined names against the kernel's symbol table and add code and data; the loader in [module-interfaces.md](module-interfaces.md) has no rule for a module symbol that replaces a kernel one. A loadable module can therefore fill a switch table but not displace `phost_ops` or the lookup routines. Reasoned from the loader's name lookup; the replace-versus-reject case was not read.
- **Interrupt vectors, streams message dispatch and the device-driver entry points** were not read for this page: unknown.

## Bottom line

The consumer's question is which of mount, host name and IPC look reachable by supplying our own kernel objects at link time, rather than by changing kernel memory while it runs. The linker policy for duplicate definitions, which these rows depend on, is resolved above (a boot object's symbol wins).
