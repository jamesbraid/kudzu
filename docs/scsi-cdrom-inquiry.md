# The INQUIRY vendor and product text of a SCSI CD-ROM

Who reads the vendor and product fields that a CD-ROM drive returns for INQUIRY, and what they change: the SGI firmware that probes the bus, the IRIX 6.5.30 and 6.5.22 kernels, and the removable-media daemon. Every entry is graded **established** (read in full in a binary, with the address), **inferred** (a reasoned reading) or **unknown**. Addresses are locators in the file named; a PROM's addresses are the load addresses its own code uses unless the entry says the base is inferred.

"Text" means the 8-byte vendor field and the 16-byte product field as INQUIRY returns them, in that order.

## Firmware

The firmware that probes a SCSI bus on these machines is the PROM for the Octane (IP30), the O2 (IP32) and the base-I/O PROM for the Origin 200/2000 and the Origin 300/3000. The CPU PROMs for the Origin machines (the IP27 6.156 and IP35 6.210 payloads) hold no SCSI target code; their SCSI strings are board-configuration messages.

Files read: the IP30 PROM Rev 4.17 shipped with 6.5.30 (`IP30prom.bin`, SHA-256 `ee4722ca6f9b821ffadf156346c4d69bf5be71fc4b911cee75e36a1f51a49972`, loaded at `0x1fc00000`), the 6.5.30 O2 PROM image (SHA-256 `11230c353cb14fcc50ede286df228e169e32fc9e5a2206276ae29c259fafb23c`), the Origin base-I/O PROM 6.156 (the gzip decompression of the IO6 payload, SHA-256 `bf341a71821541233cb96459f6b99f6f4ecd2cf90f7e9321d918686ee6c25047`, link base `0xc000000011c00000`) and the base-I/O PROM nested in the IP35 6.210 payload (SHA-256 `f903b3ce33b86c286f168ba43395f36a0073c24b1d4e703adce240f683b8c2d7`, link base `0xc000000013000000`).

What opcode `0xc9` does is unknown at the drive. The firmware sends it only to a unit that already reports type 0, so a drive that reports type 5 never sees it from firmware. The `scsicontrol` utility sends the same opcode (below), which with the public report that a Toshiba XM-3501TA comes up as a disk until put "in CD-ROM mode" is *inferred* to mean "switch the drive to its CD-ROM personality".

## IRIX kernels

Kernels read: the installed `unix.IP27`, `unix.IP30` and `unix.IP35` of 6.5.30 (SHA-256 prefixes `567474674eaa`, `607a432f441d`, `412a1aae553a`) and of 6.5.22 (`40e3f6246b58`, `e913b7022abb`, `87563dbc0cbc`).

- **A four-name test.** A table `cdrom_inq_strings` of four strings, `CDROM`, `CD-ROM`, `CD ROM`, `DVD-ROM`, and a predicate `cdrom_inquiry_test` over it that returns 1 when a substring search of the text finds any (the predicate is 108 bytes; 6.5.30 IP30 `0xa800000020095284`, table `0xa800000020425fe8`). The table and the predicate are the same in all six kernels (6.5.30 IP27 `0xc0000000000c3d5c`, IP35 `0xc00000000010fca4`; 6.5.22 IP30 `0xa80000002008be24`, IP27 `0xc0000000000cf8e8`, IP35 `0xc000000000112b50`). Three call sites in each (6.5.30 IP30 `0xa80000002008e890`, `0xa80000002009636c`, `0xa80000002009be78`). **established**.
- **No vendor name.** The kernels test no drive vendor: the only `Toshiba` strings are in the 6.5.30 IP30 and IP35 kernels, two company-name table entries; the IP27 kernel and the three 6.5.22 kernels have none. **established** (string scan plus the call sites above).
- **What the test changes** (6.5.30 IP30): at `0x2009636c`, reached only when INQUIRY byte 0 has type 0 (`0x20095f38` to `0x20095f40`), a pass rewrites the unit's INQUIRY data as type 5 with the removable bit (bytes 1 and 0 set to `0x80` and `5`) before classification; at `0x2008e890` a pass stores a pointer to a kernel-global table at offset `0x480` of the unit and a fail stores zero; at `0x2009be78` the result goes into bit 0 of a per-unit flag byte. A unit that already reports type 5 is a CD-ROM with or without a pass. **established** for what each site writes; what the table pointer and the flag bit then do is **unknown**. The call-site reading was done in the 6.5.30 IP30 kernel only; the other five are **inferred** to match.
- **Block size.** The kernel's MODE SELECT and MODE SENSE code does not test the vendor (call sites in the 6.5.30 IP30 kernel: parse `0x200925bc`, sender `0x20092b20`); this restates what the PROM-side reading found and is **established** for that kernel.

## The removable-media daemon

Files read from an installed 6.5.30 system: `/usr/etc/mediad` (SHA-256 `a2895dbbc296c402b2f13dece31f0df8460960e89eee82cbc943d86c1b0f35ec`, N32 big-endian, stripped), the device module `/usr/lib/devicelib/dev_cdrom.so` (`caecab09eef4e86783d241c959d7659f94cabae5332b4d4bcda0147f576ccce6`) and `/usr/sbin/scsicontrol` (`02583d3b76a4953a19f5937b0ca17baade3e236d6826e649c7aa55f309447cfd`). No 6.5.22 userland is held.

- **Selection by class and type, not text.** The daemon builds one device object per kernel inventory entry (its constructor from an inventory record, `0x10012c78`) and offers it to each device module's `instantiate`. The CD-ROM module's `instantiate` (`0x01cf2120`) accepts an inventory class of 9 (SCSI) with type 5 (CD-ROM), and nothing else. The daemon's fallback names are "Unknown Device", "Unknown Tape Device" and "Unknown CD-ROM Device". **established** for the acceptance test; the fallback strings are present, their selection logic was not traced.
- **The 1995 warning is gone.** The message a 1995 post reports, "Unknown CDROM brand ... may not function", is not in the daemon, its client library or the CD-ROM module. **established** for the absence of the string.
- **A brand table with command sets.** The CD-ROM module's constructor (`0x01cf2220`) compares the raw text (vendor and product, from INQUIRY byte 8) with eight prefixes by `strncasecmp` over each prefix's length and stores a class at offset `0x44`: `TOSHIBA CD` 1, refined (only when INQUIRY byte 2 masked with 7 is 2) to 3 if it also begins `TOSHIBA CD-ROM XM-5401` and to 2 if not, `TOSHIBA DVD-ROM` 7, `SONY    CD` 4, `MATSHITACD` 5, `HITACHI DVD-RAM` 6, `MATSHITADVD-RAM` 8, `TEAC    CD-540E` 10; no match leaves 0. The table is at file offset `0x4000`. `TOSHIBA CD-ROM XM-5701TA` has no entry of its own, so it is class 2 when its version byte is 2 and class 1 otherwise. **established**.
- **What the class changes.** Classes 1 to 3 send the vendor opcode `0xc4` (via the 10-byte command builder) in the routine at `0x01cf28ac` (`0x01cf29f4`), where the other classes send START STOP UNIT (`0x1b`, `0x01cf2908`, with a TEAC special case for class 10), and send `0xc9` in the routine at `0x01cf30f8` (`0x01cf3164`), which no other class reaches. Classes 1, 2 and 3 take a different path from the others in at least four further routines (`0x01cf2c88`, `0x01cf31d8`, and the device-node naming at `0x01cf266c`); classes 6 and 8 (the DVD-RAM drives) do in `0x01cf32f8`. **established** for the opcodes and the branching; that `0x01cf28ac` is the software eject and `0x01cf30f8` a mode switch is **inferred** from the START STOP UNIT pattern and the shared opcode with `scsicontrol`. No class-0 (unlisted) path uses a vendor opcode. **established**.
- **`scsicontrol`.** The utility has a routine at `0x10002d14` that sends a 10-byte command with opcode `0xc9` and a flag value of `0x80` or 0 chosen by its argument, called at `0x100040d4`; its usage text lists "-C (cdrom mode)" and it prints "revert to cdrom fails". That the routine is that option's path was not traced: **inferred**.

## Open

- What `0xc4` and `0xc9` do to a drive: **unknown** (no software reveals it beyond the callers above; the next route is a Toshiba drive manual).
- The Octane2, Origin 350, Tezro and Fuel base-I/O PROMs and the IP22 PROM: not held.
- An installed 6.5.22 `mediad` and device library: not held; the next route is a 6.5.22 system disk.
- The class table's effect on the remaining routines (`0x01cf2c88`, `0x01cf31d8`, `0x01cf32f8`): located, not read to the end.
