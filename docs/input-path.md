# Input events from a serial tablet to Xsgi

How an input event made by a STREAMS module on a serial line reaches the X server on an IRIX 6.5 Octane-class system (IP30 kernel objects, the generic `Xsgi`), and what has to be true on the way for an XInput `DeviceMotion` event to reach a client. The question that started this page: a vendor tablet module is pushed on `/dev/ttyd2` by Xsgi, the module calls the generic input-device routines for every packet, an XInput client selects `DeviceMotion` on the opened device and receives nothing, and its crosshair follows the tablet only after PS/2 mouse motion arrives.

Everything here is read from shipped binaries. Nothing was run, so nothing is an observation of behaviour.

## The path, in order

1. **Serial bytes arrive as `M_DATA`.** `idev_rput` (`idev.o` `0x18c0`) hands each data block to a per-module callback stored at word `+0x18` of the module's private record, then frees the block (`0x197c` to `0x1994`). Flush messages flush the read queue (`0x1944`); other messages go on with `putnext`, normal ones only after `canput` (`0x18fc`). Established.
2. **The callback calls the generic event routines.** `idevGenValEvents` (`0x49c`) builds valuator events, `idevGenPtrEvent` (`0x1bc`) builds pointer-position events, `idevGenBtnEvent` (`0xf64`) builds button events. Each allocates a buffer (`allocb` with priority 2 at `0x754`, `0x338`, `0x1000`), writes 12-byte event records into it and calls `putnext` on the module's own read queue (`0x6d4`, `0x3a8`, `0x1084`). Established.
3. **Event record.** Bytes 0 to 3 hold two shorts read from `+0x10` and `+0x12` of the module record (the link identity, below). Byte 4 is the low byte of the index, byte 5 the valuator or button number, byte 6 the type (0 pointer position, 1 valuator, 2 button; written at `0x374`/`0x5c0` and `0x106c`), byte 7 flags (bit 0 is "more events of this group follow" for valuators, "pressed" for buttons), bytes 8 to 11 the value (two shorts, x and y, for type 0). Established; matches the layout in `sys/shmiq.h`.
4. **The module learns its link identity from the queue driver.** When Xsgi links the stream under the shmiq device, `linkLowerStream` (`shmiq.o` `0x4d4`) allocates a free slot out of 32 (`0x4f4` to `0x508`) and sends the lower stream an 8-byte priority message with the four characters "SHMQ", the shmiq minor and the slot index (`0x524` to `0x594`). `idev_wput` (`idev.o` `0x1d38`) recognises it (`0x1db8`), stores the two shorts at `+0x10` and `+0x12` (`0x1eb4`, `0x1ec8`) and answers by queue reply with the magic reversed (`0x1ecc` to `0x1ed0`). If no answer arrives during the put, the slot is not kept: the link record is freed and the routine returns 0x47 (`0x60c` to `0x64c`). On success it calls `noenable` on the lower read queue (`0x61c`). Established. Consequence (established from this code, effect inferred): a module that does not answer the handshake cannot be linked, and events built before the handshake carry identity 0/0.
5. **The lower read queue's put routine delivers straight to the shared queue.** `shmiq_rput` (`0xf50`) calls `shmiq_rproc` (`0xcd8`) and queues the message only if that returns nonzero. For `M_DATA`, `shmiq_rproc` takes the shmiq lock, reads the slot index from the second short of the first record (`0xe7c`) and frees the message if the index is 32 or more or the slot is empty (`0xe80` to `0xe9c`, `0xf08`). If no shared-memory queue is attached it passes the message up the stream head instead (`0xf30` to `0xf40`). If the queue's overflow flag is set it returns 1 and the message waits on the lower queue (`0xeac` to `0xeb4`). Otherwise it calls `qEvents` (`0xed8`) with the record count and frees the message when all records were taken (`0xee0`, `0xf20`). Established.
6. **`qEvents` (`0x308`) copies and wakes.** It checks the shared queue's tail against the kernel's private copy and the head against the queue size and sets the corrupted flag (bit 1) on a mismatch (`0x334` to `0x35c`). It computes free space (`0x368` to `0x378`). When there is not enough room it sets the overflow flag (bit 0, `0x394` to `0x39c`). When there is room it calls `copyEventData` (`0x3f4`) and stores the new tail in both the private and the shared copy (`0x404`, `0x408`). Both outcomes then clear the device's "drained" flag and call `pollwakeup` on the shmiq's poll head with `POLLIN|POLLRDNORM` (`0x3c0`, `0x3c4`). Established.
7. **`copyEventData` (`0x1e4`) stamps and tracks the cursor.** It writes the current tick count into the first word of every copied record (`0x274`). If the link's flag word (link `+0x2c`) has a cursor bit set and the record type is 0, it saves x and/or y into the kernel's cursor state (`0x2cc` to `0x2ec`) and, after the copy, repositions the kernel cursor (`0x2b0`, `0x2f8`). Established.
8. **Xsgi waits on the queue-control device.** `shmiqGetFDs` (`Xsgi` `0x10283280`) opens `/dev/shmiq` and then `/dev/qcntl<minor>` built from the shmiq's device number, and marks both close-on-exec. `shmiqInit` (`0x100f6050`) allocates the shared memory (`0x100f6078`), calls `shmiqGetFDs` (`0x100f6088`), then issues the attach ioctl on the qcntl descriptor with an event count of 0x553 (`0x100f60a4`, `0x100f60b8`). `InitInput` (`0x1016b660`) then points the server's input-check pair at the queue's head and tail words (`0x1016b73c`, `0x1016b748`) and sets the qcntl descriptor's bit in `EnabledDevices` (`0x102c6690`) and in the 32-byte set next to it (`0x1016b75c` to `0x1016b778`). Established; that the second set is the server's wait set is inferred from its position beside `EnabledDevices`.
9. **The qcntl poll entry is level triggered.** `qcntlpoll` (`qcntl.o` `0x0`) answers only the `0x41` read bits. With no attached queue it returns an error (6). If the shared queue's head equals the private tail it reports no events and sets the drained flag; otherwise it reports `POLLIN|POLLRDNORM`; when the caller has no events yet it returns the shmiq poll head so the caller can sleep on it (`0x1c` to `0x104`). Established.
10. **Xsgi drains the queue in its dispatch loop.** At the top of each pass `Dispatch` compares head with tail (`0x101aa124`, `0x101aa128`) and, when they differ, reads records inline (the same loop as `ProcessInputEvents`, `0x100e9680`), calls a handler per record, advances head and wraps at 0x553 (`0x100e9754` to `0x100e9790`). When the queue is empty and the overflow flag is set it sends the acknowledge ioctl on the qcntl descriptor (`0x100e9700` to `0x100e9718`, request `0x20005103`). Established.
11. **Per-record dispatch.** The handler for a record is looked up in a 12-byte-per-slot table at `0x102ca580`, indexed by record byte 4; the function is at slot `+4` and its argument at `+8` (`0x100e975c` to `0x100e9778`). `shmiqLink` (`0x10094120`) fills the slot (`0x100941ec` to `0x100941f8`) with `processShmiq` (`0x10060650`) as function and the device record as argument. `processShmiq` picks a handler from the device record by record type: type 0 uses the pointer handler at `+0x58` (`0x100606c8`); type 2 the button handler at `+0x60`, a per-button table when device flag `0x10` is set (`0x100606f4` to `0x1006071c`); type 1 the valuator handler at `+0x64`, a per-valuator table when flag `0x20` is set (`0x100606a0` to `0x100606c4`). Any other type logs "Unknown event type" (`0x10060690`). Established.
12. **Handlers installed at device creation.** `simpleCreateDevice` (`0x100e14a0`) installs `simpleButton` (`0x1023fe60`, at `0x100e1774`), `simpleValuator` (`0x1009bfe0`, `0x100e1870`) and `simplePointer` (`0x101d90b0`, `0x100e1880`) in the device record that `processShmiq` reads. The valuator handler and the valuator class are created only when the module's description reports at least one valuator (`0x100e1860`, `0x100e18ac`). The creation routine's closing block sets the device's process-input and real-input procedures to `ProcessOtherEvent` (`0x10201cc0`) or, when a global XKB flag is set, to `XkbProcessOtherEvent` (`0x101b3580`), which tail-calls `ProcessOtherEvent` (`0x101b3644`) (`0x100e22b8` to `0x100e22e4`, `0x100e23ac`). Established for the assignments; that a non-keyboard device reaches that closing block was not traced (inferred from the shared tail).
13. **XInput delivery.** `simpleValuator` batches consecutive valuator records and flushes when a record's "more follow" bit is clear (`0x1009c06c`). It calls `xdevSendValEvents` (`0x102384e0`) unless the device's process-input procedure is `ProcessPointerEvent`, i.e. the device is the registered core pointer (`0x1009c09c`). `xdevSendValEvents` builds a device-motion event whose root coordinates are the core pointer's current position (`0x102384f8` to `0x10238514`) and calls the device's process-input procedure (`0x10238640`, count 2). `ProcessOtherEvent` calls `DeliverDeviceEvents` (call at `0x102022ac`) when no grab applies and `DeliverGrabbedEvent` (`0x10202570`) when one does. Established for the calls; which window `DeliverDeviceEvents` starts from is read in question 4 below.
14. **Pointer role.** `simplePointer` calls `corePointerEvent` (`0x100a9fb0`, call at `0x101d91e0`) after its own checks. `corePointerEvent` records the position and hands a motion event to the core pointer's input procedure; it does not draw or move the on-screen cursor. Established; see [Why a pointer record moves no cursor](#why-a-pointer-record-moves-no-cursor-onyx2-impact).

## Answers

### 1. Path to Xsgi, wakeup, and any wait that needs a PS/2 event

- **Path** (established): module `putnext` on its own read queue, which is the stream below the shmiq multiplexer; `shmiq_rput`/`shmiq_rproc` copy the records into the shared-memory queue (steps 2 to 7). There is no intermediate service queue on the normal path.
- **Wakeup** (established): `qEvents` calls `pollwakeup` on the shmiq poll head; Xsgi's `select` set contains the **qcntl** descriptor, whose poll entry reports readable whenever head differs from the kernel's private tail (steps 6, 8, 9). The server also compares head and tail itself at the top of each dispatch pass (step 10), so a record queued between that check and the `select` is still seen. It does not wait on the `/dev/shmiq` descriptor and does not poll only the head.
- **A path that waits for a PS/2 event** (established: none in these objects). The three coupling points are the single shared queue and its single poll head, the overflow flag, and the 32-slot table. All devices on one shmiq share one queue and one wakeup, so a PS/2 event does not wake the tablet's records any more than the reverse: the first `qEvents` call wakes the server and the drain loop reads everything queued.
  - Overflow stalls every linked device, not one: while the flag is set `shmiq_rproc` holds all `M_DATA` on its lower queue (`0xeac`), the lower read queues are `noenable`d (`0x61c`), and they drain only after the server's acknowledge ioctl on the qcntl descriptor (`0x20005103`; its handler clears the flag and schedules the upper queue through `streams_interrupt` at `qcntl.o` `0x440` to `0x450`). The acknowledge is sent only when the server finds the queue empty and the flag set (step 10). The enable of the upper queue by that callback is inferred (the callback is a pointer in `.srdata`, not read), and what the upper queue's service routine then does is established: `shmiq_rsrv` (`0x1004`) walks the 32 links from the top, takes queued messages and re-runs `shmiq_rproc` on each (`0x1044` to `0x1074`).
  - Records whose slot index is empty or 32 or more are freed without a wakeup (`0xf08`). A tablet whose link identity was never set (step 4) therefore produces records that the queue driver drops silently. Whether this applies to the tablet in question depends on the module, which was not read.
  - Whether the PS/2 mouse reaches the queue by the same path (a STREAMS stack of `ioc3_pckm.o` under the mouse module under shmiq) was not read to the end: `pckm_rx` (`0x137c`), `pckm_rsrv` (`0xea8`, which `putnext`s) and the absence of any idev call in `ioc3_pckm.o` show a raw port driver, and the translation module above it was not read. Inferred.

### 2. Does `idevGenValEvents` drop or coalesce events?

All of the following are established from the routine (`idev.o` `0x49c` to `0x788`). The module-record word offsets are inferred layout.

- **Range.** It returns 0 without doing anything when the count byte of the descriptor is 0 or less (`0x4d0`), or when first axis plus count exceeds the module's valuator count at `+0x40` (`0x4e8`).
- **Pointer axes.** If `+0x68` has either of bits `0x10` or `0x20` set it first calls `idevGenPtrEvent` for the pointer x/y axes (`0x4f8`, `0x500`). That routine emits a type 0 record only for the axes named in `+0x70`/`+0x72` and only when the transformed coordinate changed or the caller's flags include `0x42` (`0x2c0`, `0x31c`, `0x474`).
- **Valuator events need the mode bit.** If bit `0x02` of `+0x68` is clear, no buffer is allocated and no valuator record is sent (`0x514`, `0x51c`). If bit 19 of the third argument is set the same happens (`0x518`, `0x528`). The tracked per-valuator values at `+0x48` are still updated (`0x564`), so the state changes without an event.
- **Per-valuator enable.** With a buffer, a valuator is reported only if its bit is set in the bitmap at `+0x60` (`0x568` to `0x580`). A value equal to the previous one is skipped unless the flags include `0x42` (`0x650`, `0x658`). Values are clamped to the descriptor's minimum and maximum (`+0x14`, `+0x18` of a 28-byte entry, `0x660` to `0x694`).
- **Grouping.** The last record's "more follow" bit is cleared unless bit 0 of the third argument is set (`0x6ac`, `0x730` to `0x740`), and one buffer is sent with `putnext` (`0x6d4`). With no records it is freed (`0x720`).
- **Allocation failure** logs "valuator events lost" (`0x778`) and returns.
- **What sets the mode byte.** `idevSetPtrMode` (`0x13f0`, request `0x80066921`) stores the whole first byte of its argument at `+0x68` (`0x1500`), after taking x and y axis numbers from the argument when bits `0x10` and `0x20` are set. Nothing else in `idev.o` writes `+0x68`. So whether bit `0x02` and bits `0x10`/`0x20` are set is decided by whoever sends that request.
- **What sets the per-valuator bitmap.** The library has an update helper, `idevUpdateBitArray` (`0x1740`), which applies a mask-and-value pair (32 bytes each); the request that carries the pair is the enable-valuators request (`0x8040690b`; the name and code come from `idev_ioctl_name`, `0x19bc`, and agree with the names in the module's strings). The bitmap itself is written by module code, not by the library.
- **Absolute versus relative.** `idevSetPtrMode` has no absolute/relative field. Relative handling lives in `idevTransformCoord` (`0xe0`): a per-valuator transform record's mode bits and the caller's flags `0x100`/`0x400` choose pass-through absolute, delta-from-previous, scaling and acceleration (`0x0f8` to `0x1b4`). `idevSetPtr` (`0x15dc`) forces absolute by passing `0x500`. Inferred reading of the flag meanings; the branches are established.

### 3. What `pushpointer "on"` means to Xsgi

- **Meaning** (established). `xdevDeviceControl` (`Xsgi` `0x101a8440`) compares the option name with "pushpointer" (`0x101a8494`) and stores a role byte in the device record at `+0x55`: "off" gives 0 (`0x101a8680`), "on" 5 (`0x101a86a8`), "exclusive" 7 (`0x101a8b28`). A device whose descriptor class string begins with "ptr" or "pointer" starts at 5, "ptrexcl" at 7 (`0x100e1650` to `0x100e1698`, `0x100e2390`).
- **Effect, only when the byte changes and the device is open** (established). If the new value equals the old one the routine returns (`0x101a86b0`); if the device's open flag (`+0x10`) is zero it returns (`0x101a86b8`, `0x101a86bc`). Otherwise it calls the device's cursor-attach hook (`simpleAttachCursor`, `0x100d2960`, called at `0x101a8724`) and then `coreAddDevice` (`0x10185420`, call at `0x101a8748`) for a nonzero role or `coreRemoveDevice` (`0x1014f960`) for off.
  - `simpleAttachCursor` sends, through the shmiq double-indirect I_STR (`0x80085107`), the set-pointer-mode request (`0x80066921`) with mode byte 2 for roles 0 and 4, `0x32` for 5 and `0x72` for 7, and the x and y valuator numbers from the device record (`0x100d29b4` to `0x100d2a2c`); then the set-cursor-axes request (`0xc0045109`, axes 3) so the kernel tracks the cursor from this device's type 0 records (`0x100d2a54` to `0x100d2a74`). Failures print "IDEVSETPTRMODE ioctl failed" and "QIOCSETCURS ioctl failed".
  - Reading the modes against `idev.o`: role 5 sets bits `0x10`, `0x20` and `0x02` in `+0x68`, so the module sends both pointer-position records (type 0) and valuator records (type 1). Role 7 adds `0x40`, which nothing in `idev.o` reads. Roles 0 and 4 set only `0x02`: valuator records, no pointer records. Established for the values; the consequence is read from the library.
- **Does it make the device drive the core pointer?** Yes for type 0 records (established): they go to `simplePointer`, which calls `corePointerEvent`, and `coreAddDevice` registers the device in the core pointer set. The primary pointer is set up the same way, `xdevAddDeviceToCorePtr` (`0x10237320`) calling the same control with "on" (`0x102373a8`).
- **Does it change whether XInput `DeviceMotion` reaches a client?** Not directly (established): XInput motion comes from type 1 records through `simpleValuator`, which skips the send only when the device's process-input procedure is `ProcessPointerEvent`. Nothing in the pushpointer path changes the device's process-input procedure (it only calls the attach hook and the core add and remove routines), so the role byte does not gate XInput motion. Inferred from the absence of such an assignment in that path; the assignments of `ProcessPointerEvent` elsewhere (for example `ProcXChangePointerDevice`, `0x1009edd0`) were not read. Indirectly, yes: the role byte is the only thing Xsgi uses to cause the mode byte `+0x68` to be set (see Observations).

### 4. Grab or select?

- **No grab is required** (established for the structure, inferred for the window). `ProcessOtherEvent` takes the grab path only when a grab is active and otherwise calls `DeliverDeviceEvents` (step 13). Selecting the device-motion class with `XSelectExtensionEvent` is the standard XInput way to get ungrabbed delivery. This agrees with the public XInput specification; `libXi` was not read at instruction level.
- **Which window gets it** (read in `GENERIC/Xsgi`): the window under the core pointer, as in the public XInput specification. `ProcessOtherEvent` (0x10201cc0) takes no grab and, when the device has no focus record (the word at +0x9c of the device is zero, 0x10202484 to 0x10202488), calls `DeliverDeviceEvents` (0x100e2e40, 1980 bytes) at 0x102022ac with the window in `a0` loaded from the global at 0x102c6004 (the delay slot at 0x1020248c; the word at offset 0x1c of the 152-byte object `sprite`, 0x102c5fe8), the event in `a1`, a stop window of 0 in `a3` and the device in `t0`. The only writers of that word are `CheckMotion` (0x1023a0cc), `PanoramiXCheckMotion` (0x101ee014) and `DefineInitialRootWindow` (0x100e0a98), and the first two store the result of `XYToWindow` (0x1024c4f0) called with the two words at 0x102c6008 and 0x102c600c, the one pointer position the server keeps. `DeliverDeviceEvents` starts at that window and walks up its parent link (the word at +0x18 of each window, 0x100e3018) until `DeliverEventsToWindow` (0x10184890, calls at 0x100e2f70 and 0x100e3130) reports a delivery or the stop window or the root is passed, testing the device's per-window event masks on the way. There is nothing device-specific in the start window. A client that selected `DeviceMotion` on a window the core pointer is not over (or inside) receives nothing, whatever the device's own position. Established for the argument chain and the walk; the meaning of the +0x18 link as the parent, and of the words at 0x102c6008 and 0x102c600c as the pointer's x and y, are Inferred from their use as `XYToWindow`'s arguments and the loop. With a focus record the call goes to `DeliverFocusedEvent` (0x10162260, call at 0x1020249c) instead, which was not read.

## Observations that bear on the reported symptom

These are readings of the code, not observations of a run.

- **Enable requests are not needed** (corrected; see [the stock Wacom module](#the-stock-wacom-module-and-the-attach-sequence)). Xsgi builds no enable-valuators or enable-buttons request, but the tablet module fills both bitmaps itself when the stream is opened. Established.
- **Xsgi sets the mode byte from `simpleAttachCursor`, which has two callers** (corrected). The earlier reading of this page found only the role-change caller in `xdevDeviceControl` and concluded the attach never runs for a config-only `pushpointer "on"`. That was wrong: the generic device-on handler (`0x1022ea00`, called from `simpleDeviceProc` at `0x100a55c0`) also calls the hook, see the next section.
- **The tracked values are readable without events.** `idevGetValState` (`0xf04`, the get-valuators request `0x40246906`) copies up to 8 values from the module's tracked array (`0xf30` to `0xf54`). A client that queries device state when the core pointer moves would see the tablet position change in step with the PS/2 mouse while no motion events are queued. That is consistent with the report; whether the client does this is not known.

## The stock Wacom module and the attach sequence

Added from the 6.5.30 Onyx2 module `usr/cpu/sysgen/IP27boot/wacom.o` (sha256 begins `e7a46650d1ebcce3`) and the same generic `Xsgi`. The IP30 copy has the same function boundaries and differs only in register choice (compared by disassembly listing). Addresses for the module are offsets into `.text`. Nothing here was run. The library search service was unreachable, so no published tablet-protocol or input document was consulted; the protocol statements below are read from the module's state machine.

**What the module sets itself.** `wac_open` (`0xb1bc`) allocates a 0x580-byte record and initialises the generic input record at its head: mode byte `+0x68` = 2 (`0xb4d8`: valuator records only, no pointer-position records), pointer axes `+0x70` = 0 and `+0x72` = 1 (`0xb4c8` to `0xb4d0`), 10 valuators and 16 buttons (`0xb4e4`, `0xb514`), pointer bounds `+0x74` to `+0x7e` all zero (`0xb4b0` to `0xb4c0`), and both enable bitmaps filled with ones (`0xb450` to `0xb48c`). Established. The module never calls `idevSetPtrMode` on its own: its only reference is in the ioctl handler `wac_wioctl` (`0xa7e4`, call at `0xae6c`), which runs when Xsgi sends the set-pointer-mode request. Established (all call sites listed from relocations). After the library call it also rewrites the x and y bits of its valuator bitmap: set for role 5 (mode `0x32`), cleared when mode bit `0x40` is set (role 7), so an exclusive pointer stops reporting x and y as XInput valuators (`0xaec0` to `0xaf54`). Established.

**What makes Xsgi attach.** `simpleAttachCursor` (`0x100d2960`) with a screen rectangle sends, in order, set-pointer-bounds (`0xc00c6923`, helper `0x101559e0`, call `0x100d2aac`), set-pointer (`0xc0086924`, `0x100d2b3c`), the scale transform (`0x102373f0`, call `0x100d2b48`), set-pointer-mode (`0x80066921`, `0x100d29f8`) and the cursor-axes request (`0x100d2a74`). ## Why a pointer record moves no cursor (Onyx2, IMPACT)

Question from a session running an Onyx2 guest with an IMPACT (MGRAS) head: a tablet attach succeeds, each type 0 record reaches `simplePointer` and then `corePointerEvent` (`a0` = `0x10324518`, `a1` = 349, `a2` = 249, `a3` = `0xe4e3a`, `a4` = `0x16e39`), the core pointer does not move, the board's cursor-position routine `MgrasPositionCursor` is never hit, and later PS/2 relative motion moves the cursor from the screen centre. Those observations come from an emulator run. They are not hardware evidence and they are not used as evidence below.

**Which Xsgi.** Established: the generic `usr/gfx/arch/GENERIC/Xsgi` is the server an Onyx2 with IMPACT runs. The 6.5.30 media holds only two server binaries, that one and `usr/gfx/arch/IP22NG1/Xsgi` (the Indigo2 NG1 build, 13 NG1 strings; the generic one has none). `usr/bin/X11/Xsgi` links to `/var/arch/X11/Xsgi`, which links to the generic binary. The IP27 and IP35 graphics directories (`IP27GR5`, `IP27KONA`, and the rest) hold only `libGL.so` and `libGLcore.so`. The generic server has no MGRAS string and needs only `libm` and `libc`; its `dlopen` callers are the font scanner, the speech library loader and the GLX and PEX extension loaders (`scan_font`, `GLXLoadExtension` `0x101b6b40`, `PEXLoadExtension` `0x1017466c`). So no board-specific X server or dynamic DDX exists on this media. The board-specific part of the cursor path is in the kernel graphics driver, below.

### What `simplePointer` and `corePointerEvent` do

`simplePointer` (`0x101d90b0` to `0x101d91ec`, read in full) takes a record and a device. Its branches, in order (established):

1. A skip counter in the device's private record (byte `+0x74`). While it is above zero a record is dropped: when record flag bit 1 is clear, until the record's tick is 11 or more ahead of the stamp in the global at `0x102e764c` (`0x101d919c` to `0x101d91ac`); when bit 1 is set, the counter just drops by one (`0x101d90ec`, `0x101d90f0`). The counter is raised and the stamp taken only after the screen-change check below returned non-zero (`0x101d9180` to `0x101d918c`), so it only matters after a screen change.
2. A record whose flag bit 1 (`0x02`) is set is ignored (`0x101d9110`, `0x101d9114`). `idevGenPtrEvent` copies that bit from its caller's flags (`idev.o` `0x384`, `0x390`); the stock tablet module passes `0x100`, so it is clear for the tablet (inferred for the module, established for both ends of the call).
3. Flag `0x10` copies the record's x short (`+8`) into `coreX`, flag `0x20` copies the y short (`+10`) into `coreY` (`0x101d9128` to `0x101d9144`). `idevGenPtrEvent` sets `0x10` and `0x20` for the axis it moved and `0x04` or `0x08` when that axis was clamped at a pointer bound (`idev.o` `0x258`, `0x32c`, `0x248`, `0x310`). So `a1` and `a2` are the record's position only if those flags were set; otherwise they are the previous `coreX` and `coreY`. Which applies in the run is unknown.
4. Only when a clamp bit (`0x0c`) is set does it call `xdevScreenChange` (`0x101b8140`, call at `0x101d915c`); a non-zero result ends the call with no `corePointerEvent`. For the observed calls this was passed or not needed.
5. Otherwise it calls `corePointerEvent(device, coreX, coreY, tick * 10)` (`0x101d91c4` to `0x101d91e0`).

`corePointerEvent` (`0x100a9fb0` to `0x100aa0bc`, 268 bytes, read in full) has no branch that skips the move (established):

- If the global behind `screenIsSaved` is zero it first calls `SaveScreens(1, 0)` (`0x100a9fc4`, `0x100aa0a4`), which the name suggests ends a blanked screen (inferred from the name and arguments).
- It stores `a0` in a global at `0x102ca578` when it differs (`0x100a9fe0`, `0x100a9fe8`). Nothing else uses `a0`. The device is not tested against the core pointer here.
- It stores `a1` and `a2` into `coreX` (`0x102e75f8`) and `coreY` (`0x102e75fc`) (`0x100a9ff8`, `0x100a9ffc`).
- It builds a motion event of type 6 on its stack: `a3` at byte `+4` (time), `a1` and `a2` as shorts at `+0x14` and `+0x16` (the root position) (`0x100a9ff0` to `0x100aa00c`). The time is copied; nothing orders it against an earlier event here.
- When redirection is enabled (global `0x102c5f78`) and bit 0 of `0x102c5f8c` is set, it records the event's address in a small table at `0x102d0bb0 + 0x1530`, index `0x102c5f74` (`0x100aa010` to `0x100aa070`). That is bookkeeping for a client that redirects pointer events; it does not drop the event.
- It always ends by calling word `+4` of the core pointer device record (`corePtr`, `0x102ca4a8`) with the event, the device and a count of 1 (`0x100aa078` to `0x100aa080`).

Answers to the candidates for question 1, from the code above: the "is this the core pointer" test does not exist in `corePointerEvent`; no timestamp or ordering test exists in it; no read of shmiq or `qcntl` cursor state exists in it or in `simplePointer`; the screen-change test is in `simplePointer` (step 4) and was passed; a grab or freeze can only act after the call, in the procedure at `+4`. Established.

**Where the call goes.** `RegisterPointerDevice` (`0x101c73a0`, called from `InitCorePointer` `0x10091800` at `0x10091974`) stores one of two procedures at `+4` and `+8` of the core pointer record: `ProcessPointerEvent` (`0x101f7aa0`) when the global at `0x102c5d44` is zero, `CoreProcessPointerEvent` (`0x10223ac0`) otherwise (`0x101c73c8` to `0x101c7410`). The first is a wrapper that calls the second (`0x101f7b10`) and then does keyboard-extension state and LED work that was not read. Which one is live depends on that global at run time: unknown. If the device were frozen by a grab, word `+4` would hold an enqueue routine instead (inferred from the standard device-record layout: `+4` process, `+8` real, `+0xc` enqueue; `RegisterPointerDevice` sets `+4` and `+8` alike).

`CoreProcessPointerEvent` for a type 6 event (`0x10223bc4`, `0x10223bc8`) calls `CheckMotion` (`0x1023a050`, call at `0x10223e44`). The time handling before it (`0x10223b38` to `0x10223b74`, `0x10223d14` to `0x10223d40`) only rewrites a time that is behind the last event; it never drops the event. `CheckMotion` with an event and the global at `0x102c5fc8` clear (named by its use as the event-replay flag: inferred):

Established for all of that. So the server's own pointer position is updated, and it is updated before any grab is consulted. Xsgi does not draw the cursor on this path. It reaches the hardware only through the set-cursor-position hook, which fires on clamping, on warps and at attach. ### Who moves the cursor on screen

Established, in the IP27 objects:

1. **Xsgi to the queue driver.** `ddxSetCursorPosition` (`0x1022a4c0`) sends the stream-ioctl request (`0x5308`) on the `/dev/shmiq` descriptor with command `0xc004510a` and a four-byte x and y (`0x1022a4dc`, `0x1022a52c`, `0x1022a530`), or `0xc004510d` when a multi-screen flag (global `0x102c5cac`) is set and two screen-number globals (`0x102c5c10`, `0x102c5c40`) are equal (`0x1022a4e4` to `0x1022a504`). In the queue driver the first stores x and y in state `+0x2c` and `+0x30`, clears state `+0x198` and calls `positionCursor` (`shmiq.o` `0xc9c` to `0xcb8`); the second sets `+0x198` to 1 and calls `positionCursorAll` (`0xc74` to `0xc8c`). `simpleAttachCursor` (`0x100d2960`) calls it with the attach rectangle's origin (`0x100d2acc`) before it sends set-pointer-mode and the cursor-axes request, but only when a rectangle was passed and only when the device record's link value at `[[device] + 0x7c] + 0x18` is above zero (`0x100d299c`); otherwise it returns 1 having sent nothing. That value was not identified: unknown. A successful attach return therefore does not show that the cursor-axes request was sent.
2. **Which input links drive the kernel cursor.** The cursor-axes request (`0xc0045109`, from `simpleAttachCursor` at `0x100d2a54`, payload slot and axes `3`) is handled in `shmiq_wput` at `0xa3c`: it clears all but the low two bits of the slot's flag word (link `+0x2c`) and ORs in the axes. An empty slot gives an error.
3. **Which stream is the display.** Request `0x80045106` (sent by `ddxChangeToScreen` `0x10206210`, call at `0x102062d4`, payload the per-screen slot at `[screen] + 0x48`; `SetRectOffsets` `0x101e4320` also sends it, payload not read) stores the slot in the queue driver's cursor-stream field (state `+0x44`, `shmiq_wput` `0xb4c` to `0xb70`). It is refused when that slot has no link. `GfxProto` answers the same handshake as any other lower stream (`gfx.o` `0x1788` to `0x17b4`: the reply carries the reversed magic, and the two slot shorts are stored at private `+0x30` and `+0x32`), so the graphics stream sits in one of the 32 slots next to the input devices. Inferred from that handshake: Xsgi links the graphics stream under the queue driver; the link call itself was not read.
4. **Records move it in the kernel.** `copyEventData` (`shmiq.o` `0x1e4`), for each record: finds the slot from the record's second short (`0x224`), requires slot below 32 and a link (`0x22c` to `0x244`), reads the link's flag word (`0x24c`) and, if it is non-zero and the record's type byte is 0 (`0x25c`, `0x260`), copies x into kernel state `+0x2c` when flag bit 0 is set and y into `+0x30` when bit 1 is set (`0x2d4` to `0x2ec`). After the whole batch, if any record qualified, it calls `positionCursorAll` (`0x9c`) when state `+0x198` is non-zero and `positionCursor` (`0x0`) otherwise (`0x2a4` to `0x2f8`). The same routine stamps every copied record's first word with the tick counter (`0x1e4`, `0x274`).
5. **Kernel to the graphics stream.** `positionCursor` takes the link named by state `+0x44` (`0x0` to `0x10`), returns silently if there is none (`0x1c`), allocates a 0x18-byte block (`0x28`), makes it a priority protocol message (type byte `0x83`, `0x4c`) holding the four characters "SHIQ" and the x and y from state (`0x58` to `0x78`), and calls the put routine of the queue below the link's lower stream head (`0x7c` to `0x8c`). `positionCursorAll` does the same for every link whose `+0x30` word is 1 (`0xd8`, `0xdc`), and for a link other than the cursor-stream slot first adds the link's offsets (`+0x34`, `+0x38`) and wraps at its sizes (`+0x3c`, `+0x40`) (`0x154` to `0x19c`).
6. **Graphics stream to the board.** `GfxProto` (`gfx.o` `0x173c`) accepts that magic (`0x1764`, `0x1774`), takes the stream's private record, and returns the message freed with no action when the record's `+0x20` word is zero (`0x17bc` to `0x17c0`, `0x1814`). Otherwise it calls word `+0x30` of that table with the board pointer from private `+0x28` and the x and y (`0x17c8` to `0x17d4`). In `mgras.o` the first data object is a 28-entry table of board routines, and its `+0x30` entry is `MgrasPositionCursor` (data relocation at `.data` `0x30`). `MgrasPositionCursor` is at `mgras_retrace.o` `0x14cc`; it records x and y at board state `+0x190` and `+0x194` and writes the cursor position words in the board's register window (`0x1520`, `0x152c`, `0x15cc` to `0x15dc`). That the table in `mgras.o` is the one a graphics stream's `+0x20` word points at on an IMPACT head was not traced: inferred from the matching entry offset and the routine's signature (board, x, y).

So yes: Xsgi can let the kernel move the cursor and does by default for any input link with cursor axes set. Reading the position back from the shared queue: none found in the routines read. `simplePointer` takes the position from the record itself, not from the queue's cursor state, and neither `corePointerEvent` nor `CheckMotion` reads any queue header field. The kernel's cursor x and y live in the driver's private state and are written only by `copyEventData` and the two position requests. A search of the rest of Xsgi for readers of the shared queue's own cursor fields was not done: unknown.

### What would leave `MgrasPositionCursor` unhit

None of these needs the tablet records to be malformed, since they reached `simplePointer`. Each is a point on the chain in the previous list that a run can check (all inferred as causes; the reading of each test is established):

- The slot's flag word (link `+0x2c`) is zero because the cursor-axes request was never sent or failed. `simpleAttachCursor` sends nothing when its link value (item 1) is not above zero, and prints "QIOCSETCURS ioctl failed" when the request fails.
- State `+0x44` names a slot with no link, or a slot that is not the graphics stream, so `positionCursor` returns at `0x1c` or sends the message to an input device's module. Request `0x80045106` sets it; the initial value and whether Xsgi's `SetRectOffsets` or `ddxChangeToScreen` ran for this screen were not read.
- The message arrives but `GfxProto` frees it at `0x1814` because the stream's table word is zero.
- `MgrasPositionCursor` runs under another address than the breakpoint, or the board's table entry is not that routine. The session also says PS/2 motion moves the cursor with no hit at that routine, and the same chain serves a PS/2 link (it also needs the cursor-axes request and a `type 0` record). So either the PS/2 cursor is moved by something other than this chain, or the breakpoint is not on the live copy of the routine. This point decides between "tablet link misses a precondition" and "chain broken for every device", and the checks below separate them.

**Attach as a discriminator.** `simpleAttachCursor` calls `ddxSetCursorPosition` at attach with the rectangle origin (item 1), which should itself run `positionCursor` once. If that never reaches `MgrasPositionCursor` either, the chain is broken for every device, not just the tablet.

### The two operands

- `a3` = `0xe4e3a` is the record's tick count multiplied by 10 (`0x101d91d4`: `t0 * 4 + t0`, then doubled in the call's delay slot at `0x101d91e4`). It is a time in milliseconds only if the tick is 10 ms (the usual 100 Hz clock: inferred, the multiplier is established). The tick is the kernel's clock counter, loaded once per batch and written into word 0 of every copied record (`shmiq.o` `0x1e4`, `0x274`). `0xe4e3a` is 937 530 ms, about 15.6 minutes after the counter started. The time is stored into the event at `+4` and is not compared with anything in `corePointerEvent`.
- `a4` = `0x16e39` is not an argument. `corePointerEvent` reads only `a0` to `a3` before writing them (fact sheet: argument registers read before written are `a0`, `a2`, `a1`, `a3`). `a4` is a leftover register from the caller: `$t0` still holds the record's word 0 (`0x101d91c8`, `lw t0, 0(s0)`). `0x16e39` is 93 753, and `93 753 * 10 = 937 530`, which matches `a3` exactly. Established arithmetic; the reading as a tick count follows from the stamp store in `copyEventData`.
- `a0` = `0x10324518` is the device object that `simplePointer` loaded from its second argument (`0x101d90b0`, `lw t2, 0(a1)`; `0x101d9168`, `0x101d91c0`). Its only use in `corePointerEvent` is the compare and store at `0x100a9fe0` and `0x100a9fe8`. That it is the device record that the pointer-handler table in the device holds was not checked against `processShmiq`: inferred.

- `0x102062d4` and `0x101e4320`: the slot sent with `0x80045106` and the result.

- `shmiq.o` `0xa3c` (cursor-axes handler; the written flag word is link `+0x2c`), `0xb4c` (cursor-stream request; the stored slot is state `+0x44`), `0x2cc` (record qualifies), `0x2a8` and `0x2f8`/`0x2b0` (call into `positionCursor` or `positionCursorAll`), `0x1c` (no cursor link), `0x8c` (send to the graphics stream).
- `gfx.o` `0x1774` and `0x17d4`: accepted magic; the call of the board routine.
- `mgras_retrace.o` `0x14cc`.

Run the same breakpoints with a PS/2 motion: whichever one first stops being hit for the tablet and not for PS/2 is the answer. If the PS/2 motion also never reaches `shmiq.o` `0x2cc`, the cursor is not moved through this chain in that run.
