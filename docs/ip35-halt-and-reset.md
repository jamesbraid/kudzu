# IP35 kernel halt, power-off and reboot paths

How the IRIX 6.5.30 IP35 kernel (`6.5.30/unix.IP35`, linked 64-bit image with a symbol table and DWARF) takes the machine down: the controller commands it sends, when it falls back to a local power-off, and which hardware resets it writes. Everything below was read in full in that image unless a line says otherwise. `gp` is 0xc000000001643770. Where the symbol table gives a routine no name or a misleading one, the address is used.

## Power-off request and the controller loop

- `uadmin` (`6.5.30/unix.IP35`, address 0xc0000000002f95bc, 680 bytes): command 0x100 with function 9 stores 1 in the kernel word `power_off_flag` (0xc000000001646510, `gp`+0x2da0) and does nothing else. Function 9 given to `mdboot` (0xc0000000002af460, 204 bytes) stores the same 1 before it calls the common stop routine at 0xc0000000002af52c. No other store to that word exists in the image (searched for every `gp`-relative access to offset 0x2da0 and every literal-pool copy of the address). Established.
- `prom_reboot` (`6.5.30/unix.IP35`, address 0xc0000000002afa98, 216 bytes), as each processor runs it (section below on which processors reach the loop): when `panicstr` (0xc000000001646250) is zero, which is every orderly reboot, halt and power-off, it goes straight to `prom_reinit` (`6.5.30/unix.IP35`, address 0xc0000000000404dc, 60 bytes), which sends the local controller command 0x2005 and spins when `power_off_received` (0xc00000000163b784) is set, and otherwise ends in the restart request 0x0ead0030 to the routine at 0xc000000000041240 (through `he_arcs_restart`, which `prom_reinit` calls). When `panicstr` is set it asks `kopt_find` for the PROM variable "rebound": a nonempty value means reboot when its first character is `y` and stay otherwise; with no value the kernel word `reboot_on_panic` (0xc00000000163c76c) decides, and a `reboot_on_panic` of 2 stays 2. For "stay", the master logs "[Press reset to restart the machine.]" and calls `cpu_waitforreset` (0xc000000000077a78), and every other processor spins in a branch to itself, so those never reach the reset loop. For "reboot", every processor (the master after logging "Restarting the machine...") calls `prom_autoboot` (`6.5.30/unix.IP35`, address 0xc0000000000404c0, 28 bytes), which wraps `he_arcs_reboot` and so runs 0xc000000000041240 with 0x0ead0040, and then `prom_reinit`. Established.
- `prom_reinit` (`6.5.30/unix.IP35`, address 0xc0000000000404dc, 60 bytes) sends the local controller command 0x2005 through `elsc_pwr_off` and then spins when `power_off_received` is set, and otherwise enters `he_arcs_restart` (`6.5.30/unix.IP35`, address 0xc0000000000413b8, 32 bytes). Established.
- `he_arcs_reboot` (`6.5.30/unix.IP35`, address 0xc0000000000413d8, 32 bytes) and `he_arcs_restart` pass 0x0ead0040 and 0x0ead0030 to the unnamed routine described below and return its result. Established.

The unnamed 376-byte routine at 0xc000000000041240 (no symbol covers it; `he_arcs_set_vectors` at 0xc000000000041234 is a 12-byte setter just before it) was read in full. It ORs 0x100 into its argument when `panic_level` is zero, then for every compact node (count in `maxnodes`) stores the argument as a 64-bit word at hub offset 0x608010 through the remote register window (pool word `gp`+0x898 is 0x9200000001e10000, displacement -0x7ff0, NASID shifted left 33). It waits one second. If `reboot_on_panic` equals 2 it initialises the controller state and sends command 0x2001 (`elsc_system_reset`) and returns on success; on failure it prints a message and does the register writes of `ni_reset_port`. Otherwise every processor that enters the routine ends in the same loop; they differ only in when they start (corrected after a second read: an earlier version of this note said the other processors only delay). The loop's test, at 0xc00000000004131c, is "this processor's number equals `master_procid` (halfword at gp-0x63f0, 0xc00000000163d380), or at least one delay has passed". The master therefore starts at once; every other processor first sits out one three-second delay (0x2dc6c0 microseconds) and then joins. Each pass: when `power_off_flag` is nonzero the processor calls `get_elsc` (0xc000000000065240, the controller state of its own node) and `sc_power_down_all`; when it is zero it calls `ni_reset_port`. Then it waits three seconds and goes round again. The return value is discarded and no counter, deadline or reply leaves the loop, so `ni_reset_port` is repeated every three seconds by every processor that got here, not called once. The paragraph below on how processors reach the routine says which those are. Established.

- `sc_power_down_all` (`6.5.30/unix.IP35`, address 0xc0000000000d0190, 136 bytes) reads the doubleword at 0xffffffffffffc400 (the per-processor page; it holds the node's platform data pointer, inferred from the caller of `router_map_init` below) and the word at offset 0x8c68 in it. If that word is not positive it calls `sc_power_down` (`6.5.30/unix.IP35`, address 0xc0000000000d0144, 76 bytes): `sc_command_interp` with destination type 0 (the local controller), rack field 0x3ff, bay field 0x3f and the command text `* pwr d`. If it is positive it calls `elsc_partition_get`, takes the low byte of the result as a signed number *p*, and calls `sc_command_interp` with destination type 1, the same rack and bay fields, and the text `p <p> pwr d`. The destination word the interpreter builds is `type << 28 | rack << 18 | bay << 12`: 0x0ffff000 for type 0 and 0x1ffff000 for type 1; the message adds the task number 3. Established.
- `sc_command_interp` (`6.5.30/unix.IP35`, address 0xc0000000000cfef8, 588 bytes) waits for the reply through `sc_command_kern` (`6.5.30/unix.IP35`, address 0xc0000000000d5568, 92 bytes), whose receive wait is 2,000,000 (microseconds, inferred from the delay routine's unit). A send or receive failure returns -0x64 and the text is not retried inside the routine. Established.
- `elsc_partition_get` (`6.5.30/unix.IP35`, address 0xc0000000000cf7b8, 248 bytes) sends command 0x0009 (task 6) to the local controller (destination 0x0ffff000) and returns the integer the reply carries (read through `sc_interpret_resp` as a 32-bit integer), or one of -0x64, -0x67, -0x70 for open, build and parse failures. A negative result is not tested by `sc_power_down_all`, so a failure prints a negative number in the command text (the low byte of -0x64 is -100). The partition identifier therefore comes only from the controller reply to command 0x0009; neither the PROM-written scratch words nor KLCONFIG's partition field are read on this path. Established (no other source is read between the test and the send).

## What decides between the local and the controller form

The word tested at offset 0x8c68 is a count kept by `router_map_init` (0xc000000000051764, 436 bytes), called once per node from `init_platform_nodepda` (0xc00000000004ddcc) with that node's platform data. It zeroes the count (at 0x10000 less 0x7398 from the structure) and then, for every compact node that is not a PE brick (the node-type test is the 0xf000 mask of the node-info word equalling 0xc000), walks the node's KLCONFIG board list for boards of class 0x31 (found by `find_lboard_class`). For each such board whose flag byte (offset 9) has bit 2 clear it appends a 16-byte entry at offset 0x8868 + 16*count: the 8-byte value at board offset 0x18, the 16-bit value at 0xe and the byte at 0xa. `router_map_get` (0xc000000000051918, 108 bytes) searches those entries. Established.

So the kernel uses the local `* pwr d` form exactly when it found no router board of that kind in KLCONFIG, and the controller form `p <id> pwr d` whenever at least one is listed. It never probes for a rack controller, and it has no timeout or retry limit on the controller form. That the class 0x31 is a router and that bit 2 of the flag byte means "device" are inferred from the board layout in published headers; the code only tests the numbers. Inferred.

The emulated runs that show the controller form on topologies with a router and the local form on those without (an Origin 3200 and an Onyx 3000 with two bricks) are consistent with this; they are model behaviour, not hardware.

## Reboot and port reset

- `ni_reset_port` (`6.5.30/unix.IP35`, address 0xc000000000041534, 28 bytes) writes 1 to the doubleword at 0x9200000001680010 and then 6 to 0x9200000001680008 (pool words at `gp`+0x8a0 and `gp`+0x8a8). Those are the local-form addresses of hub offsets 0x680010 and 0x680008 (network interface reset enable and port reset). The only other users of the two pool words are the failure path of the reset command above, which performs the same two stores. Established. A search of the instruction stream for the remote-window form of either register (a `lui` of 0x68, or a pool word holding the remote form) found none; an address built another way would not be found. Inferred that no other kernel path writes them. Each write goes to the hub of the processor that makes it and does not name a remote node. Every processor that reaches the reset loop makes them (see the section on which processors reach it), so each node with an online processor is written, not one node. Established. In the 6.5.30 kernel the only writes to hub offset 0x608010 found are the per-node stores above (the pool word search covered 0x9200000001e10000-based addressing only). Inferred.
- `router_set_fences` (`6.5.30/unix.IP35`, address 0xc00000000004314c, 312 bytes; also in `ip35-router.md`) only clears bits in the router's register 0x10 and in each live port's register at 0x18 (never sets), for ports that came up. The kernel therefore only narrows whatever the PROM programmed. Established (re-read 0xc00000000004314c).


## Which processors reach the reboot loop

Every processor that is online. The stop is a cross-call to each of them and each then runs the same routine. All of it was read in full in the linked image.

- `mdboot` (`6.5.30/unix.IP35`, address 0xc0000000002af460, 204 bytes) picks the routine every processor will run and passes it, with its own second argument, to the common stop routine at 0xc0000000002af52c (400 bytes, no symbol). Functions 0, 2, 3 and 9 pass `prom_reboot`; functions 2 and 3 first log "Sorry, no interactive reboot." and "Sorry, no standalone exec." at `cmn_err` level 4, and function 9 first stores 1 in `power_off_flag`. Function 1 passes `prom_autoboot`. The callers are `dumpsys` (two sites, the panic path), `icmn_err_tag` (two sites), `sn1_sc_versioncheck` and `phost_reboot`. Established.
- The common stop routine at 0xc0000000002af52c (no symbol; read in full) first, when `maxcpus` (0xc000000001644c14) is 2 or more, logs "<Power off|Reboot> started from CPU <n>" at `cmn_err` level 6. It then takes a lock, stores the routine to run at offset 0x1100 of a global block, sets an arrival count to 1 and calls each entry of the null-terminated `io_halt` table (0xc0000000015400f8) on the calling processor. It walks the processor table (`pdaindr`, 0xc000000001647568; 16-byte entries, the processor number in the first word and a data-area pointer in the second) up to the larger of `maxcpus` and `nmi_maxcpus`. For each entry that is not -1 and not the calling processor it adds one to the count and calls `cpuaction` with that processor, the handler at 0xc0000000002af6bc and the flag 1. Last, the caller runs the handler itself.
- `cpuaction` (`6.5.30/unix.IP35`, address 0xc000000000294ae0, 312 bytes) runs the function directly when the target is the calling processor, and otherwise calls `nested_cpuaction` (`6.5.30/unix.IP35`, address 0xc0000000002949d4, 268 bytes), which takes a lock, calls `sendintr` (0xc000000000060824) and unlocks. The target is therefore interrupted; the request queue itself is described only by the callee names. Established.
- The handler at 0xc0000000002af6bc (no symbol; read in full) takes the same lock and subtracts one from the arrival count. A processor that is not the master (its number differs from the halfword at offset 0x428 of the pointer held in `masterpda`, 0xc000000001645f88) then calls the stored routine at once. The master waits until the count reaches 0, in turns of `us_delay` 100,000 with a console buffer flush each turn, or until a deadline of five times `timer_freq` (0xc000000001644c94) counts of the hub clock at 0x9200000001030100, whichever comes first, and then calls the stored routine too. So the routine runs on every processor; a processor that never takes the interrupt costs the master only the wait. That `masterpda` and `master_procid` name the same processor is not shown by code: the two words are never compared. The clock count's unit is taken to be the clock's own.
- `panicspin` (`6.5.30/unix.IP35`, address 0xc0000000002af314, 220 bytes) is where the other processors sit after a panic: it loops calling `doactions` with a 500 microsecond `us_delay` between turns, so a processor there takes the cross-call and joins. A processor that cannot take the interrupt is not reached, and nothing waits on it past the master's deadline. Established.
- On a multi-node machine this means the scratch-2 stores at the top of 0xc000000000041240 are made by every processor, each over all nodes with the same value. Every processor then repeats `ni_reset_port` on its own node's hub (the local-window address names the hub of the executing processor): the master from about one second, the others from about four seconds, then every three seconds. A node with no online processor gets no write; a node with four processors gets four writers on the same two registers. With `reboot_on_panic` at 2 every processor instead sends 0x2001 to its own node's controller and returns. This follows from the entries above.

## Link errors at run time

How the kernel treats a NUMAlink link that fails or recovers after boot.

- `hubni_eint_init` (`6.5.30/unix.IP35`, address 0xc00000000005824c, 260 bytes) connects the only link-state interrupts the kernel has: level 126 for a node's own network interface errors (`hubni_eint_handler`, `6.5.30/unix.IP35`, address 0xc00000000005909c, 36 bytes) and levels 103 and 104 for "Remote NI interrupt" (`hubni_rmteint_handler`, `6.5.30/unix.IP35`, address 0xc0000000000590c0, 36 bytes). There is no link-up interrupt and no handler that re-reads the topology. Established for the connections.
- `hubni_error_handler` (`6.5.30/unix.IP35`, address 0xc000000000059064, 56 bytes) passes the node's own number, a description string and a flag to the report routine at 0xc000000000058ea0. Established.
- The report routine at 0xc000000000058ea0 (no symbol; read in full) reads the node's NI error word (hub offset 0x680100, through the remote window at 0x9200000001e80100). If an error bit in 0x001fffffff000000 is set and `part_id` is positive it calls `ni_port_down_reset` and returns: a link reset caused by another partition is tolerated. With `part_id` zero it logs "Detected a link reset due to other partition reset" and returns when bit 52 of the error word ("Detected a link reset") is set and the NI word at 0x680010 is zero. Every other case is fatal, including an interrupt with no error bit set: it masks interrupts, sets the node panic flag, prints the NI and router state, writes "Fatal NUMAlink error: NI error detected by %s NASID %d" to the error log, enters panic mode and then, for the node's own interrupt (the flag argument is 1), logs "Fatal NUMAlink error." through `cmn_err` level 0 and returns (`bnez` at 0xc000000000058fdc, `jal` at 0xc000000000059004); for the remote interrupt (flag 0) it calls `panicspin` (`jal` at 0xc000000000058fe4), which spins and does not return. That level 0 is not fatal was not checked.
- `ni_port_down_reset` (`6.5.30/unix.IP35`, address 0xc000000000058af4, 176 bytes) returns at once when `part_id` is not positive. Otherwise, when bits 2:1 of the NI status word (offset 0x680000) read 2, it polls up to 1,000 times with `us_delay` 200 for bit 1 to set; it then reads the clear word (0x680120), always stores zero to the error word (0x680100), and repeats the read and the store only while the reads keep showing error bits. Established; the exact sequence, and what clears the level-126 interrupt after a tolerated reset, are in [What clears the NI error interrupt after a tolerated link reset](ip35-hub-errors.md#what-clears-the-ni-error-interrupt-after-a-tolerated-link-reset).
- `part_id` (`6.5.30/unix.IP35`, address 0xc000000000496400, 8 bytes) is `move v0,zero` in this image, as are `part_from_addr`, `part_from_region` and `nasid_to_partid` after it; the routines that allocate pages for a partition panic. The partition branches above are therefore never taken in `unix.IP35` as linked; what a partitioning build links in was not read. Established.
- `check_ni_errors` (`6.5.30/unix.IP35`, address 0xc000000000059040, 36 bytes) passes the caller's node to a worker at 0xc000000000058ba4. Its callers are `hubpi_eint_handler`, `hubii_eint_handler`, `dobuserre` and `kl_panic_setup`. Established.
- The worker at 0xc000000000058ba4 (no symbol; read in full) makes the same decision as the report routine, with its own messages ("Fatal NI error interrupt on NASID %d", one line per set error bit, "Another node detected a fatal NI error"), and on its fatal path calls `protected_broadcast` (0xc000000000060c04) with 103 and then 104. That the broadcast raises the "Remote NI interrupt" levels on the other nodes follows from the matching numbers only.
- `ni_llp_error_monitor` (`6.5.30/unix.IP35`, address 0xc00000000005b384, 300 bytes) and `ii_llp_error_monitor` (`6.5.30/unix.IP35`, address 0xc00000000005b31c, 104 bytes) only add link-level error counts to a per-node block (sampled by `hub_error_count_update` every 100 ticks once `syssgi` enables it) and log one warning when a high count field is nonzero. They act on no link. Established.
- `probe_routers` (`6.5.30/unix.IP35`, address 0xc000000000051bb4, 224 bytes) has one caller, `sn0_error_dump` (`6.5.30/unix.IP35`, address 0xc00000000005c0ac, 456 bytes), so a router is probed afresh only in the error dump after a fatal error. `router_init` (`6.5.30/unix.IP35`, address 0xc000000000043500, 1296 bytes) has one caller, `io_xswitch_widget_init`, run at boot; `xtalk_device_powerup` (`6.5.30/unix.IP35`, address 0xc000000000097c3c, 64 bytes) can call `io_xswitch_widget_init` again for one widget, but no direct caller exists and who reaches it at run time is not established. `router_poll_ticks` and `p_routertick` are read only in `router_init` and `capture_router_stats` (`6.5.30/unix.IP35`, address 0xc000000000043284, 196 bytes; user statistics). No periodic rediscovery was found, from the absence of callers, searched by `jal` target and by `gp`-relative and literal-pool references. Inferred.

## An I/O brick that is off at boot

What the kernel does when the C-brick's I/O brick is powered off or held in reset. The PROM side is not covered here.

- `klhwg_add_all_xbows` (`6.5.30/unix.IP35`, address 0xc0000000000737b4, 280 bytes) builds the crossbow vertex for a node from the KLCONFIG board the PROM left, through `klhwg_add_xbow` (`6.5.30/unix.IP35`, address 0xc000000000072f34, 692 bytes), which reads only the node class word and board fields. The kernel does not probe the link to find an I/O brick. If the PROM listed no crossbow board for a hub, the board search returns nothing, the loop ends and nothing on that path logs or panics; no hub-to-widget wiring exists and nothing attaches below it. Established for these routines. That the PROM leaves no board when the I/O brick is down is the PROM's behaviour and was not read.
- `assfail` (`6.5.30/unix.IP35`, address 0xc0000000000619f4, 1084 bytes) is called by two assertions in the set-up of the system-critical graph on the base-I/O crossbow and bridge vertices (call sites 0xc00000000004cd18 and 0xc00000000004cd30, in a static routine the symbol table folds under `scsi_ctlr_nums_add`), and the caller branches on afterwards (0xc00000000004cd20, 0xc00000000004cd38). The same routine wants a base-I/O console vertex; with none it logs "sys_critical_graph_init: baseio_console_vhdl not set" at `cmn_err` level 4 (site 0xc00000000004cf5c) and returns. These checks log and continue, by this reading: `_assfail` (0xc0000000002af970, 296 bytes) prints "assertion failed cpu %d: ..." and the registers, enters and leaves panic mode and returns, with no panic call on the path read, but its `kdebug` word was not followed and `cmn_err` level 4 was not shown to be non-fatal in every configuration. Inferred.
- If the PROM did list the crossbow but its link is dead when the kernel runs, the first probe is `xbow_attach` (`6.5.30/unix.IP35`, address 0xc000000000097fe0, 776 bytes): it maps the crossbow registers through `xtalk_piotrans_addr` and, for ports 8 to 15, `xbow_widget_present` (`6.5.30/unix.IP35`, address 0xc0000000000987a0, 100 bytes) reads the identification word at +4 and a port word at 0x13c over the link, with no fault guard in either routine. What a failed uncached read does (a Hub I/O-interface error interrupt, the processor's bus-error exception, or both) was not established. `hubii_eint_handler` (`6.5.30/unix.IP35`, address 0xc00000000005b17c, 416 bytes) logs "Hub %d to Xtalk Link failed (II_ECRAZY) Reason: ..." at level 0, runs the CRB and PRB handlers (the PIO-write one says "cleaning up and continuing") and returns, so that path continues. `dobuserre` (`6.5.30/unix.IP35`, address 0xc00000000005c2a0, 1352 bytes) classifies a bus error and can call `kl_panic`; which branch a kernel read of a dead widget takes was not followed. Unverified: whether the kernel panics or continues in this case.

## Open points

- What the controller does with `p <p> pwr d` when no rack controller exists: unknown, no kernel path reacts to it.
- Whether the machine's firmware clears `power_off_flag` or the router map on a partitioned system: unknown, not read.
