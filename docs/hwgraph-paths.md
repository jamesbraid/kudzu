# Hardware-graph path and edge names in the 6.5.30 kernels

Which names the 6.5.30 kernels put into the hardware graph, where each one is added, and which path shapes each machine builds. The full list is [inventory/hwgraph-adds.tsv](inventory/hwgraph-adds.tsv), generated by [tools/hwgraph_sites.py](../tools/hwgraph_sites.py) from the three linked kernels `6.5.30/unix.IP27`, `unix.IP30` and `unix.IP35`. Each row gives the callee, the name, the routine that makes the call, and the site address in each build that has it.

Grades: **established** means the routine's entry was read in the binary and the argument role is taken from that code; it is a grade of the argument roles below, not of any table row. **located** means the site was found and the name was read from the image's own data at the address the argument resolves to; the routine containing the site was not read. **unresolved** means the argument is not a literal in straight-line code (it is set at a join, loaded through a computed base, or copied from another register). The reason column text names the scan step that lost the value, not the program's cause: most unresolved names are text formatted into a stack buffer by `sprintf`, and the table does not record the format string. No row is graded established yet.

## The add routines and their name arguments

Established from the entry code of the IP27 image:

- `hwgraph_edge_add(from, to, name)`: the third argument is the edge name. The routine passes `from` as the source and `to` as the target to `graph_edge_add`, with the name as its fourth argument.
- `hwgraph_path_add(from, path, out)`: the path is the second argument, and the new vertex is written through the third. The path is walked with `graph_path_get_component`.
- `hwgraph_char_device_add(from, path, prefix, out)`: the path is the second argument and the third is the driver prefix, which the routine passes to `device_driver_get` before it looks up the character switch table. The fourth argument receives the device vertex.
- `hwgraph_device_add(from, path, prefix, out, ...)`: calls `hwgraph_path_add` with the path it was given, so the path is its second argument.

Also established from the entry code of the IP27 image, read in a later pass:

- `hwgraph_block_device_add(from, path, prefix, out)`: the same shape as the character add. The prefix goes to `device_driver_get` and the path to `hwgraph_path_add`.
- `hwgraph_link_add(from, path, name)`: it traverses the first argument, adds the second as a path and passes the third to `hwgraph_edge_add` as the edge name.
- `if_hwgraph_alias_add(vertex, name)`: it calls `hwgraph_edge_add` with a global graph root as the source, the first argument as the target and the second argument as the edge name, so the alias name is the second argument.
- `if_hwgraph_add(from, path, prefix, alias, out)`: it calls `hwgraph_char_device_add` with the first three arguments and the fifth as the output, then adds an edge from the global root to that vertex named by the fourth argument. The table reads the path and the prefix; the fourth argument, a second name the call adds, is not tabulated.

`graph_edge_add` is the generic graph routine under `hwgraph_edge_add`. Its three sites in the images are all inside `hwgraph_edge_add`, so it adds no device names of its own.

## Names by kind

Path components (from `hwgraph_path_add`, located):

- Board and CPU structure, added by the KLCONFIG walk (`klhwg_add_node`, `klhwg_add_hub`, `klhwg_add_mem`, `klhwg_add_rps`, `klhwg_add_xbox_rps`, and `init_all_devices` on IP30): `node`, `hub`, `memory`, `cpu`, `cpubus`, `cpunum`, `rps`, `xbox_rps`. The board path shapes are in [hwgraph.md](hwgraph.md), which reads the IP27 routines.
- Bus and adapter parents: `xtalk` and `xtalk/15` (IP30 `init_all_devices` adds `xtalk/15`), `gio` (IP30 `giobr_attach`), `pci-x/0` and `pci-x/1` and `agp/0` and `agp/1` (IP35 `pic_attach`), `ohci/0` (IP30 and IP35 `fire_attach`), `ioc4` (IP35 `ioc4_attach`), `vme` and `usrvme` (`universe_attach` and `usrvme_device_register`), and the VME slot names `a16n`, `a16s`, `a24n`, `a24s`, `a32n` on IP27 and IP35.
- Devices and subsystems: `scsi`, `scsi_ctlr`, `scsi_ctlr/0`, `disk`, `rdisk`, `target`, `net`, `audio`, `midi`, `gfx`, `ttys`, `input`, `consumer`, `producer`, `ipl`, `external_int`, `base`, `usrpci`.

Edges (from `hwgraph_edge_add` and `hwgraph_link_add`, located): `root`, `usr`, `swap`, `io`, `xtalk`, `link`, `heart`, `console`, `keyboard`, `mouse`, `tablet`, `ioc3`, `sys_critical_parent`, and the internal `.host`, `.guest`, `.master`, `.connection`, `.devhdl`, `.id`, `.invent` names.

Device nodes (from `hwgraph_char_device_add`, located): the name is the edge under the vertex and the prefix is the driver name. Examples: `d8`, `d16`, `d32` with prefix `usrvme_`, `mem`, `mem32`, `mem64`, `kmem`, `zero`, `null`, `random`, `urandom`, `prom`, `nvram`, `flash`, `tg`, `ef`, `eg`, `ei`, `mad_subsys`, `emu_subsys`, `usbaudio_subsys`, `mgras`, `odsy`, `xframe`, `net/if_tg`, `net/if_xframe`. `block` is the block-device name from `hwgraph_block_device_add`.

## Path shapes by machine

These are the shapes the names above give, read from the routines that add them. Vertex parents other than the adding routine were not read for every row, so the shapes are located, not established, except where [hwgraph.md](hwgraph.md) says otherwise.

- **IP27 (Origin 200/2000, Onyx2):** KLCONFIG board vertices `<module>/slot/<slot>/<kind>` with `node`, `hub`, `memory`, `cpu/<letter>` and `cpubus/0` below them ([hwgraph.md](hwgraph.md), established). I/O adds `xtalk`, `vme` and `usrvme` parents with `a16n`-style VME names, and `net`, `scsi`, `disk` and `rdisk` leaves.
- **IP30 (Octane):** `node` and `cpu` and `memory` from `heart_startup` and `init_all_devices`, `xtalk/15` for the IO bus, `gio` for the GIO bridge, `scsi_ctlr` and `scsi` under it, and `ohci/0` from `fire_attach`. The IP30 `mad_ioctl` adds `audio` (`mad_subsys` is a device node name).
- **IP35 (Origin 300/350, Onyx 300/350):** the same `node`, `hub`, `cpu`, `cpubus` and `memory` set as IP27 from `klhwg_*`, `pic_attach` parents `pci-x/0`, `pci-x/1`, `agp/0` and `agp/1`, `ioc4` under them, and `usrvme` with `a16n`-style VME names.

## Hinv strings

`6.5.30/sbin/hinv` holds these format strings in its read-only data. They are located, not established: the code that prints or uses each one was not read.

- `/hw/` (the path prefix), `/hw/net/%s%d`, `/hw/net/ef%d` and `/hw/gm%d` (format strings that look like network device paths built from a name and a unit number; the use was not read).
- `/pci` and `/ef`, used with the same prefix.
- `XIO slot %s`, `PCI slot %d` and `Location: %s`, which print where a board sits.
- `module %s`, `slot %d`, `module -1`, `xio_slot`, `pci_slot`, `pci_bus`, `xtalk_pci`, `pci_xio`, `node` and `motherboard`, the component names the inventory lines use.

The hinv image was disassembled, but the references to these strings did not resolve to code with the straight-line scan used here. Which hinv routine prints each one is unknown until it is read.

## ioconfig

The user-space program is `6.5.30/sbin/ioconfig`, read in [ioconfig.md](ioconfig.md): it takes its rules from the files in `/var/sysgen/ioconfig` (the 6.5.22 copies are in `6.5.22/var/sysgen.IP27`, `IP30` and `IP35` `ioconfig/`), from ten built-in rows, and from `/etc/ioconfig.conf`, where it records the numbers it handed out as `<number> <path>` lines. It reads each vertex's inventory records through the `_inventory` attribute and writes a number through the `_controller_name` attribute of the vertex path. The README in the shipped directories defines the line format, the `-1` wildcards, the rule that a more specific line follows a more general one, and the start number. The fragments `dmedia`, `ifcl`, `usb` and `vme` give the class, type, start number and driver request for each device family.

The 6.5.30 program and the 6.5.30 IP35 kernel's attribute operation are read; the shipped fragments are 6.5.22 files, and the 6.5.30 `/var/sysgen/ioconfig` fragments are not held.

## Not established

- The alias name that `if_hwgraph_add` takes as its fourth argument is not in the table. The argument roles of the other add routines were read on IP27 only; the IP30 and IP35 entries were not read.
- The 285 of 613 add sites whose name is not a literal in straight-line code (94 in IP27, 73 in IP30, 118 in IP35). Each table row says which scan step lost the value. In the rows read, the name is text the routine formats into a stack buffer with `sprintf` (for example `dk_add_hw_disk_alias`, `klhwg_add_cpu` and `io_xswitch_widget_init`), so the format string and its arguments are what is left to read.
- Objects under `usr/cpu/sysgen/*boot` that are not linked into the three kernels are not scanned.
- The hinv routines that use the format strings above.
