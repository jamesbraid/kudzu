# The software side of the crosstalk link in IRIX

How the IRIX 6.5 kernel sees the XIO (Crosstalk) link: the provider layer, widget discovery, the table that ties a widget identification word to a driver, the hardware-graph paths, how the PROM and the kernel probe and number widgets, and how interrupts are allocated and targeted. Everything here is software behaviour. Link-level and packet behaviour (credits, LLP, the crossbar's arbitration) is hardware and belongs to the chip datasheets, not to this page.

## How to read this page

Names: XIO is the connector and product name, Crosstalk the protocol, a widget a device on the link, Crossbow (XBOW) the switch. Crosstown is XIO carried over a cable between enclosures. Its end boards are the Onyx2 rack's KTOWN (which SGI's theory-of-operations manual also calls the Crosstown conversion board) and, in the Onyx 300 graphics module, the Ktown2 board that takes the XIO link from the compute module; Xtown2 is the XIO cable and channel between a C-brick and an I/O brick. PIC is the PCI interface chip of the IX-brick. Xbridge (widget part 0xd002) is a different chip from the Crossbow's own 0xd000 variant and from PIC. Bridge, HEART, Hub and Bedrock are the other widgets and nodes named below. The Hub's per-widget 16 MiB address window is the Little Window; SGI's own header and PROM spell it "small window" and "SWIN", and those spellings are quoted only where they are SGI's identifiers.

Evidence follows the repository rule: a fact is **established** only where a routine, table or string was read in full at an address of a 6.5.30 or 6.5.22 binary. **Inferred** says a reasoned reading and gives the reasoning. **Unknown** has a discriminating test. Binaries read:

- `6.5.30/usr/cpu/sysgen/IP27boot/xtalk.o`, `cdl.o`, `xbow.o`, `xswitch.o`, `xioba.o`, `tpu.o`, and the same-named objects of `IP30boot` and `IP35boot` (relocatable kernel objects with symbols; addresses are object-relative and written `object+0xNN`).
- The linked kernels `6.5.30/unix.IP27`, `unix.IP30`, `unix.IP35` (addresses are absolute), compared with `6.5.22/unix.IP27`, `unix.IP30`, `unix.IP35`.
- The shipped IP35 PROM `6.5.30/usr/cpu/firmware/ip35prom.img` (addresses are the mapped base `0xc00000001fc00000` plus the payload offset) and the strings of `ip27prom.img`.
- Shipped headers under `6.5.30/usr/include/sys` (`xtalk/xwidget.h`, `xtalk/xbow.h`, `PCI/bridge.h`, `PCI/pic.h`, `SN/addrs.h`, `SN/SN0/hubio.h`, `SN/SN1/hubio_next.h`, `tpureg.h`) and the driver reference page `xtalk(D3)` and its siblings `xtalk_intr(D3)`, `xtalk_pio(D3)`, `xtalk_dma(D3)`, `xtalk_error(D3)` (`6.5.30/usr/share/catman/p_man/catD/`).
- `master.d` descriptors of `6.5-base/var/sysgen/master.d/` (`xtalk`, `xbow`, `xbmon`, `heart`, `pciio`, `pcibr`) and `6.5.30/var/sysgen/master.d/` (`xbridge`, `pic`).

## 1. Three layers, one provider per kernel

A crosstalk driver calls the generic layer `xtalk_*`; the generic layer calls one **provider** that knows the machine's bus controller. The generic layer is `xtalk.o`.

- **Provider selection is made when the kernel is linked, not at run time.** The `xtalk.o` of `IP27boot` and `IP35boot` references 30 `hub_*` routines and no other provider; the `IP30boot` one references 28 `heart_*` routines and no `hub_*`. Each PIO-map, DMA, interrupt and provider life-cycle entry in the table below (not the composite `xtalk_pio_addr` or the early-translation pair) is a short stub: a frame for `ra`, one `jal` to the provider with the argument registers untouched, a `nop` delay slot. Established, by `nm` of the three objects and by reading the stubs; the IP35 stubs are listed in [ip35-xtalk.md](../ip35-xtalk.md).
- The provider is the node controller or the HEART. On IP27 (Origin 200/2000, Onyx2) the node controller is the Hub; on IP35 (Origin 3000, Origin 300/350, Onyx 3000, Onyx 300/350, Tezro) it is the Bedrock; on IP30 (Octane, Octane2) it is the HEART. Both IP27 and IP35 kernels use the same `hub_*` routine names, which are the software role name for whichever node controller the platform has; the chip behind the name differs (the shipped headers give the Hub part number 0xc101 and the Bedrock 0xc110). Where this page says "Hub" for code that both kernels share, read "node controller".

### Provider registration

`xtalk_provider_register(vertex, table)` stores the provider's function table in the vertex's fast-info slot (`hwgraph_fastinfo_set`, `xtalk.o+0x7e4`); `xtalk_provider_unregister` stores zero; `xtalk_provider_fns_get` reads it back. Established. On the kernels read, the generic stubs do not consult the table (they call the provider directly); what else reads it through `xtalk_provider_fns_get` was not searched for. The IP27 and IP35 `io_init_node` code registers the Hub's table on the node vertex and then calls `xtalk_provider_startup` (`unix.IP27` 0xc000000000025ab0 and 0xc000000000025ab8, in `do_init_hub_provider`); the IP30 `heart_startup` does the same on its `node` vertex (`unix.IP30` 0xa80000002003ee8c and 0xa80000002003ee94). Established.

## 2. The widget identification word and the part table

A widget's identity is the 32-bit word at offset 0x04 of its configuration block. The shipped header `xtalk/xwidget.h` gives the field masks, and the kernel applies them in `io_xswitch_widget_init` (`unix.IP27` 0xc000000000024aac to 0xc000000000024ad8): revision is bits 31:28 (`srl 0x1c`), part number bits 27:12 (`srl 0xc`, mask 0xffff), manufacturer bits 11:1 (`srl 1`, mask 0x7ff). Bit 0 is not extracted; the PROM complains "Bad bridge id register value (LSB != 1)" when it is clear on a Bridge, so bit 0 is expected set (PROM string, `ip35prom.img` payload offset 0x087148; the expectation is established, the reason is not). The configuration block is a set of 32-bit registers at odd word offsets (0x04 ID, 0x0c status, 0x14 and 0x1c error address, 0x24 control, 0x2c request timeout, 0x34 and 0x3c interrupt destination, 0x44 error command word, 0x4c LLP configuration, 0x54 target flush); the offsets are from the shipped header, and the kernel's own use of 0x04, 0x24 (Bridge control, low nibble = widget number), 0x34 and 0x3c is confirmed below.

A scan of the linked kernels and of that object for 16-bit immediates finds no 0xc101 or 0xc110, so those two are known here only from the shipped headers and the PROM (a hint for 0xc101, not evidence), and stay out of the header.

## 3. The registry: how attach is called

The registry is a generic "part/mfgr" store (`cdl.o`, the Connection Point and Driver List). Its first user is crosstalk: `xtalk_init` calls `cdl_new` with the names "xio", "part" and "mfgr" and commits the result with `compare_and_swap_ptr(&xtalk_registry, 0, new)`, deleting its own copy if another thread won the race (`xtalk.o+0x78c` to `+0x7e0`; strings at `xtalk.o` `.rodata` 0x198, 0x1a0, 0x1a8). `xwidget_driver_register` calls `xtalk_init` itself when the registry is still null (`xtalk.o+0x890`), so a driver may register before the bus code has run. The same facility serves the PCI layer: `pciio.o` creates a registry named "pci" keyed on "vendor" and "device" (`pciio.o+0xd64`), and `scsi.o`, `vmeio.o` and `gioio.o` call `cdl_add_driver`. Established.

- **Entries and wildcards.** An entry is a (key1, key2) pair with a list of drivers and a list of connection points. `cdl_add_connpt(registry, part, mfg, vertex, 0)` stores the vertex and, when neither key is -1, recursively adds the same vertex under (-1, mfg), (part, -1) and (-1, -1) (three recursive calls at `cdl.o+0xeb4`, `+0xecc`, `+0xee4`). That is how a wildcard driver sees every device. The extra last argument of `cdl_add_connpt` in 6.5.30 chooses the lock mode (`mrlock` mode 2 when non-zero, mode 1 when zero, `unix.IP27` 0xc0000000000c60b0 to 0xc0000000000c6118); crosstalk always passes zero. Established.
- **Order of arrival does not matter.** Adding a driver calls the attach routine of every connection point already present on the entry (`cdl_add_driver` loop at `cdl.o+0x830` to `+0x870`); adding a connection point calls every driver already present. The attach routine is reached through `cdl_call_attach`, which finds the driver's character-device switch by the registered prefix and calls its attach entry with the connection-point vertex as the only argument, exactly as `xtalk(D3)` describes. A zero return from attach on a driver-added connection point removes the vertex from the entry's "unknown" listing (`cdl.o+0x958` to `+0x970`). Established.
- **Where it shows in the hardware graph.** For each (part, mfg) pair seen, a vertex named from the two values as eight upper-case hex digits (part first, then mfg, four digits each) is created under `.id/xio/` from the graph root, and an edge from it to each connection point named by the vertex handle in decimal (strings ".id", "0123456789ABCDEF", "%u" in `cdl.o` `.rodata` 0xd8 to 0xf8). If a connection point has been offered to the drivers and none returned success, an "instance" edge is added under `unknown/xio/part/0x<part>/mfgr/0x<mfg>/instance/` (format "%s/%s/%s/0x%x/%s/0x%x/instance", `.rodata` 0xb8). Established for the strings and the code path; the exact vertex handle numbers are run-time values.
- **Attach threading.** `cdl_call_attach` first copies the driver's thread priority into the device descriptor when the device has no `INTR_SWLEVEL` administration label (string at `.rodata` 0x28), then binds execution to a processor of the connection point's master node (`setnoderun`). When the global `io_init_async` is set, the connection point carries an async-attach record and the driver's switch has the async-attach flag, the attach runs in a new thread named "cdlattach%d" (`.rodata` 0x38) and the record counts it; otherwise it runs inline. Established by the strings and call targets (`async_attach_signal_start`, `sthread_create`); the data-flow inside was not traced instruction by instruction, so the exact conditions are inferred from the call structure.

`master.d/xtalk` declares the prefix `xtalk_` with flag `ns` and a dependency on `cdl`; `master.d/xbow`, `heart`, `xbmon`, `xbridge`, `pic` and `pcibr` declare their drivers (`nsc`, `ncs`) with no dependencies. The generic infrastructure object is therefore always built with `cdl`; the drivers are independent of one another except through the registry. Established (descriptor files).

## 4. The per-widget record

`xwidget_register(hwid, vertex, widget_number, master_vertex, master_widget_number, async_info)` (`xtalk.o+0x8f8`, 0x124 bytes; `unix.IP27` 0xc00000000006c6f0) creates the record every other `xwidget_info_*` accessor reads. Established, read in full.

| Offset | Size | Contents | Grade |
|---:|---:|---|---|
| 0 | 8 | fingerprint: the address of the string "widget_info" (the global `widget_info_fingerprint`, `xtalk.o` `.sdata`) | established |
| 8 | 4 | the widget's vertex | established |
| 12 | 1 | the widget number (0..15) | established |
| 16 | 4 | part number (copied from the first word of the hardware-id structure) | established |
| 20 | 4 | revision | established |
| 24 | 4 | manufacturer | established |
| 28 | 4 | the master's vertex | established |
| 32 | 1 | the master's widget number | established |
| 40 | 8 | error handler function (zeroed) | established |
| 48 | 8 | error handler argument (zeroed) | established |
| 56 | 8 | pointer to a private copy of the canonical name of the vertex (`dev_to_name`, then `strlen` + 1 bytes copied) | established |

The record is 64 bytes (`kmem_alloc(64)`). After filling it the routine calls `xwidget_info_set`, which stores the record in the vertex's fast-info slot and also adds it as the label "_xwidget" (`xtalk.o+0x5c8`), calls `device_master_set(vertex, master)`, adds the async-attach info to the vertex when one was passed, and finishes with `cdl_add_connpt(registry, part, mfg, vertex, 0)`, which is what triggers driver attach. `xwidget_info_get` panics with "%v bad xwidget_info" when the fingerprint of a non-null record does not match (`xtalk.o+0x570`); `xwidget_info_chk` answers "is this vertex a widget" by looking for the "_xwidget" label. `xwidget_unregister` removes the inventory entries, deletes the connection point, frees the name and the record. The accessors `xwidget_info_dev_get/id_get/master_get/masterid_get/part_num_get/mfg_num_get/name_get` each panic with a "null xwidget_info" message on a null pointer. `xwidget_name_get(-1)` returns the constant "No Name". All established. Layout offsets are from the instructions; the field names are mine.

The widget number stored here is the **target port on the crossbar**, 8 to 15 for external widgets, and the master's widget number is the Hub's own widget number on the link (read by `hub_widget_id`, `unix.IP27` 0xc00000000001d64c: the low nibble of the doubleword at +0x20 from a base held in a pool word, 0x9200000001c00000 for NASID 0, which lies in the node's widget-1 window; the shipped `addrs.h` calls widget 1 `HUB_REGISTER_WIDGET`, the window of the local Hub's registers). Established for the read; that the register is the Hub's widget control register (`IIO_WCR`, 0x400020 in Linux's `hubio.h`) is inferred from the offset and the nibble mask.

## 5. Probing and numbering widgets

### 5.1 The kernel on IP27 and IP35

Per node, in the order of the binary, `io_init_node` (an unsymbolled routine in `unix.IP27` at 0xc000000000024f58; the DWARF of `kernel.o` carries no name for it, so the name is my label):

1. Router set-up for the node (`router_init` for each dependent router not yet initialised), `hubdev_docallouts(hub vertex)` and `nic_hub_vertex_info(hub vertex)` (reads the Hub's NIC). Established.
2. **Early probe.** A routine at 0xc00000000002471c reads the Hub's LLP control/status word (offset 0x128 within the hub register window, `IIO_ILCSR` in Linux) and tests bit 0x2000 (`IIO_LLP_CSR_IS_UP`). With the link up it reads the identification word at offset +4 of widget 0's Little Window (the Hub always reaches the first widget as number 0) and splits it into part, revision and manufacturer. With the link down it returns -1 for all three. When the part is -1, the node's I/O is done and `io_init_done` runs (no vertices at all). Established. The register read is in `HUBIO_DECODE.h` as `HUBIO.llp_csr` (offset 0x128, bit 13). Re-read in `6.5.30/unix.IP27` (sha256 `567474674eaa83d36431e70f079a35819d0bc3ce1d4b4a2758b8e891b5acc463`): the doubleword load at 0x9200000001c00128 and the `& 0x2000` branch at 0xc000000000024760; the Origin 300/350 routine `hubii_eint_init` (`6.5.30/unix.IP35`) loads the same offset. That the bit means link up is inferred from the Linux name and from the routine's use of it.
3. Register the Hub as provider on the node vertex and start it (section 1). Create the path `xtalk` below the node vertex and an edge `io` from the node vertex to it (strings at `unix.IP27` 0xc000000001405998 and 0xc0000000014059a0; the path add is the call at 0xc00000000002509c's predecessor 0xc000000000025004 and the edge add 0xc000000000025018). Established.
4. **Choose the base widget number.** The routine reads the ID word of widget 0 again. Part 0xc002 or 0xd002 (Bridge or Xbridge directly on the Hub): the node's base widget number is the low nibble of the widget's control register (offset 0x24; store at 0xc000000000025250). Part 0, 0xd000 or 0xd100 (a crossbow): zero (store at 0xc000000000025080). Anything else: the same nibble is stored (0xc000000000025290) and the kernel panics ("Unknown Widget Part Number 0x%x Widgt ID 0x%x attached to Hub %v", the spelling is the kernel's; the call passes level 0; the shipped `cmn_err.h` defines `CE_PANIC` as `LOG_EMERG`, which is 0 in the usual syslog numbering, a value not checked in a shipped header here, so "panics" is inferred from that). Established for the call and the string; the byte is stored at +18908 of the node's `nodepda_s`.
5. Create the vertex named `%x` of the base widget number below `xtalk` and store its handle at +18912 of `nodepda_s` (0xc00000000002509c path add, 0xc0000000000250a8 store). The base-widget vertex is the first widget and, with a crossbow, the crossbow itself ("xtalk/0"). Established.
6. **Mastership.** `device_master_set(widget vertex, Hub vertex)`: exactly one Hub of those wired to the same crossbow gets a zero return. That Hub calls `xwidget_register` for the first widget (part/revision/mfg as read in step 2, widget number = base widget number, master = itself, master widget = its own widget id from the `_node` label) and continues; the other waits on a semaphore in its own node data (`psema`, +18840). Established for the control flow: `device_master_set` at 0xc0000000000250d8, `xwidget_register` at 0xc000000000025114, and the `psema` of the losing Hub at 0xc000000000025178.
7. A widget that is **not** a switch (a Bridge directly connected, as on Origin 200) ends the node's work after `io_link_direct_widget`, which formats "%d/pci" with the base widget number, finds that vertex below `xtalk` and stores it in the I/O board's graph-link word (+144, or -1 with the message "Couldn't find hwgraph vertex for on-board bridge from vertex %d (%v)" when it is not found). "Is a switch" means part 0, 0xd000 or 0xd100 and manufacturer 0. Established (0xc000000000024e3c to 0xc000000000024f58).
8. **Switch path.** The master volunteers its own vertex into the crossbow's volunteer list (label "_xswitch_volunteer"), then the peer Hub's vertex when the node has a peer (`xbow_peer`, +18832 of `nodepda_s`, -1 when none), then assigns every enabled port to a volunteer (below), then wakes the peer through `vsema` (calls at 0xc000000000025124, 0xc000000000025168, 0xc00000000002520c and 0xc00000000002521c). Established.
9. Both Hubs then call the per-widget initialiser for ports 8 to 15: `io_init_xswitch_widgets` (0xc000000000024b70) loops `io_xswitch_widget_init(crossbow vertex, Hub vertex, port, async-info)`, where the async-info is created by `async_attach_new` before the loop and drained by `async_attach_waitall` and `async_attach_free` after it (0xc000000000024ba4 to 0xc000000000024bf8; the two calls from `io_init_node` are at 0xc000000000025184 and 0xc000000000025190). Established.
10. `io_link_xswitch_widgets` repeats step 7 for every populated crossbow port ("%d/pci" below the crossbow vertex, board lookup by module and slot and, when absent, on the peer's board list, message "Could not find PROM info for vertex %v, FRU analyzer may fail"), then two per-node words (+19308 and +19576 of `nodepda_s`, stores at 0xc0000000000251d0 and 0xc0000000000251e4, after a call to `xbow_get_bridge_pointers`) are set to 1; their names in the DWARF were not checked, so their purpose is inferred to be bookkeeping for the Hub's DMA-timeout kick. Established for the control flow (0xc000000000024c08 to 0xc000000000024e1c for the link routine).

**Volunteers and assignment.** The crossbow's volunteer record (label "_xswitch_volunteer") holds a mutex, a count and up to a small fixed number of Hub vertices (count at +16, list from +20; added with the mutex held; `0xc000000000024148`). A missing label produces the message "volunteer for widgets: vertex %v has no info label". Assignment (`0xc00000000002422c` onward):

- Port 0, the crossbow itself, goes to the first volunteer.
- For each port 8 to 15 that `xbow_port_io_enabled` says is enabled in the KLCONFIG crossbow record: if `is_master_nasid_widget` says the port holds the global master I/O board, the volunteer whose NASID equals the console NASID gets it, and finding none is fatal ("Nasid == %d, console nasid == %d"); otherwise a fixed table decides by IO slot; otherwise the volunteers take ports round-robin. Established.
- The table, indexed by I/O slot number 0 to 12, holds the node slot of the preferred Hub: -1, then 1, 3, 1, 3, 1, 3, 2, 4, 2, 4, 2, 4 (13 bytes at 0xc000000001415dd0, read directly). So nodes in slots 1, 3, 2 and 4 own I/O slots {1, 3, 5}, {2, 4, 6}, {7, 9, 11} and {8, 10, 12}. A node that has no peer on the crossbow owns every port. Established.

`xswitch_info` (`xswitch.o`) is the per-crossbow table the loop consults: 152 bytes allocated by `xswitch_info_new`, holding per port a "link ok" flag, the widget vertex and the master assignment, and the provider table for link reset (`xswitch_provider_register` stores it at +144). `xbow_attach` marks the live ports with `xswitch_info_link_is_ok`; the test for liveness is `xbow_link_alive` (bit 31 of the status word at port block + 0x114, where the port block is 0x40 bytes times the port number's low three bits) and `xbow_widget_present` (bit 5 of the word at port block + 0x13c; for the PIC-generation crossbow, part 0xd100 with manufacturer 0, port 15 counts as present without reading it). Established (`unix.IP27` 0xc00000000006d56c to 0xc00000000006d5e4, `xbow_widget_present` and `xbow_link_alive`); [ip27-kernel-io.md](../ip27-kernel-io.md) has the rest of `xbow_attach`.

**The per-widget routine.** `io_xswitch_widget_init` is `unix.IP27` 0xc000000000024810 (0x360 bytes), `unix.IP35` 0xc00000000004bb70 (0x794 bytes). In 6.5.30 it is one iteration of the old loop, with the arguments (crossbow vertex, master Hub vertex, port, async-info). Established for IP27 by full read:

1. Fetch the `xswitch_info` of the crossbow vertex. Read the `_node` label of the Hub vertex (NASID at +10, Hub widget number at +12 of the record) and the `_xswitch_id` label of the crossbow (the crossbow number). The peer NASID is the halfword at +18832 of the node data, or the node's own NASID when -1.
2. Skip the port unless `xbow_port_io_enabled(nasid, port)` or the same for the peer, then unless `xswitch_info_link_ok` is true and `xswitch_info_master_assignment_get` equals this Hub's vertex.
3. Name the slot (`get_widget_slotname`, `get_widget_slotnum`) and the board (`get_board_name`, which looks the board up with `find_lboard_modslot` and falls back to a name in the board record; one of its results is the literal "baseio"). Create the path "module/%M/slot/%s/%s" (module id, slot name, board name) below the root, mark the connection point's master as this Hub (`device_master_set(hwgraph_connectpt_get(widget), hub)`), and if `is_master_baseio` says this is the global master base I/O, redo the same path and call `klhwg_baseio_inventory_add`. Add an edge from the crossbow vertex to the new vertex named by the port in decimal ("%d"). Record the vertex in the switch info (`xswitch_info_vhdl_set`).
4. **Read the widget's identification word directly from the port's Little Window** (NASID in bits 32 and up, port in bits 24 and up, plus the uncached I/O window base 0x9200000000000000; the window is 16 MiB, shipped `addrs.h` `SWIN_SIZE_BITS` 24). Split it as in section 2. Port 0 uses a different base (a pool word, 0x92000000e0000000, which looks like the Hub's own widget window) and is only used for the base widget.
5. Add an inventory record for the widget vertex from the board (module, slot, revision), then call `xwidget_register(&hwid, widget vertex, port, Hub vertex, Hub widget number, async-info)`. Finally `bte_bpush_war` for the node.

The kernel therefore **takes the part number from the widget, not from the PROM's KLCONFIG**. KLCONFIG supplies which ports are enabled, the module and slot, and the board name; the ID word that picks the driver is always re-read from the widget by the kernel (established: step 4 loads the word itself). The IP35 version adds, before the registration, Brick-type queries over the system controller (`iobrick_module_get_nasid`, `iobrick_l1type_get_nasid`, `iobrick_L1bricktype_to_name`), the vertex labels "_elsc", "_nic" and "_mon", path formats "module/%M/%s/L1", "module/%M/node/xtalk/0", "module/%M/%s" and "module/%M/%s/%s/%d" (the last with a literal "xtalk"), an edge "link" between two of those vertices, and a call `hub_set_piomode(…, 2)` taken when the part is 0xc104 or 0xc105, when the part is 0xc102 (compared on a separate path ahead of that test), when a global mask test selects a graphics-class system, when `get_chimera_type` returns 2, 3 or 5, or for the PIC bus-0 and bus-1 identifications (0xd102, 0xd112, both with manufacturer 0x24, the second only when a per-port bit is set). Established by instruction-level reading of the 6.5.30 `IP35boot/kernel.o` routine (comparisons at object offsets 0xbf24, 0xbf30, 0xbf90, 0xbf9c and 0xc090 and the call at 0xbfcc; call targets by relocation); the console message for a brick without a recognised type and the meaning of the Chimera types were not traced.

**Run-time hot-plug path.** `xtalk_device_powerup(master vertex, port)` obtains the connection point of the master vertex (`hwgraph_connectpt_get`) and calls `io_xswitch_widget_init` for that port with zero async-info, then returns 0 (`xtalk.o+0xbc4`; IP27 and IP35 only). `xtalk_device_shutdown(master, port)` formats the port as decimal, finds that edge with `hwgraph_traverse`, and calls `xwidget_unregister` on the vertex it finds, returning 0 on success or 1 when no vertex was found (`xtalk.o+0xc04`). Established. Whether any shipped code calls them is not known.

### 5.2 The kernel on IP30

`heart_startup` (`unix.IP30` 0xa80000002003ee44, run from `init_all_devices` at 0xa800000020013808) builds the single-provider graph directly:

1. Path `node` from the root; register the HEART provider table on it and start the provider.
2. Path `xtalk` below the node, `xswitch_id_set(xtalk vertex, 0)`, one more path named "0" below it (the widget-0 vertex) and an edge `io` from the node to the `xtalk` vertex, `device_master_set` on it, then `xwidget_register` for the first widget with the ID word read from address 0x9000000010000004 (widget 0 of the HEART's own window) and widget number 0, master the node, and the master's widget number taken from a HEART register (low nibble of the doubleword at 0xffffffffaff00080).
3. A loop from port 15 down to port 0: where `xswitch_info_link_ok` is true, create a path named "%d" (decimal) below `xtalk`, record it in the switch info, read the port's ID word at 0x9000000010000000 plus the port number times 2^24 plus 4, and call `xwidget_register` for it with the same master.

Established (control flow and values read in full). IP30 Octane window layout (widget 0 Crossbow, 8 HEART, 15 base-I/O PCI) is from the public Linux IP30 code and is consistent with the loop; HEART is the registered `heart_` driver of part 0xc001 and the Bridge at port 15 uses the `xbridge_`, `giobr_` and `srflash_` drivers. `heart_attach` adds an edge `heart` from the widget to its master and `.connection` back (edge strings at `unix.IP30` 0xa8000000203afed8 and 0xa8000000203afec8) and registers an error handler with `xwidget_error_register`. Established.

### 5.3 What the PROM does before the kernel

The PROM does the same work in its own terms and hands the kernel the KLCONFIG board list ([klconfig.md](../klconfig.md)); it does not hand over widget identification words (see step 4 above). The reading below is of the IP35 PROM; the IP27 PROM image carries the same message set (the strings listed in the sources) and was not read for control flow, so everything about the IP27 PROM is **unknown beyond its strings**.

- `widget-discovery` (IP35 PROM payload offset 0x04afbc) takes the crossbow's base address, a mode flag, a module id and the part number of the first widget. It tests that part: 0xd000 and 0xd100 lead to the I/O-brick board record builder (offset 0x04a9b8), 0 leads to the midplane board record builder (0x04a758), and anything else prints "Unexpected widget part number: 0x%x" and returns no board. Established (branches at offsets 0x04b008 to 0x04b050).
- It then steps through the crossbow's links in increasing order (helper at 0x04bdec returns the next candidate link). For each, a helper at 0x04bdd4 decides whether the link leads to another Hub; if it does, the PROM does not read an ID word and treats the part as 0xc110 (the Bedrock peer value, loaded at 0x04b190). Otherwise it reads the link's ID word through a helper at 0x04ea30 (-1 on failure, which is handed to a diagnostic helper at 0x04a4ec) and takes bits 27:12 as the part. The window address it forms for the link is `0x9200000000000000` plus the node bits plus the link number shifted left 24, the same address the kernel forms. It prints "New Widget %x connected to HUB." for some paths when the mode flag is set, and "XBow link %d:no NUMAlink, skipping" when the Hub-class peer check at 0x04a4d4 fails. Established for the loop, the address and the helpers' call sites; what each helper tests internally was not read, so the descriptions of the three helpers are inferred from their call contexts and strings.
- It dispatches on that part number: 0xc002, 0xd002 and 0xd102 to a bridge-style builder (offset 0x04b384, which reads the Bridge NIC string and prints "Found %s at 0x%x" with "Bridge" or "Xbridge", and "WID %x, Bridge NIC: %s"); 0xc013 to the graphics builder at 0x04ab14 (subsystem names "mgras", "odsy", "kona", otherwise "unknown_gfx" and the note "Found gfx widget with unknown subsystem"); 0xc102 to the graphics builder at 0x04adf4; 0xc202 to a TPU builder (0x04a324, "WID %x, TPU NIC: %s"); 0xc104 and 0xc105 to a builder that reads a NIC with a lock-retry loop ("retrying GSN NIC lock %d", "got lock for SHAC NIC on GSN_A board" and "…GSN_B board", 0x04a068); 0xc110 to a Hub-peer branch that skips a record already made. Every other part, including 0xd112 on a straight reading of the branches, falls to the generic builder at 0x04a64c. Established for the dispatch targets (compare chain at 0x04b0fc to 0x04b2f0); the names are those of the PROM strings; the reading of 0xd112 is inferred from the comparison chain and was not exercised.
- Two other PROM strings give its own naming: "/hw/module/%M/xtalk/%d" in IP35 diagnostics, and "slot/%s/node/xtalk/0/xbow" and "/hw/module/%M/slot/io%d" in the IP27 image. These match the kernel's paths (section 5.1 and 5.4).

The numbering a PROM-built KLCONFIG records is the crossbow port (widget) number; the kernel's widget number for the same board is the same port. The module and slot the PROM records are what name the board vertex ("module/%M/slot/…"). Inferred from the matching port loop and the shared `xbow_port_io_enabled` test; not independently checked against a recorded KLCONFIG dump here.

## 6. Interrupts: allocation and targeting

A crosstalk interrupt is a software object that ties a widget, a target processor and an 8-bit vector together; the widget is then taught the destination by a driver-supplied callback. The manual page `xtalk_intr(D3)` states the three phases; the binary agrees.

1. **Allocate.** `xtalk_intr_alloc(widget vertex, device descriptor, owner vertex)` and the `_nothd` form (no interrupt thread; the stub passes a flag of 1 to the same routine) call the provider's allocator. On the Hub this is `hub_intr_alloc` (`unix.IP27` 0xc00000000003bfbc), which chooses a processor and a Hub interrupt level (a processor from the descriptor's target if set, else `intr_heuristic`: the master node of the widget, then nodes in rising distance, then the boot processor's node; [interrupts.md](../interrupts.md) has the details) and allocates a 48-byte handle. Established there.
2. **The generic accessors read that handle.** `xtalk_intr_dev_get` returns the word at +0 (the device vertex); `xtalk_intr_target_get` the byte at +4 (the master's widget number, from `xwidget_info_masterid_get`, i.e. the Hub's widget id); `xtalk_intr_vector_get` the byte at +5 (the interrupt bit within its block: the 8-bit vector the widget must send); `xtalk_intr_addr_get` the doubleword at +8; `xtalk_intr_sfarg_get` the doubleword at +16 (the set-function argument) (`unix.IP27` 0xc00000000006c2dc to 0xc00000000006c300). The IP30 `heart_intr_alloc` reaches a shared routine `do_heart_intr_alloc` with the same 28-byte stub shape. Established. Because these accessors are provider-independent, a driver sees the same four values on both providers; the meaning of the address on the Hub is a Hub interrupt-pending address (NASID shifted left 38 plus a fixed offset, per [interrupts.md](../interrupts.md); inferred there).
3. **Connect.** `xtalk_intr_connect(handle, handler, handler arg, set function, set-function arg, thread)` is a stub to `hub_intr_connect` (`unix.IP27` 0xc00000000003c06c), which installs the handler at the chosen level and bit through `intr_connect_level`, stores the set function and its argument into the handle (+24, +16), calls the set function once with the handle when it is non-null, and marks the handle connected. The manual states the set function "will always be called once, to set the initial assignment; the system may call it again, later, if the interrupt needs to be migrated". `xtalk_intr_disconnect` calls the set function again with the bit and removes the handler. Established ([interrupts.md](../interrupts.md)).

**The set function is where a widget is told its destination.** The crossbow's own is `xbow_setwidint` (`xbow.o+0x944`): it reads target, address, vector and set-function argument (the register block) from the handle through the accessors and calls `xbow_intr_preset(registers, 0, target, address, vector)` (`xbow.o+0x9b0`), which stores two 32-bit words:

- at register offset 0x34: vector (low 8 bits) shifted to bits 31:24, target widget (low 4 bits) at bits 19:16, and address bits 47:32 in bits 15:0;
- at register offset 0x3c: address bits 31:0.

These offsets and fields are exactly the interrupt destination pair of the shipped `xwidget.h` (`WIDGET_INTDEST_UPPER_ADDR`, `WIDGET_INT_VECTOR` bits 31:24, `WIDGET_TARGET_ID` bits 19:16; `WIDGET_INTDEST_LOWER_ADDR`). Established (instruction-level). The same pair is what the Bridge and PIC drivers program through `pcibr_setwidint` and, for individual PCI interrupts, `pcibr_setpciint` ([ip35-pci-bridge.md](../ip35-pci-bridge.md), [ip27-driver-attach-interrupts.md](../ip27-driver-attach-interrupts.md)); here the bridge is the widget and the PCI function is below it. For the Hub, an address of `(NASID << 38) + 0x800001800090` yields upper-16 bits `0x8000 + (NASID << 6)` and low word `0x01800090` (arithmetic on the value [interrupts.md](../interrupts.md) records; derived, not separately read from a widget).

**Error and reset paths.** `xwidget_error_register(vertex, handler, argument)` stores the handler pair in the record (+40, +48). `xtalk_error_handler(vertex, code, mode, record)` calls that pair when set. When none is set it returns 0 (the shipped `ioerror.h` `IOERROR_HANDLED`) without a message for modes 0, 2 and 3, which are `MODE_DEVPROBE`, `MODE_DEVUSERERROR` and `MODE_DEVREENABLE` in the shipped enumeration; for any other mode (`MODE_DEVERROR`, 1) it logs "Xbow at %v encountered Fatal error" at level 4 (`CE_WARN`), dumps the record with `ioerror_dump` and returns 9 (`IOERROR_UNHANDLED`) (`xtalk.o+0x390` to `+0x438`, compare chain at `+0x3e0` to `+0x3f4`). Established. `xwidget_reset` calls `xswitch_reset_link` (the crossbow provider's link reset); `xwidget_gfx_reset` does that and then, on the SN platforms, calls the Hub's `hub_widget_reset(master, widget number)` (`xtalk.o+0xb10`), asserting that the widget record exists. Established except where noted.

## 7. What a driver sees, end to end

1. At boot each driver's init registers (part, mfg, prefix).
2. The kernel walks nodes, creates vertices and for each live widget calls `xwidget_register`, which stores the record and calls the attach routine of every matching driver with the **connection-point vertex** (`hwgraph_connectpt_get(widget vertex)` is the vertex the driver receives from the manual's point of view; the code passes the vertex given to `xwidget_register`).
3. The driver finds its registers with `xtalk_piotrans_addr(vertex, 0, offset, size, 0)` or `xtalk_pio_addr`, a DMA map with `xtalk_dmamap_alloc`, an interrupt with `xtalk_intr_alloc` followed by `xtalk_intr_connect` with a set function that writes the widget's destination registers, and its error handler with `xwidget_error_register`.
4. The widget number, the master and the part are available through `xwidget_info_get(vertex)` and its accessors, and the user-visible name through `xwidget_name_get`.

Step 2 contains one open point: the manual says attach receives "the hardware graph connection point vertex", while `xwidget_register` adds `vertex` itself to the registry; whether these are the same object for the vertices `io_xswitch_widget_init` creates (the widget path is created with `hwgraph_path_add` and the registry receives that handle, while the master is set on `hwgraph_connectpt_get` of it) is unknown (test in the table below).

## Corrections (2026-11-10)

A review of this page against the binaries and manuals changed the following.

- Crosstown naming: Ktown2 is a board (in the Onyx 300 graphics module), not a cable; Xtown2 is the XIO cable and channel between a C-brick and an I/O brick (manuals 007-4509-001 and 007-4311-002). The KTOWN "conversion board" wording is kept only as the Onyx2 theory-of-operations manual's own name for the rack board.
- Provider on IP35: the IP35 kernels are the Bedrock kernels, so the page no longer says the Bedrock machines are outside the kernels read. The `hub_*` routines are the shared software role name; the PROM's 0xc110 peer value is the Bedrock's.
- Parts 0xc104 and 0xc105: no longer "PROM only". The IP35 per-widget routine compares both and takes the same `hub_set_piomode(…, 2)` path as graphics parts (read in `IP35boot/kernel.o`). Absence of a driver registration still holds.
- `odsy_` driver: `IP35boot/odyssey.a` does contain the registration for part 0xc013, manufacturer 0x23. The linked IP35 kernel read has no `odsy_init` symbol (the stub object is linked), so the "linked into" entry stays IP30 with that qualification.
- Provenance: a sentence describing how one routine's control flow was first read was removed. Every claim on the page rests on the binaries, headers and manuals listed above.
- Checked and unchanged: the IP35 per-widget routine address and size (the linked IP35 kernel has it at 0xc00000000004bb70, matching the page). Not re-checked in this pass: the 6.5.22 claims, the unsymbolled IP27 `io_init_node` steps, the `cdl.o` offsets and the IP30 `heart_startup` addresses.
