# Video format files: where they sit on the media, what they hold, and what reads them

The SGI graphics boards of IRIX 6.5 take their video timing from files under `/usr/gfx/ucode/<board>/`, not from the kernel. This page is the cross-board view: which boards have such files, where they are on the install media, the one container most of them share, the compiler that makes them, and which programs read them at run time. The per-field decode of each board's files stays in the repository that owns the board (crime repository, odsy repository, gr4 repository, kona repository); the links below name the page.

Grades follow the repository rule: **established** (the bytes or the whole routine were read), **inferred** (a reasoning, stated), **unknown** (with what would settle it). Sources are the extracted media of the 6.5 base set (June 1998, eight discs) and the 6.5.30 overlay set. The files and programs were read from those two trees; the 6.5.22 set was not opened for this page. File sizes and counts below are from the extracted trees.

## Answer in brief

- The files are `.vfo` (compiled format), `.sdb` (the same container, the IMPACT name), `.cmb` (a combination of formats) and, on older boards, `.u` and `.vof` files in other layouts. Newer ones all open with the same big-endian XDR container (magic `sdb `, a symbol directory at the end), so a reader needs about thirty lines and no board knowledge to open any of them. Established.
- Boards with files: O2 (CRIME/GBE), VPro (Odyssey) and its compositor, IMPACT (MGRAS), InfiniteReality (KONA), RealityEngine, Express (GR2) and Newport (NG1, "XL"). Not LG1 (Entry/Starter): no directory, no path string and no timing reference in its X module. Established.
- Who reads them: `setmon`, `ircombine` and the board's X module (`crm.so`, `impact*.so`, `odyssey.so`, `kona*.so`, `gr2*.so`, `ng1.so`) each open files themselves and each carries its own copy of the reader. `gfxinit` loads microcode and, for RealityEngine, VOF programs; the kernel never opens a file. Established for the strings and the call sequences cited below; inferred where only the strings were read.
- A driver running outside IRIX can read the files unchanged from the user's own install media or an installed root; nothing in them is host-endian or encrypted. Established for the format; the media container (EFS volume, inst archives) needs its own reader, see the last section.

Established for the strings, unknown for the contents.

## The container

The derivation is in kona: display-file-format.md (kona repository, `software/video/display-file-format.md`) (from `xdr_SDBfileHeader` and `xdr_SDBsymbolTableEntry` in `konal.so`). It was checked here against a second, independent copy of the same code: `usr/gfx/ucode/vfc/sdbutil` (6.5.30, sha256 `3fa52d6c92f4026b…`), whose `xdr_SDBfileHeader` is at 0x1000b434, `xdr_SDBsymbolTableEntry` at 0x1000b618, `xdr_SDBversionNumber` at 0x1000b6e0, `SDBreadOpenDatabase` at 0x1000ac5c and the type switch `mapTypeToXDRPROC` at 0x1000b038. The two readings agree word for word. A parser written from the layout below opened every file under `usr/` of both trees whose first eight bytes are the magic: 486 files (212 in the 6.5 base tree, 274 in 6.5.30: the O2, VPro, compositor, IMPACT and KONA formats and combinations and the `IR/data` diagnostic copies). One fails: `usr/diags/IR/data/160x100_5000.vfo`, whose directory offset is one byte too high, a defect the kona page already documents. Established.

Layout, all words big-endian (XDR):

| Offset | Content |
|---|---|
| 0 | word 4, the length of the magic (an `xdr_bytes` count, not a version), then the bytes `sdb ` |
| 8, 12 | file-format version, major and minor: 0 and 1 in every file |
| 16, 20 | data version, major and minor: the value of `VFCMajorVersion` and `VFCMinorVersion` in a `.vfo` (1 and 1 from 6.5.30; 0 and 1 in the 6.5 base files, which carry neither field), 1 and 0 in a KONA `.cmb` |
| 24 | word 100 (the `xdr_bytes` count), then 100 bytes padded with zero: the producer, `VideoFormatCompiler` in a `.vfo`. The count word is the byte `0x64`, the letter `d`, so a dump of the header reads `dVideoFormatCompiler`; the producer is not that string. |
| 128 | symbol count |
| 132 | a file offset, 0 in every file |
| 136 | file offset of the symbol directory |
| 140 | a word 0 (an empty array of up to ten words) |
| 144 | the values, in the order the compiler wrote them |
| directory | the symbol count again, then per symbol: name length, name padded to four bytes, type word, element count (0 for a scalar), file offset of the value; sorted by name |

A value at its offset is the XDR form of its type. A scalar is one item. An array (element count above 0) starts with a count word and then holds the elements. A string is a length word and the bytes padded to four. Types seen: 2 int, 7 `u_short` (one word on the wire, 16 bits of value), 10 bool, 15 string, 16 float (only in `.cmb` files, per the kona page), 17 double (IEEE, big-endian). Types 7, 10 and 15 are also confirmed by the writer calls in `setmon` (`SDBaddNewScalarSymbol` with type numbers 7, 15 and 2 for the version words, strings and integers of a `.cmb`). The other type numbers of the 21-entry switch map to the remaining `xdr_*` routines and no file uses them. Names are at most 31 characters.

A reader never needs to know a file's layout. It opens the directory, looks a name up (binary search), and decodes the value at the offset. The shipped programs do exactly that: `SDBreadOpenDatabase`, `SDBgetSymbolValueScalar`, `SDBgetSymbolValueArray`, `SDBgetSymbolElementCount`, `SDBcloseReadDatabase` are statically linked into `setmon`, `ircombine`, `sdbutil`, `vfc` and every X module listed below (dynamic-symbol and string evidence, established).

Position-based reading is not needed and not safe. The O2 notes in the crime repository read a "fixed block" by position; that matches the directory only because every O2 file has the same writer order. The symbol offsets differ per file (the `p` and `2@` variants shift them), and the directory gives them exactly.

Field names shared by every board (the generic part the compiler always writes): `FormatName`, `FieldsPerFrame`, `SwapsPerFrame`, `FramesPerSecond`, `VerticalRetraceRate`, `TotalLinesPerFrame`, `TotalPixelsPerLine`, `ActiveLinesPerFrame`, `ActivePixelsPerLine`, `HorizontalFrontPorch`, `HorizontalSync`, `HorizontalBackPorch`, the `FormatInfo_*` digest (pixel clock, porches, interlace, stereo flags, per-field vertical timing), the monitor and system rate limits, and the state-table fields (`StateTableLineType`, `StateTableRepetitions`, `LineTypeLength`, `TransitionValue` and its per-edge arrays `TransitionLineTypesUsingNNNNN`). Established (138 names occur in every O2 file and 114 in every IMPACT base file; the VPro, IMPACT and KONA sets leave out the O2 state-table and `DacPll_*` names that their hardware does not use, as the table below shows).

Board blocks (names present in every file of the family and absent from the O2 set):

| Family | Extra names | What they carry |
|---|---|---|
| O2 | `DacPll_M`, `DacPll_N`, `DacPll_P`, `OptionHardware`, `def_version` | The GBE pixel-clock scalars, and the option board the format needs (`None`, `Presenter_1024`, `Presenter_1280`, `Flatpanel_1600SW`, `O2_DCD`). Decode in crime gbe.md (crime repository, `devices/gbe/gbe.md`). |

Decode in odsy display-files.md (odsy repository, `software/video/display-files.md`). |
| IMPACT | `FrameTab`, `LineSeqTab`, `DacPll_cntl/r/v`, `DIB*`, `DRB*`, `REFControl`, `RECount`, `MgrasDefMajorRev`/`MinorRev`, `VCHardwareName` = `VC3 for Impact` | The VC3 timing tables, DAC clock words, and the display-buffer layout of the framebuffer mode. `VfoVersion` and `DisplayArchitecture` are not a reliable switch between families. IMPACT and O2 both use `VfoVersion` 1, KONA and the compositor use 0 and most KONA files omit `DisplayArchitecture`. The family is known from the directory, or from `VofHardwareName`, `VTGHardwareName` or `VCHardwareName` when a file is handed over on its own. Established (counts over every file).

## The compiler and its sources

Established. `usr/sbin/vfc` (6.5.30, sha256 `b811f875cd630668…`) compiles a format description into an SDB file. Its usage text lists `-a` (analysis: `ascii`, `postscript`, `highlevel`, `xgraph`), `-c chip=<file>,board=<file>` (the two hardware rule files), `-i` (the preprocessor command), `-o` (the output), `-p` (extra preprocessor directives) and `-s` (statistics); the rule files are searched under `$VFC_HARDWAREDEF_PATH`, the current directory, `/usr/gfx/ucode/vfc/rules` and `/usr/gfx/common/ucode/.rules`. `usr/gfx/ucode/vfc/sdbutil` converts between SDB and a text form (`sdbutil file.vfo` prints a file; `-c out.sdb [in.txt]` creates one). The `vfc` product (disc `foundation2` of the base set, `vfc_6530m` on the overlay) also ships a worked example set.

The inputs are two kinds of text file.

- A **format source** (`.vfs`, shipped samples `1280x1024_60.vfs`, `1920x1080_60.vfs`, `646x486_30i.vfs`, `1024x768_96s.vfs`, `1280x1024_120s.vfs`, `BlockSync.vfs` and the shared `StereoTemplate.def`, 6.5 base only). It states the general timing (fields per frame, frame rate, total and active lines and pixels, a name), the horizontal porches in pixels or microseconds, and then, per field region, a list of lines with the low and high times of the sync signals, written with `repeat` counts. Stereo formats are built from a template with defines for rate, active size and porches.
- **Hardware rule files** (`usr/gfx/ucode/vfc/rules/*.def`). A chip file declares the timing generator's limits and its signals and edges; a board file declares how board signals map to chip signals and holds the postprocessing rules that compute register values from the format. The shipped set is `O2_Chip.def`, `O2_Board.def`, `VPro_Chip.def`, `VPro_Board.def`, `VPro_DCD.def`, `VPro_BlockSync.def`, `mgras_vc3.def`, `mgras.def`, `dg4.def`, `dg4_ddo_gvo.def`, `dplex.def` and `voc1.def` (the 6.5.30 overlay; the base set has fewer, with sample chip and board files).

Chip limits as stated in the files, which is what a reader may rely on when it checks a file against its board: O2 chip: line length at most 2160 pixels, 200 vertical states, 32 line types, 28 edges, 5 signals (`A` to `E`) with fixed edge ranges; VPro chip (`VTG1`) and IMPACT chip (`VC3 for Impact`): line length at most 32768 and at most 16 fields (their board files set 255 line types); the DG4 chip file (`voc1.def`): 256 states, 32 line types, 50 edges, line length from a 13-bit field (at most 8191). Established.

The O2 board rules solve the GBE pixel clock by exhaustive search over `M`, `N` and `P` with output `20 MHz * M / (N * 2^P)`, then take the combination whose output is closest to the target (`lines * pixels * rate`) with the loop clock between 80 and 220 MHz. The rule file's constants are `M` up to 40, `N` up to 64, `P` up to 3, with `M` limited to 8 whenever `N` is 16 or more. A comment in the file says the limit on `M` was lowered from 256 for support of a part it calls Arsenic, and that a larger `N` needs a smaller `M` on that part. Established for the rule and the comment; inferred that Arsenic is a later GBE revision (the file does not say).

That change is visible in the shipped files. Every O2 file of the 6.5 base set (rule revision 1.5) carries large `M` and `N` values; every file of the 6.5.30 set (revision 1.6) carries values that respect the tighter limits, at the price of a small clock error. Example, `1280x1024_60`: base `M,N,P` = 252, 47, 0 (107.234 MHz); 6.5.30 16, 3, 0 (106.667 MHz) against a 107.245 MHz target. Nine of the 15 files that exist in both sets changed; `1024x768_60`, `1024x768_60p`, `1024x768_70`, `1280x1024_75`, `800x600_60` and `800x600_72` did not. The worst error against the target is 0.54 percent (`1280x1024_60`). Established (both file sets compared by symbol). A driver that programs GBE from the files should use the 6.5.30 values; the base values fit the GBE 1.1 field widths (8 bits for `M`, 6 bits for `N`, crime) but not the limits of the part the comment names. The crime page's table is the 6.5.30 set.

## What reads the files, and when

Established unless marked.

- **`setmon`** (6.5.30, sha256 `a59868a509468f55…`; man page `setmon(1G)`). It resolves a name to a file itself. The path strings are in its rodata: `/usr/gfx/ucode/CRM/vof/`, `/usr/gfx/ucode/MGRAS/vof…` (through `mgGetVOFpath`), `…/ODSY/vof` (through `odyGetVOFpath`), `…/KONA/dg4/{vfo,cmb}`, `…/STINGRAY/{vfo,cmb}`, `…/VOYAGER/{vfo,cmb}`, `/usr/diags/compositor/data`, `/usr/gfx/ucode/RE/vs2/vof`, and per-family files `/var/X11/Xvc/Crm<n>_TimingTable`, `Impact<n>_`, `Odyssey<n>_`, `NG1<n>_`, `GR2<n>_`, `SC2_<n>_` and `SG2_<n>_`. `-x` writes the chosen format name into the family's `_TimingTable` file (a text file; the O2 file holds the format name and then a second line, see crime xmodule.md (crime repository, `software/xsgi/xmodule.md`)); on RealityEngine and InfiniteReality `-x` writes the board EEPROM instead. For the O2, crime's reading of `crm_setmon` (0x1000e40c, software/kernel/functions.md (crime repository, `software/kernel/functions.md`)) is complete: with an X server running it lists and loads the format through the video-control extension, so the X module does the file read; with none it joins the environment variable `GL_GRROOT`, `/usr/gfx/ucode/CRM/vof/`, the name and `.vfo`, opens the file with `SDBreadOpenDatabase`, reads only `ActiveLinesPerFrame`, `ActivePixelsPerLine` and `VerticalRetraceRate`, maps width, height and rate to one of the 13 built-in timing codes, and sends a 48-byte record holding that code and flags with ioctl 0x55f6. The file's PLL scalars are not used on that path (established there; the three names were also resolved here through the GOT of 0x1000e704 to 0x1000e758). `GL_GRROOT` is a root prefix, so the format directory can be relocated; the `%s/usr/gfx/ucode/...` strings of the other modules suggest the same prefix (inferred).
- **The board's X module**, at server start and on a format change requested through the SGI-VIDEO-CONTROL extension (crime reads `crmLoadAndFree`). For the O2 `crm.so` reads `/var/X11/Xvc/Crm0_TimingTable`, builds `/usr/gfx/ucode/CRM/vof/<name>.vfo`, reads it with `SDBreadOpenDatabase` and sends the timing to the kernel (`crmLoadTimingTable`, ioctl 0x55f6). `impact.so`, `impactsr.so` and `impactpc.so` read `Impact<n>_TimingTable`, search `MGRAS/vof`, `vof/2RSS`, `vof/cmb`, `cmb/1RSS`, `cmb/2RSS` and the FPGA directory, and call `mgrasLoadTimingTable` (a message says "old timing tables not supported"). `odyssey.so` reads `Odyssey<n>_TimingTable`, enumerates `.vfo` and `.cmb` files (patterns `.*\.vfo`, `.*\.cmb`), and sends frame and line tables to the kernel (`odsyLoadTimingTable`, with the failure message `ODSY_LOAD_TIMING_TABLE`). The KONA modules (`kona.so`, `konal.so`, `konas.so`, `konad.so`) read format and combination files with the same library and send a 1532-byte format block to the display generator (kona repository). `gr2.so` and `ng1.so` read `.u` files (below). Their reader library names itself in a message prefix (`libvidfmt: %s`); the functions are `vfmtFind…FormatFile`, `vfmtRead…VideoFormat`, `vfmtRead…Combination`. The kona, odyssey and compositor modules carry all the board directory strings, because they share that library.
- **`ircombine`** (6.5.30 also ships `sgcombine`, not read): builds, reads and writes `.cmb` combination files with `SDBopenNewDatabase`, `SDBaddNewScalarSymbol` and `SDBaddNewArraySymbol` (the writer half of the library, present in `setmon` too, which also writes combinations). It needs write access to `/usr/gfx/ucode/KONA/dg4/cmb` to load a combination (man page).
- **`gfxinit`** (6.5.30): loads microcode (`/usr/gfx/ucode/…` for GR2 HQ2/GE7, MGRAS HQ3/GE11, KONA and RE parts) and, for RealityEngine and its VS2 variant, the VOF programs of the `.u` files (`venice_load_vof`, `loadVofToDataStructure`, `loadVS2VOFFromData`). It holds the `Crm_TimingTableFiles` path table for the O2 but reads no timing file for the O2 itself (crime). It does not read the `.vfo` set of the SDB boards. The set of strings was read; the loader bodies for RE were not.
- **The kernel** never opens a file. It receives records over ioctls from the X module or `setmon`, or uses a built-in table (the O2 kernel has 15 built-in timing records; crime). Established for the O2; the IMPACT and VPro drivers receive tables through `MGRAS_LOAD_TIMING_TABLE` and `ODSY_LOAD_TIMING_TABLE`-class calls (gr4 (gr4 repository, `software/kernel/display-timing.md`), odsy (odsy repository, `devices/display/README.md`)), and the IR board takes a `LoadFormat` request through the KONA driver (kona (kona repository, `devices/dg/README.md`)).

So the format file is the single source of truth for a board's timing on every SDB board except the O2 direct route of `setmon` (no X server), which selects one of 13 built-in kernel records by size and rate. A replacement driver that starts from the same files gets the timing the IRIX X module sends. Established for the O2 direct route, inferred for the other boards (the X modules were read by strings and, for crime, by routine).

## Files that are not SDB

- **Express (GR2)**, `GR2/vof/*.u`, 14 files of exactly 2176 bytes (names such as `30hz.u`, `60hz.u`, `ntsc.u`, `pal.u`, `st492.u`, `iris3k.u`; two further `.bin` files `adjntsc.bin`, `adjpal.bin` of 4636 and 5283 bytes). Binary, big-endian, no magic. The first word is a per-file length-like value (0x14e to 0x36a). A group of words at 0x860 holds the raster: width then height (0x500 by 0x400 for the 1280 by 1024 files, 0x280 by 0x1e5 for NTSC, 0x30c by 0x23f for PAL, 0x401 by 0x300 for `iris3k`), then an interlace flag (1 for `30hz`, `ntsc`, `pal`, `rs343a`) and three small values. The remaining words were not decoded. `gr2.so` appends `.u` to the name, maps the file and passes it on (strings `/usr/gfx/ucode/GR2/vof/%s`, `.u`, "couldn't mmap file"); the standard names `30hz`, `48hz`, `50hz`, `60hz`, `72hz`, `st492`, `rs343a`, `iris3k`, `pal`, `ntsc` are compiled into the module. Established for the layout facts listed, unknown for the rest. What would settle it: a read of `expLoadTimingTable` and the hardware's timing generator manual. The setmon man page says "minus the `.vfo` extension" for GR2 and NG1, but the media holds `.u` files; the module appends `.u`, so the man page is imprecise.
- **Newport (NG1, XL)**, `NG1/vof/*.u`, 31 files of 791 to 1768 bytes, all printable ASCII. The first line is five comma-separated hexadecimal values (`ng1.so` parses it with a `%x,%x,%x,%x,%x` format string); the second and third values are the width and height and the fourth the rate (`0020,0500,0400,003c,006c` in `1280x1024_60`), and the following lines are hexadecimal word tables. The `_r3` and `_r4` suffix files are chosen by a module string pair, so the choice is by board revision (inferred from the strings). The contents of the tables and the first and fifth header values were not decoded.
- **RealityEngine (RE, DG2)**, `RE/dg2/vof/*.u` and the VS2 and VX2 trees: binary; all 50 DG2 files begin with the word `0x45810003`, and the one read in full carries the text `vofc 1.1` and a build date in the header, then the VOF edge tables. `setmon` has the message "VOF is not for DG2", so it checks the header (inferred from the message). This is the format of the older `vofc` compiler, which `vfc` replaced. Established for the header, not decoded further.
- **IR early text format**, `KONA/vof/default.vof`, `640x480_60.vof`, `vga.vof`, `*.monitor` (base set only): text with `I` and `E` directives for signal initial levels and edges, and `.monitor` files giving porch and sync limits. Documented in the kona repository's data-file page.
- **LG1**: nothing. No `LG1` directory in `usr/gfx/ucode`, and `lg1mc.so` contains neither a path nor a timing-table string. Its only monitor reference is the symbol `lg1MonitorSizeTable`. The setmon man page says Entry and Starter graphics support one standard name (`60HZ`). Established for the absence, inferred that the timing is built in.

## Reading the files from the user's media at run time

The question is how a driver or setup program that ships none of SGI's data gets the files. Established facts first.

1. The files are ordinary data. No file is signed or encrypted. The format is endian-independent (XDR), so a little-endian host decodes it with byte swaps; the doubles are IEEE.
2. The set a board needs is small: 324 KB for the O2 (26 files), 660 KB for VPro (71), about 1.3 MB for InfiniteReality `.vfo` (74), 0.4 MB for the IMPACT files. A driver needs one directory, not the whole media.
3. On the installed system the files are at `/usr/gfx/ucode/<board>/…` in the root filesystem. On the install discs they are inside inst archives: the disc is an SGI volume header with an EFS filesystem holding a `dist/` tree of per-product `.idb` manifests and `im…` archive files whose records may be `compress`ed; the media inventory lists each file with its product (`eoe`, `eoe_6530m`), subsystem (`eoe.sw.gfx`) and disc. The Origami `tools/extract-irix` reads all of this and is the reference reader for the media container.

Inferred recommendation (not a measurement): do not parse EFS or inst archives inside a kernel driver or at boot. Run a one-time setup step in user mode that extracts the family's directory (`eoe.sw.gfx` entries under `usr/gfx/ucode/<board>/`) from the user's media or from an installed root, into the driver's own data directory, and have the driver read the extracted files with the 30-line reader above. Nothing from the SGI media then ships with the driver. The per-board decode pages above say which symbols a driver must read (for example `crmLoadTimingTable` reads `FormatInfo_*`, `DacPll_*`, `OptionHardware` for the O2).

A driver should also read the file's own board-identifying symbols and refuse a file for another family, since the generic names are shared (the O2 `O2_DCD` option name, for instance, appears in only eight of the 26 O2 files, the `2@` ones).

## Corrections made by this pass

- The producer string of a `.vfo` is `VideoFormatCompiler`. The leading `d` in earlier odsy and kona pages is the low byte of the count word 100 that precedes it. Fixed in those repositories.
- The word 4 at the start of a file is the length of the magic, not a version. The crime and odsy pages called it a version word. Fixed there.
- The crime page said the schema offsets were not decoded and that values are read by position. The directory gives name, type, count and offset, and is decoded (kona, gr4 and here). Fixed there.
