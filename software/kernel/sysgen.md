# Kernel configuration tables (sysgen)

The kernel build reads a small set of configuration files per machine: one driver file per module (`master.d`), tunable defaults (`mtune`) and the link directives (`system/*.sm`). This page covers the three tables made from them, which are generated by [tools/sysgen_tables.py](../../tools/sysgen_tables.py):

- [inventory/sysgen-drivers.tsv](../../evidence/inventory/sysgen-drivers.tsv): one row per driver module, with its flags, prefix, external major numbers, device count, dependencies, stub count, the machines that configure it, a check of the prefix against the kernel's symbol table, and the grade of its role.
- [inventory/sysgen-tunables.tsv](../../evidence/inventory/sysgen-tunables.tsv): one row per tunable line in `mtune`, with its block, class (`static` or `run`), default, minimum and maximum, and the machines that configure its module.

## Release

The tables are built from the 6.5.22 configuration tree, because it is the only complete copy held. The 6.5.30 `var/sysgen` directory is listed as wanted in [evidence/irix-files.md](../../evidence/irix-files.md) and is not in `root/6.5.30/`. The generator refuses a release without `var/sysgen.IP27`, `sysgen.IP30` and `sysgen.IP35` directories, so the 6.5.30 tables are produced by running it with `--release 6.5.30` once that tree is copied in. Nothing in the 6.5.22 tables is a 6.5.30 fact.

## Method

- Each machine directory was compared by content before use. The `master.d` and `mtune` trees are byte-identical across IP27, IP30 and IP35 in 6.5.22. The machines differ only in `system/*.sm`, so the machine columns come from those files.
- A module is configured for a machine when a `USE`, `INCLUDE` or `VECTOR: module=` line in that machine's `system/*.sm` names it, after the modules it depends on are added. An `EXCLUDE` line removes a name. The order of directives across the files is not modelled, so an `EXCLUDE` anywhere wins. This is a model, and the symbol check below tests it.
- The prefix check counts kernel symbols beginning with the module's prefix in `root/6.5.22/unix.IP27`, and for a character or block module whether `<prefix>cdevsw` or `<prefix>bdevsw` is present. Nonzero counts and present switch tables are facts about that kernel image.
- Flags are decoded from the letter legend in the `master.d` README, in our own words. A `-` in the flag field means no flags.
- A tunable line is kept as written. Only lines with three values name a minimum and a maximum. A two-value line (`name default other`) is recorded with `two-values` and its raw values, because the second value could be a bound or something else; the table does not guess.

## Results (6.5.22)

| Measure | Count |
|---|---:|
| driver modules (`master.d` files, excluding README) | 450 |
| masters with no active data line (`if_hy`, whose only flag line is commented out and which says the driver is no longer supported; `fs_cell`, which has no flag line; four element-spec files) | 6 |
| modules configured for IP27 / IP30 / IP35 | 285 / 272 / 303 |
| tunable lines | 613 |
| tunable lines in three-value form (minimum and maximum named) | 403 |
| tunable lines with two values (raw values only) | 20 |
| understood driver rows | 10 |

Tunable blocks are `static` (286 lines) or `run` (259 lines); 68 lines sit before any block header.

### Configuration model against the kernel image

Of the 174 modules configured for IP27 that have a prefix, 137 have symbols under that prefix in the 6.5.22 IP27 kernel. The disagreements are not resolved here:

- Configured by the system files, no symbol under the prefix (37): among them `ide`, `ipv6`, `tpiudp`, `xtimer`, `sockmod`, `wacom`. Some are stream modules whose code may sit under other names; that has not been checked for any of them.
- Not configured by the system files, but symbols present (28): among them `cxfs`, `cell`, `cfs`, `crime`, `grio2`, `midi`, `tpu`, `xvm_cell`. Either the installed kernel was linked from a configuration other than the one these files describe, or the model misses a path that brings modules in. The `cxfs` and `cell` cases point at the `noncell` alternative in the IP27 system file, which is not modelled.

Until these are settled, a `configured` value is a statement about the configuration files, not about the linked kernel.

## Grades

A driver row is `understood` only with a grade (`established` or `inferred`), a role in plain words, and a citation naming the release, the master file and the symbols checked. Roles are in [tools/config/sysgen-roles.json](../../tools/config/sysgen-roles.json). `established` means the flags, prefix, dependencies and symbol counts were read from the shipped files and the kernel image; `inferred` means the role is taken from the module name and the symbols, without reading the code. The other 440 driver rows are `located`: they carry their source line and mechanical fields, and no role yet. Tunable rows are `located` throughout; no tunable has a role written.

## Tunable read sites

[inventory/tunable-summary.tsv](../../evidence/inventory/tunable-summary.tsv) and [inventory/tunable-sites.tsv](../../evidence/inventory/tunable-sites.tsv) map each tunable to its data symbol in the linked 6.5.30 kernels and list every routine that loads or stores it. The tunable names come from the 6.5.22 tables above, and the sites are read from the 6.5.30 kernels. The method is in `tools/tunable_sites.py`: the symbolic pass of `retools/tools/facts.py` resolves each access to an absolute address, so a site is an access the pass resolved, not every use of the variable.

Roles are written for the hardware-related tunables whose IP27 sites were read in the disassembly (the R10000 check, the memory-error counters, the NUMA migration selectors) and live in `tools/config/tunable-roles.json`. Each role names the kernels whose sites it covers. The symbolic pass finds no read of the NUMA migration tunables in the IP30 kernel. The IP35 sites named in the roles are listed but not yet traced; those rows stay `located`.
