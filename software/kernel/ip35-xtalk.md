# Crosstalk layer entry points of the IP35 kernel

Routines of the machine-independent crosstalk layer (`xtalk`) in the IRIX 6.5.30 IP35 kernel (`6.5.30/unix.IP35`, a linked 64-bit image with DWARF). The routines read here are thin entry points: each one is a 28-byte routine that keeps `ra` in a 16-byte frame, makes one direct call to a routine of the hub's crosstalk provider (`hub_*`) with the argument registers untouched, and returns that call's result. The provider routines themselves are mostly not read here; where one is small enough to read in full, the entry says what it does. Call sites are named only when they lie inside the caller's recorded extent.

- `xtalk_piomap_alloc` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc000000000097078): allocates a programmed-I/O map for a crosstalk widget by passing the whole request to `hub_piomap_alloc` (0xc000000000062214).
  The delay slot of the call at 0xc000000000097080 is a nop, so every argument register reaches the provider as the caller left it, and its result is returned. There is no conditional branch and no instruction is branch-likely. Callers are `xtalk_pio_addr` (call at 0xc0000000000971a4), `pcibr_piomap_alloc` (0xc00000000009f378) and `kona_attach` (0xc000000000479ac0). Established.
- `xtalk_piomap_free` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc000000000097094): releases a programmed-I/O map; the only work is a call to `hub_piomap_free` (0xc00000000006252c).
  The call is at 0xc00000000009709c with a nop delay slot, and `v0` comes back unchanged from the provider. The same three routines that allocate a map through `xtalk_piomap_alloc` also reach this one: `xtalk_pio_addr` (call at 0xc0000000000971ec), `pcibr_piomap_free` (0xc00000000009f470) and `kona_attach` (0xc000000000479cd0). No instruction is branch-likely. Established.
- `xtalk_piomap_addr` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc0000000000970b0): turns a programmed-I/O map plus an offset into a kernel address by calling `hub_piomap_addr` (0xc000000000062618).
  Nothing is computed here: the call at 0xc0000000000970b8 follows the 16-byte frame set-up and has a nop delay slot, so a0-a3 are the caller's and the provider's `v0` is returned. It is called from `xtalk_pio_addr` (0xc0000000000971c4), `pcibr_piomap_addr` (0xc00000000009f4c8, which first rewrites the second argument) and `kona_attach` (0xc000000000479ad4). Established.
- `xtalk_piomap_done` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc0000000000970cc): tells the provider a programmed-I/O map is no longer in use, through one call to `hub_piomap_done` (0xc000000000062678).
  The call is at 0xc0000000000970d4, the delay slot is a nop and the result is the provider's. The only caller found in the image is `pcibr_piomap_done` (call at 0xc00000000009f4e4). The frame holds `ra` alone and no instruction is branch-likely. Established.
- `xtalk_dmamap_alloc` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc00000000009722c): the crosstalk entry for creating a DMA map object; it jumps through to `hub_dmamap_alloc` (0xc00000000006274c) with its arguments intact.
  The provider call is the `jal` at 0xc000000000097234. The bridge driver reaches it from `pcibr_dmamap_alloc` (call at 0xc00000000009fb44). Aside from the stack frame for `ra` the routine has no other instruction that reads or writes data, and none is branch-likely. Established.
- `xtalk_dma_enabled` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc000000000097540): asks the hub provider whether DMA is enabled for a widget, by calling `hub_dma_enabled` (0xc0000000000790bc).
  The argument is passed through unchanged (delay slot of the call at 0xc000000000097548 is a nop) and the provider's answer is the result. The first two things `hub_dma_enabled` does are look up the widget record and its id from its argument; the rest of its body was not read for this entry. The only caller found is `pcibr_dma_enabled` (call at 0xc0000000000a1964). No instruction is branch-likely. Established.
- `xtalk_dmamap_free` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc000000000097248): releases a DMA map object by calling `hub_dmamap_free` (0xc0000000000627cc) with its arguments untouched.
  The call is at 0xc000000000097250 with a nop delay slot, and the provider's `v0` is returned. `hub_dmamap_free` loads the word at +12 of the map, clears bit 0 of it (AND with -2) and stores it back in the delay slot of its call to `kern_free(map)`, so the store happens before the callee runs; the result is whatever `kern_free` leaves in `v0`. `xtalk_dmamap_free` is called from `pcibr_dmamap_alloc` (at 0xc00000000009fcc8 and 0xc00000000009fcfc) and from `pcibr_dmamap_free` (0xc0000000000a0014). The frame holds `ra` only, and no instruction is branch-likely. Established.
- `xtalk_dmamap_addr` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc000000000097264): turns a DMA map and an address into the bus address for the transfer; it forwards both unchanged to `hub_dmamap_addr` (0xc0000000000627f4).
  The call is at 0xc00000000009726c, the delay slot is a nop, and the provider's result is returned. `hub_dmamap_addr` returns its second argument (`a1`) on every path. It reads the word at +12 of the map: when bit 1 (0x2) is clear it sets that bit and stores the word back; when bit 1 is set and bit 2 (0x4) is clear it logs "%v: hub_dmamap_addr re-uses dmamap." through `cmn_err` at level 4 with the word at map +0 (the string is at 0xc000000001524f08, pool word at gp-22568 plus 16); when both are set it does nothing. The only caller found is `pcibr_dmamap_addr` (call at 0xc0000000000a0340). No instruction in this routine is branch-likely. Established.
- `xtalk_dmamap_list` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc000000000097280): maps a scatter list for DMA by handing the whole request to `hub_dmamap_list` (0xc000000000062850).
  The call is at 0xc000000000097288 with a nop delay slot. `hub_dmamap_list` has the same body as `hub_dmamap_addr` read for `xtalk_dmamap_addr` except for its message: it tests and sets bit 1 of the word at map +12, warns about bit 2 with "%v: hub_dmamap_list re-uses dmamap\n" (at 0xc000000001524f30, pool word plus 56) and returns `a1` on every path. The only caller found is `pcibr_dmamap_list` (call at 0xc0000000000a0518). Frame 16 bytes, no branch-likely instruction. Established.
- `xtalk_dmamap_done` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc00000000009729c): tells the provider a DMA transfer through a map has finished, via `hub_dmamap_done` (0xc0000000000628ac).
  The call is at 0xc0000000000972a4, the delay slot is a nop and the result is the provider's. `hub_dmamap_done` reads the word at map +12: when bit 1 (0x2) is set it clears it and stores the word back; when bit 1 is clear and bit 2 (0x4) is set it returns without a store; when both are clear it logs "%v: hub_dmamap_done already done with dmamap\n" (at 0xc000000001524f58, pool word at gp-22568 plus 96) through `cmn_err` at level 4 with the word at map +0. It sets no result register of its own. The only caller found is `pcibr_dmamap_done` (call at 0xc0000000000a0904). No instruction is branch-likely. Established.
- `xtalk_dmatrans_addr` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc0000000000972b8): the crosstalk entry for a direct (map-less) DMA translation; it calls `hub_dmatrans_addr` (0xc0000000000628fc).
  The call is at 0xc0000000000972c0 with a nop delay slot. `hub_dmatrans_addr` is two instructions, a return and a copy of its third argument into the result register, so the value comes back unchanged and the translation is the identity on it. The callers found are `pcibr_directmap_init` (call at 0xc00000000009e790) and `pcibr_dmatrans_addr` (0xc0000000000a09c0). The frame holds `ra` only and no instruction is branch-likely. Established.
- `xtalk_dmatrans_list` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc0000000000972d4): the crosstalk entry for a direct DMA translation of a scatter list; it calls `hub_dmatrans_list` (0xc000000000062904).
  The `jal` to the provider is at 0xc0000000000972dc and its delay slot is a nop. `hub_dmatrans_list` has the same two instructions as `hub_dmatrans_addr` (a return and a copy of `a2` into the result register), so a list translation also hands back the caller's third argument unchanged. `pcibr_dmatrans_list` is the only direct caller (call at 0xc0000000000a0da0). Apart from the return there is no branch, and no instruction is branch-likely. Established.
- `xtalk_dmamap_drain` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc0000000000972f0): asks for the DMA writes through a map to be drained; it calls `hub_dmamap_drain` (0xc00000000006290c) and does nothing else.
  The call is at 0xc0000000000972f8 with a nop delay slot. `hub_dmamap_drain` is `jr ra` followed by a nop: this hub provider does no work to drain a map and leaves `v0` as it was. The only caller found is `pcibr_dmamap_drain` (call at 0xc0000000000a10d0). The frame holds `ra` only and no instruction is branch-likely. Established.
- `xtalk_dmaaddr_drain` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc00000000009730c): the drain entry for a DMA address range; it calls `hub_dmaaddr_drain` (0xc000000000062914).
  The provider is reached by the `jal` at 0xc000000000097314, whose delay slot holds a nop, so the range arguments pass straight through. `hub_dmaaddr_drain` is a bare return followed by a nop: on this hub nothing is flushed for an address range, and the routine never sets `v0`. `pcibr_dmaaddr_drain` is the only direct caller (its call is at 0xc0000000000a110c). There is no branch except the return, and none is branch-likely. Established.
- `xtalk_dmalist_drain` (`6.5.30/unix.IP35`, occupies 28 bytes at address 0xc000000000097328): the drain entry for a DMA scatter list; it calls `hub_dmalist_drain` (0xc00000000006291c).
  The call is at 0xc000000000097330 with a nop delay slot. `hub_dmalist_drain` is `jr ra` and a nop, so it drains nothing and does not write `v0`. The only caller found is `pcibr_dmalist_drain` (call at 0xc0000000000a1144). The frame holds `ra` only and no instruction is branch-likely. Established.
