# Kernel debugger command tables

The commands the optional kernel debugger registers, read from the relocatable objects `idbg.o` and the `*idbg` modules in `usr/cpu/sysgen/IP35boot` of the 6.5.30 media. The linked kernels carry only the stub form of the debugger ([kernel-tracing-and-modules.md](kernel-tracing-and-modules.md#the-kernel-debugger)), so this is what a kernel built with the debugger subsystem would accept. Nothing here was run on a guest.

## How the tables are built

Established, from the sections and relocations of the objects.

- `idbg.o` exports eighteen words at the start of its `.data` (offsets 0x28 to 0xb8, with one gap at 0x78: `_idbg_setup`, `_idbg_copytab`, `_idbg_tablesize`, `_idbg_dofunc`, `_idbg_error`, `_idbg_switch`, `_idbg_addfunc`, `_idbg_delfunc`, `_qprintf`, `__prvn`, `_idbg_late_setup`, `_idbg_unload`, `_idbg_addfssw`, `_idbg_delfssw`, `_printflags`, `_padstr`, `idbg_mrlock` and `_prsymoff`), the vector the kernel's `debug_init` fills from the loaded module.
- Its base command table starts at `.data` offset 0xc0 and has 109 entries of 32 bytes: a pointer to the command name, a pointer to the handler, a zero word, and a pointer to a one-line help string. The first entry is the help command, whose name is `??`. Exactly one entry, `call` (call an arbitrary function), has no handler pointer; the dispatcher treats it specially. Further tables later in `.data` (system-call argument printers, semaphore commands, thread lists) bring the object's total to 178 name and handler pairs.
- Most other modules keep a `.data` table of the same pairs; the rest (address spaces, cachefs, dispatcher, module loader, NFS, NUMA, RPC, process groups, processes, sessions, device special files, STP) call `idbg_addfunc(name, handler)` from their init routine, once per command, which `idbg.o` stores in a table whose capacity is `idbgmaxfuncs`, 1200.
- The user entry is `syssgi` selector 4 ([kernel-tracing-and-modules.md](kernel-tracing-and-modules.md)). Its first argument 1 reaches `_idbg_dofunc` with a pointer to a request block. `_idbg_dofunc` copies in 56 bytes of request, checks the command index against the number of entries in the table (the table end minus its base, divided by 32, less the sentinel), and returns 14 if the copy faults and 22 on a bad index or argument count. Established for the 56-byte copy and the error value 14; the index bound and the 22 returns are Inferred from the compare and branch pattern at the start of the routine; the request field layout was not decoded.

## Argument forms

The table records no argument types: the third word of a base entry is zero in all 109 entries, and the help string is free text. A handler is called by `_idbg_dofunc` with the numeric arguments the request carries (up to four, Inferred from the argument-count bound above and the register moves before the indirect calls; not followed through every arm), and prints through the debugger's `qprintf`. Which handler takes an address, an integer or a string is in each handler's code and is not decoded here.

## Method

For the table form, the `.rel.data` relocations of each object were resolved against `.rodata` (name and help strings) and the symbol table (handlers). For the code form, the init routine's `idbg_addfunc` calls were read from the disassembly with relocations and the name taken from the `.rodata` offset the call loads. Counts depend on that reading; a command registered through a pointer table the scan did not recognise would be missing.
