# Checkpoint and restart in the IRIX kernels

IRIX 6.5.30 ships a kernel checkpoint and restart facility, built from the object archive `cpr.a` and gated by the tunable `ckpt_enabled`. This page documents the kernel half: the system call and `syssgi` selector it adds, the `/proc` requests that save and restore process state, the hooks the rest of the kernel carries for it, what it refuses, and what is still unknown. The IP35 kernel (`6.5.30/unix.IP35`) was read first; IP27 differences are in the last section. The user-space half (the `cpr` command, its library and the viewer) is held in `root/6.5.30` since 2026-11-11 and read only for imports; its format questions are still open.

Evidence is the linked kernels and the kernel object archives `cpr.a`, `cprstubs.a` and `os.a` in the 6.5.30 and 6.5.22 boot directories, plus the 6.5.22 IP35 system-generation configuration files. No published manual for the facility was available when this page was written, so no manual page is cited and every behaviour below is read from the kernel.

Routine names and sizes come from the kernel symbol table where the routine is global, and from the symbol tables of the object files where it is `static`; a static routine's address in a linked kernel is the object's text base plus its offset in the object. Grades follow [AGENTS.md](../../AGENTS.md), with two of its words written as the reading verbs: "Read" is the repository's established (the statement was read in the named routine, table or section), "Reasoned" is its inferred (a reasoned reading whose basis is given), and "Unknown" names what would settle it. The first list below uses the repository's own word, Established.

## Does the facility exist, and how is it configured

The global entry points, with address and size in the 6.5.30 IP35 kernel (checked by the claim checker):

- `ckpt_sys` (`6.5.30/unix.IP35`, 0xc00000000043efb0, 648 bytes) is the `syssgi` back end. Established.
- `ckpt_restartreturn` (`6.5.30/unix.IP35`, 0xc00000000043f238, 560 bytes) is system call 1225. Established.
- `ckpt_prioctl` (`6.5.30/unix.IP35`, 0xc00000000043def0, 560 bytes) handles the process-wide `/proc` requests. Established.
- `ckpt_prioctl_thread` (`6.5.30/unix.IP35`, 0xc00000000043e120, 728 bytes) handles the per-thread `/proc` requests. Established.
- `ckpt_prioctl_attr` (`6.5.30/unix.IP35`, 0xc00000000043aa80, 96 bytes) returns a flag word per request. Established.
- `ckpt_lookup_add` (`6.5.30/unix.IP35`, 0xc00000000043a880, 304 bytes) records file identifiers on a vnode. Established.
- `ckpt_vp_open` (`6.5.30/unix.IP35`, 0xc00000000043a5c8, 280 bytes) opens a vnode for the facility. Established.

- The facility is present in all three 6.5.30 kernels. `cpr.a` holds three objects, `ckpt_sys.o`, `ckpt_procfs.o` and `ckpt_util.o`; the process-side hooks are in `pproc_ckpt.o` inside `os.a`. The 6.5.22 archives hold the same objects. Read.
- The linked IP35 kernel defines the global routines `ckpt_init` (0xc00000000043a5a4, 36 bytes), `ckpt_sys` (0xc00000000043efb0, 648 bytes), `ckpt_restartreturn` (0xc00000000043f238, 560 bytes), `ckpt_prioctl` (0xc00000000043def0, 560 bytes), `ckpt_prioctl_thread` (0xc00000000043e120, 728 bytes) and `ckpt_prioctl_attr` (0xc00000000043aa80, 96 bytes), and the switch `ckpt_enabled` (0xc00000000163c1b0, one word). Read.
- `cprstubs.a` is the build without the facility. The real `cpr.a` is in the base subsystem of the installation media and is linked in the shipped kernels; the user commands `cpr` and `cview` and the library `libcpr` are on the same media in the separate optional subsystem `eoe.sw.cpr` (idb entries of the 6.5.30 media), outside `root/`. Its object `cprstubs.o` defines every entry point as an eight-byte stub: `ckpt_sys` and `ckpt_restartreturn` return 89, `ckpt_lookup_add` returns -1, `pproc_get_ckpt` returns -1, `ckpt_prioctl`, `ckpt_prioctl_thread` and `ckpt_prioctl_attr` return 0, and the rest return at once, except that the `ckpt_init` stub stores zero through the global pointer register in its delay slot. The object also references the four-byte switch `ckpt_enabled` (an undefined small-data symbol, written by that store), so another object must define it. Its fork and exit stubs are named `pproc_ckpt_fork` and `pproc_ckpt_exit`, where the linked kernel names the real routines `ckpt_fork` and `ckpt_exit`. Read. That the configuration tool links the stubs only when `cpr.a` is absent is reasoned from the two `master.d` files below; the linked kernels carry the real routines.
- The configuration files of 6.5.22 (`master.d/cpr`, `master.d/cprstubs`, `mtune/kernel`, `master.c`) show the tunable: `mtune/kernel` has a stanza `ckpt: run` with the single tunable `ckpt_enabled`, default 1, and the comment "enable/disable cpr"; `master.c` lists the module `ckpt` with state `N_RUN` and initialises `ckpt_enabled` to 1; the kernel makefiles build with `-DCKPT`. The 6.5.30 system-generation directory is not held, so these are 6.5.22 facts; the 6.5.30 kernels carry the same `ckpt_enabled` symbol, and the word at 0xc00000000163c1b0 in the linked `6.5.30/unix.IP35` file reads 1. Read for the 6.5.22 configuration and for the 6.5.30 IP35 initial value; the 6.5.30 tunable file itself is not held.
- `ckpt_init` has no direct caller. Its address is stored as a data word at 0xc0000000015984e8 in `6.5.30/unix.IP35`, next to what looks like an initialisation table entry, so it is reached through a table. It allocates one kernel memory zone with 0x38-byte elements and keeps the zone pointer at gp+0x3260. The zone holds the per-vnode file-identifier records described below. Read for the zone, reasoned for the table.

## The two user entry points

### `syssgi` selector 178 reaches `ckpt_sys`

- The `syssgi` case for selector 178 (0xc0000000002e1c20 on IP35; row in [selectors.tsv](../../evidence/inventory/selectors.tsv)) loads the five argument doublewords at +8 to +40 of the argument block and calls `ckpt_sys` with them, passing the return-value pointer as the sixth argument. The first argument is the sub-command, the others its arguments. Read. The selector number is the same on IP27 (0xc000000000232534) and IP30 (0xa8000000201ec524). The kernel names the case by its symbol `ckpt_sys`.
- `ckpt_sys` (0xc00000000043efb0, 648 bytes) compares the sub-command unsigned with 0x17 and jumps through a table of 23 words at 0xc0000000004e22b0. A larger value returns 22. It does not test `ckpt_enabled` itself, and it checks no privilege (no `cap_able` call); whether `syssgi` checks privilege before dispatching was not read. Read for what `ckpt_sys` does and does not test.

### System call 1225 is `ckpt_restartreturn`

- `ckpt_restartreturn` (0xc00000000043f238, 560 bytes) is call 1225 in both the native `sysent` table and `irix5_64_sysent` ([syscalls.tsv](../../evidence/inventory/syscalls.tsv)), three arguments, first flag byte 0x10. That flag makes the dispatcher skip storing return values, which is what `sigreturn` does too (see [syscalls.md](syscalls.md)). Read.
- It reads the first argument as a signed doubleword, the next as a 32-bit word and the third as a doubleword. If the third is nonzero it decodes the 32-bit word as a wait status with `ckpt_wstat_decode` (0xc00000000043f468, 152 bytes) and calls `exit` with the decoded kind and value, so the process ends with the status the original had. Read.
- `ckpt_wstat_decode` maps a wait status to a pair: low byte 0 gives kind 1 with the high byte as value; a nonzero high byte with a low byte of 0x7f gives kind 5 with the high byte as the stop signal; the pattern 0xffff gives kind 6 with value 0; a zero high byte with any nonzero low byte gives kind 3 if bit 0x80 (core dumped) is set and kind 2 otherwise, with the signal in the low seven bits; any other pattern (a nonzero high byte with a low byte that is neither 0 nor 0x7f, and is not 0xffff) returns without storing either output word. These numbers are the standard child-status codes of the `siginfo` header (exited, killed, dumped, stopped, continued), which is a hint; the arithmetic is read.
- Otherwise it sets bit 0x20000000 in the thread flag word at thread+0x340 under the thread bit lock, calls `stop` with reason 7, clears the bit again, and takes and drops the read lock of the process's address-space record. It then acts on the first argument: zero returns 0; a negative value first waits on `sigisready`; if bit 0x80 is set in the word at +0xa0 of the record the thread points to at +0x328, it calls `prctl` (with sub-command 2 when the argument is -1, otherwise sub-command 3 once per count); if the bit is clear it calls `procblk` once per count. Read for the branches. The role (the restarted thread parks itself in a stop until the restart tool releases it, then releases or waits for its peers) is reasoned; the meaning of the `prctl` sub-commands 2 and 3 and of the bit at +0xa0 was not looked up.

## The `/proc` requests

The bulk of the state transfer is a set of `/proc` ioctl requests numbered 0x71b0 to 0x71e8.

- The `/proc` ioctl routine `prioctl` (0xc000000000434478) calls `ckpt_prioctl` (call at 0xc0000000004346a0) after a test of bit 0x400 in a flag word (the branch at 0xc000000000434684), and the per-thread routine (0xc000000000434c00) calls `ckpt_prioctl_thread` (call at 0xc000000000434c5c) after a test of bit 0x400 in the word at +0x10 of its first argument (0xc000000000434c40). `ckpt_prioctl_attr` is called at 0xc000000000435dc4, where the ordinary request table has no entry for the request. What opens a `/proc` file with that bit is unknown; the route is the `/proc` open path. Read for the dispatch, unknown for the opener.
- `ckpt_prioctl` subtracts 0x71b0 from the request, compares it unsigned with 0x2e and jumps through a table at 0xc0000000004e1f98; `ckpt_prioctl_thread` subtracts 0x71b4, compares with 0x35 and uses a table at 0xc0000000004e2108; `ckpt_prioctl_attr` subtracts 0x71b0, compares with 0x39 and returns a flag word per request from a table at 0xc0000000004e1dc8 (values such as 0x421, 0x423, 0x441, 0x443, 0x4c5, 0x601 and 0x603, or 0). The flag word is a per-request attribute, not a property of the opened file, and it is what sets bit 0x400: `prioctl` loads it once for the request (the fill routine at 0xc000000000435e70, whose table lookup ends in the call to `ckpt_prioctl_attr` at 0xc000000000435dc4 for requests it has no entry for), keeps it in the local word at sp+0x20, and tests it in turn: bit 0x80 picks the mode passed to `prlock` on the target (2 when set, 1 when clear, at 0xc000000000434554 to 0xc00000000043455c); bit 0x1 must be set on the process-wide path or the call fails with 22 (0xc000000000434630 to 0xc000000000434634 and 0xc000000000434728); bit 0x200 sends the request to the per-thread routine at 0xc000000000434c00 and passes bit 0x40 along to it (0xc000000000434638 to 0xc000000000434660); with 0x200 clear and 0x40 set, bit 0x400 sends it to `ckpt_prioctl` (0xc000000000434680 to 0xc0000000004346a0), and with 0x400 clear it goes to the table of ordinary requests (0xc0000000004346b0). Nothing about how a `/proc` file was opened enters this: the word comes only from the request code. Every value `ckpt_prioctl_attr` returns for a request in its range (0x71b0 to 0x71e8) is nonzero and has bit 0x400: the seven values are 0x421, 0x423, 0x441, 0x443, 0x4c5, 0x601 and 0x603 (the default 0x421 is the instruction in the jump's delay slot at 0xc00000000043aaa0), and a request outside the range gets 0 and so never reaches `ckpt_prioctl` by this route. Established by reading `prioctl` and the table code. Read for the tables and their sizes.

  The fill routine (0xc000000000435e70, 304 bytes, reached from `prioctl` at 0xc000000000434524 and read in full) is the consumer of four more bits. It takes the block at sp+0x10, the `/proc` node record, the user argument pointer and the open-file flags word, stores the request-table word in the block at +0x10 (0xc000000000435ee4), and then: bit 0x2 means the request needs the file open for writing, and returns 9 when bit 2 of the flags word is clear (tests at 0xc000000000435ef8 and 0xc000000000435efc, return at 0xc000000000435f0c to 0xc000000000435f10 and 0xc000000000435f84); bit 0x4 means the request is allowed on a node record whose type word at +0x58 is 1, and for that node type a request without bit 0x4 returns 13 (0xc000000000435f00 and 0xc000000000435f74 to 0xc000000000435f7c); bit 0x8 allocates a zeroed 0x370-byte buffer for the request and stores it in the block at +8 (`kmem_zalloc` at 0xc000000000435f30, store at 0xc000000000435f38); bit 0x10 does the same only when the user argument pointer is non-zero (0xc000000000435f20 to 0xc000000000435f28). The cleanup routine (0xc000000000435fa0) frees that buffer with the same 0x370 size. The meaning of node type 1 is not known; the reading says only that it is a value of that word. Established for the tests and the constants; that the flags word is the file's open flags and the return values 9 and 13 are the usual write-access and permission errors follows from the argument position and the numbers and is inferred. Bit 0x20 is not tested by `prioctl` between 0xc000000000434478 and 0xc0000000004346d0, by the fill routine, by the cleanup routine or by the per-thread routine up to its call of `ckpt_prioctl_thread` (0xc000000000434c5c); its consumer, if any, is in a handler that is passed the block, and the ordinary-table values that carry it (0x21, 0x23, 0x29, 0x2b, 0x63, 0x6b, 0x171 and 0x173) were not followed into those handlers. Bit 0x100 (in 0x171, 0x173 and 0x309) was not decoded either.

### What state is covered, by area

- **Registers and execution context.** Integer and floating-point registers, saved and restored in both the native layout and the 32-bit layouts (`irix5_prgetregs` and `irix5_prsetregs` and the floating-point pair). Read.
- **Address space.** The map (0x71ca), per-mapping status (0x71db), region duplication (0x71dc), the executable's segments (sub-command 1), the break (2), the data page (7), local unmapping (19) and growth (22). The shared-memory half of the address space is covered by `ckpt_shm` and the shm label calls (20, 21). Read for the entry points.
- **Share groups.** `ckpt_getshdpids` (sub-command 8) lists the group's member ids; `ckpt_fork` is called from `procfork` (0xc0000000002eab68, 1216 bytes; call at 0xc0000000002ead48), the common process-creation routine that `dofork` and `newproc` call (the call follows a branch on the routine's first argument at 0xc0000000002eac1c, which was not identified as a share-group flag), and copies the shared-memory record to the new process (whether a share-group member reaches it was not followed); `ckpt_restartreturn` has a share-group branch. Read for those calls.
- **File descriptors.** Duplicate (0x71d5), swap (0x71b9), status (0x71c8), reopen through the target (0x71c9), current and root directory (0x71d8, 0x71d9), set root (0x71da), file-identifier open (sub-command 0), times (9, 10), the kernel file address (4). Read.
- **Pipes and sockets.** A pipe made on restart comes from sub-command 5. For sockets the facility has only `ckpt_sockmate` (15), which returns the word at +0x40 of a file record, and `ckpt_fpaddr` (4), which returns the file record's kernel address. Neither reads socket state, buffered data or addresses; no handler in `cpr.a` calls a socket routine. Read that none is called; reasoned that the two let a user tool pair the two ends of a local connection, since both return identities, not content.
- **System V IPC.** `ckpt_shm` (0x71b4) returns the shared-memory ids a process has used, kept by the process record: `pproc_ckpt_shmget` (0xc0000000002de114, 264 bytes) records an id in an AVL tree hung off the process at +0xb30, 16 ids to a node (each slot holds the id plus one so that zero means empty), under the lock at +0xac8; `pproc_get_ckpt` (0xc0000000002de3e0, 92 bytes) with sub-operation 0 returns how many ids are recorded and with 1 copies them out (the two static helpers `ckpt_get_shmcnt` and `ckpt_get_shmlist` in `pproc_ckpt.o`); `ckpt_fork` (0xc0000000002de43c, 216 bytes) copies the tree to a new process; `ckpt_exit` (0xc0000000002de514, 112 bytes) frees it, and `pproc_exit` calls it (call at 0xc0000000002d4548). The shared-memory object also gets a mark: `as_allocshmmo` stores the value 4 at +0xc8 and a word at +0xcc of the new record when `ckpt_enabled` is set. Read. No handler touches message queues or System V semaphores by that name; user-space synchronisation objects are covered by `ckpt_getpusema`. Reasoned that message queues and semaphore sets are not saved; the route to settle it is the missing user-space tool.
- **Signals.** Pending state (0x71d0), the current signal (0x71d2), queueing a signal back (0x71d1, 0x71b7), and the `sigreturn` hook below. Read.
- **Timers.** Interval timers (0x71de, 0x71df); only the real-time timer has a setter, so the virtual and profiling timers are read but not restored by name. Reasoned from the handler list.
- **Threads.** The thread requests above run per user thread, and `uthread_apply` appears in `ckpt_setcontext` and `ckpt_getutinfo` uses `uthread_sched_getscheduler`, so thread state is part of it. Read for the calls; whether a checkpoint covers every thread kind (process, sproc, pthread) was not followed.
- **Credentials, accounting, process info.** `ckpt_setsuid` (16), accounting words (0x71b0, 0x71b1), `ps` record (0x71cd, 0x71ce). Read.

## File identifiers

- `ckpt_vp_open` (0xc00000000043a5c8, 280 bytes) allocates a file record (`vfile_alloc`), opens a vnode with the open mode masked with 0x790ff (`vp_open`), stores the supplied index in the word at +0x40 of the new file record, marks the file ready, stores the new descriptor, and reports the open to the audit code (`sat_open`). It is the open used by `ckpt_propen`, `ckpt_diropen`, `ckpt_mldset_raffopen` and the others. Read.
- `ckpt_lookup` (0xc00000000043a7fc, 100 bytes) allocates a record from the zone and asks the filesystem for the file identifier of a vnode (`ckpt_fid`, a static routine, which calls the vnode operation at table slot +0xb8 and, on error 89, the one at +0xb0). `ckpt_lookup_add` (0xc00000000043a880, 304 bytes) appends such a record to a list hung off the vnode at +0xf8, comparing identifiers with `memcmp` to avoid duplicates, and returns the position of the entry (the count before it); `ckpt_lookup_get` (0xc00000000043a9b0, 76 bytes) returns the nth entry; `ckpt_vnode_free` (0xc00000000043a9fc, 72 bytes) frees the whole list. `ckpt_lookup_add` does not record a vnode whose type word (+0x20) is 0, 2, 5, 7 or 8: it frees the record and returns -1. Read. `lookuppn` takes the identifier of the directory that held the last path component and `vn_open` adds it to the opened vnode's list, storing the index through an optional pointer; `ckpt_setfd` (0xc00000000043aa44, 60 bytes), called from `ioctl`, `elf64exec`, `elf32exec` and `remove_proc`, stores a value at +0x40 of a file record (default -1).
- `ckpt_diropen` (sub-command 0) uses all of that: it takes the file behind a descriptor, rejects a socket (flag 0x200 at +0x24 of the file record) or a record whose index is -1 with 22, fetches the entry for that index from the vnode's list, calls the filesystem's file-identifier lookup (slot +0x48 of the filesystem operations) to get the directory's vnode, and opens it with `ckpt_vp_open`. Reading: when a process opens a file, the kernel remembers which directory it found it in, as a file identifier, so a restart can open that directory without knowing a path and then open the file relative to it. Read for the mechanism; the purpose is reasoned.

## What it refuses

- Any `/proc` request that passes the caller's ABI word to `ckpt_supported_abi` (a static routine of 12 bytes at 0xc00000000043aae0 that returns whether bit 4 of the word is set) fails with 89 when the bit is clear: `ckpt_getmap`, `ckpt_getcontext`, `ckpt_setcontext`, `ckpt_shm`, `ckpt_getutinfo`, `ckpt_getpsinfo`, `ckpt_setpinfo`, `ckpt_getsiginfo`, `ckpt_cursig`, `ckpt_sigthread`, `ckpt_queuesig`, `ckpt_getitimers`, `ckpt_setrealitimer`, `ckpt_getpusema`, `ckpt_abort` and the memory-placement requests call it (24 call sites in all, found by scanning the IP35 text for calls to it); `ckpt_memstat` and `ckpt_dup` do not. `ckpt_getmap` was read in full and returns 89 in that case. Read for `ckpt_getmap`; the other callers are read as callers and the error is reasoned to be the same. The ABI word in `sigreturn` uses the values 2, 4 and 8 for the three ABIs and calls the 64-bit variant for 4, so bit 4 is the 64-bit native ABI; the request is that the tool making the call be 64-bit (the caller's ABI, not the target's: the context handlers carry both layouts). Reasoned.
- Sockets: `ckpt_diropen` returns 22 for a socket descriptor, and `ckpt_lookup_add` skips five vnode types; which types 0, 2, 5, 7 and 8 are was not looked up. No socket state is saved anywhere in `cpr.a` (see above).
- Without the facility configured, `ckpt_sys` and `ckpt_restartreturn` return 89 (stubs). Read.
- A fault reading a user word in `ckpt_stop` or `ckpt_mark` returns 14 when `fuiword` returns -1 and 9 for other negative values.
- What a checkpoint tool must refuse at a higher level (for example processes with open devices, graphics contexts or tty sessions) is not in the linked kernel's checkpoint code: no routine in `cpr.a` rejects a descriptor by file type except `ckpt_diropen` and `ckpt_lookup_add`. Unknown: the user-space tool decides.

## Jobs and array sessions

- `ckpt_getjinfo` (0xc00000000043dc88, 184 bytes) and `ckpt_setjinfo` (0xc00000000043dd40, 168 bytes) reach the process's job record through the pointer at proc+0xb50, its field at +0x28 and an operation at slot +0x258, then under a spinlock at +0xc of the record copy an 8-byte id, four 32-bit words and a 0x100-byte block into a 0x118-byte user structure (get), or write one 32-bit word (at +8) and the 0x100-byte block back (set); the id and the other words are not written. Read. That the record is the process-accounting job is reasoned from the field names around it, which are not in the symbol table.
- No routine in `cpr.a` or `pproc_ckpt.o` refers to an array session, an array session handle or a session id by name (the undefined symbols of the four objects were listed and none matches). The facility therefore does not appear to save or restore array sessions. Reasoned; the user-space tool might handle a session on its own, which is unknown.
- The published guide says the tool does handle them. *IRIX Checkpoint and Restart Operation Guide*, 007-3236-009 (78 pages; its text names the 6.5.16 and 6.5.20 releases, so it is not older than those), printed pages 4 and 35: `cpr -c statefile -p ASH:ASH` checkpoints every process of an array session, given the session handle, and jobs started with the array services are supported when their handle is unique; on each machine a checkpoint server starts and synchronises the clients and the statefiles are saved locally. That fits the kernel reading, because the grouping is then by process id in the tool and needs no kernel routine of its own. The statements are the manual's and are not checked against the tool, which is not held: **Inferred.**
- Accounting: `ckpt_getcsa` and `ckpt_setcsa` copy seven doublewords (+8 to +0x38) of the accounting record the pointer at proc+0x7a0 names, and return 1700 when that pointer is null. Read. What the counters mean is unknown.

## The on-disk format and the user tools

- The kernel never writes a checkpoint file. Every handler copies to or from the caller's memory (`bsd_copyin`, `bsd_copyout`, `copyin`, `copyout`) or manipulates descriptors; no routine in `cpr.a` calls a file write routine. Read. So the file format is entirely a user-space matter.
- The published manual is *IRIX Checkpoint and Restart Operation Guide*, document number 007-3236 (revisions -001 to -004 and -009 are held in the Library; -009 has 78 pages and was the one read). It covers the `cpr` command and its attributes (chapter 1), administration and the first lists of checkpoint-safe and unsafe objects (chapter 2, printed pages 20 and 21), the `SIGCKPT` and `SIGRESTART` handlers and `atcheckpoint` and `atrestart` for programs (chapter 3) and the per-object detail and limitations (chapter 4, "Checkpoint and Restart of System Objects", printed pages 33 to 36). It does not give the statefile layout, the restart steps at the level of kernel requests or the privilege rules, so those stay unknown. Revision -009 mentions the 6.5.16 and 6.5.20 releases; it was not compared with the 6.5.22 and 6.5.30 tool, which is not held. **Inferred** that it describes the shipped tool.
- Kinds of state, as the manual states them (printed pages 20, 21, 33, 34 and 36; each is the manual's word, not read in the tool): processes, process groups, sessions, array sessions, `sproc` groups, user memory, signal state, credentials, resource limits, working and root directories, locked memory and user semaphores, queued signals, open and mapped files with their locks (including NFS), pipes with their data, `/dev/tty`, `/dev/console`, `/dev/zero`, `/dev/null` and `ccsync`, System V shared memory (the original id is not restored), IRIX jobs, `PR_ATTACHADDR` regions, `blockproc` and `unblockproc` and R10000 counters read through `/proc` with the descriptor closed are checkpoint-safe; network sockets, X sessions and graphics terminals, other devices such as tape and CD-ROM, files opened with a set-user-id credential that cannot be re-established, and System V semaphores and message queues are not. A program that holds a socket or device is expected to close it in a `SIGCKPT` handler and reopen it in a `SIGRESTART` handler. **Inferred.** The kernel side agrees where it can be read: `cpr.a` calls no socket, message-queue or semaphore-set routine (above), and `ckpt_lookup_add` and `ckpt_diropen` are the only places that refuse a descriptor by file type.
- The commands and library are held in `root/6.5.30` since 2026-11-11 (`6.5.30/usr/sbin/cpr`, `6.5.30/usr/sbin/cview`, `libcpr.so` in three ABIs) and were read only for imports so far. `cpr` imports `ckpt_create`, `ckpt_restart`, `ckpt_stat`, `ckpt_remove` and a few helpers from `libcpr.so` and none of `syssgi`, `ioctl`, `fcntl` or `syscall`; `libcpr.so` imports `open`, `syssgi`, `sysmp`, `ioctl`, `fcntl`, `schedctl`, `opendir` and `syscall`. So the requests to the kernel facility described above come from the library, not the command (Established, dynamic symbol tables). Manual pages are not held. The format, the file layout, the restart sequence and the privilege rules of the tool are still unknown; see [open-questions.md](../../questions/README.md). The 6.5.22 tree has no such file.
